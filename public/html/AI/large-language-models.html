Large Language Models

Complete Guide to LLMs & Modern AI

Introduction to LLMs

A Large Language Model (LLM) is a neural network trained to predict the next token in a sequence. After enough data, parameters, and compute, that simple objective produces systems that can write, translate, summarize, reason over code, call tools, and hold a conversation.

An LLM is not a search engine and not a database. It compresses patterns from training text into weights. It can sound confident while being wrong. Ground it with retrieval, tools, and evaluation when the answer has to be true.

An LLM is a next-token engine: tokenize the prompt, run it through stacked transformer layers, sample the next token, repeat, then detokenize into text.

The three "larges"

  • Large data: Trillions of tokens from web, books, code, papers, and licensed corpora. Quality filtering matters as much as volume.
  • Large model: Billions to trillions of parameters. Mixture-of-Experts (MoE) models activate only a subset per token, so they can be huge without paying full dense cost.
  • Large compute: Pretraining runs on thousands of GPUs/TPUs for weeks. Inference still needs GPUs, batching, and a KV cache.
  • Transformer backbone: Almost every modern LLM is a decoder-only transformer with self-attention.

What an LLM actually does

Given tokens t1 … tn, the model outputs a probability distribution over the vocabulary for t(n+1). Chat products wrap this loop with a conversation template (system / user / assistant), sampling settings, and often tool calls.

Decoder-only (GPT-style)

Reads left to right. Best for generation, chat, coding, and agents. This is the default LLM architecture in 2026.

Encoder-only (BERT-style)

Reads both directions. Strong for classification, NER, and embeddings. Smaller and cheaper than generative LLMs.

Encoder–decoder (T5-style)

Encode the input, decode the output. Still used for translation and some speech/multimodal stacks.

What is a token?

A token is a subword chunk — not always a whole word. English averages roughly 0.75 words per token; code, URLs, and other languages differ.

// Typical BPE-style splits (illustrative) "chatbot" → ["chat", "bot"] "understanding" → ["under", "stand", "ing"] "GPT-5" → ["GPT", "-", "5"]

Keep these limits in mind from day one

  • They hallucinate: fluent text is not evidence. Cite sources or refuse when context is missing.
  • They have a knowledge cutoff unless you retrieve or tool-call live data.
  • They follow statistics, not a guaranteed world model. Math, dates, and rare facts need tools or RAG.
  • They are not private by default on hosted APIs. Check retention, regions, and zero-retention options.

Transformers

The Transformer (Vaswani et al., 2017, Attention Is All You Need) replaced recurrence with self-attention. Every token can look at every other token in the window in parallel. That is why LLMs scale on GPUs and why long-range references ("it" → "the cat") work at all.

Self-attention: each token builds a Query, Key, and Value. Similarity of Q to every K decides how much of each V to mix in. That is how "it" can bind to "cat".

A decoder block, in order

  1. Causal self-attention — token i may only attend to tokens ≤ i (no peeking at the future).
  2. Residual + layer norm — add the input back, then normalize so deep stacks stay trainable.
  3. Feed-forward network (MLP) — a large per-token MLP (often SwiGLU). This is where most parameters live.
  4. Residual + layer norm again. Repeat this block dozens to hundreds of times.

1. Self-attention (Q, K, V)

For each token the model projects the hidden state into three vectors:

  • Query (Q) — "what am I looking for?"
  • Key (K) — "what do I contain?"
  • Value (V) — "what information do I pass along?"

Attention weights are softmax(QKT / √d). The output is a weighted sum of values. In "The cat sat on the mat because it was tired", attention lets it put high weight on cat.

2. Multi-head attention

Several attention heads run in parallel with different projections. One head might track syntax, another coreference, another code structure. Outputs are concatenated and projected back to the model width.

3. Positional information

Attention itself is permutation-invariant. Models add position via RoPE (rotary embeddings) or similar schemes so "dog bites man" is not the same as "man bites dog". Long-context variants extend RoPE (YaRN, NTK scaling) so a 4K-trained model can run at 128K+ with some quality loss.

Why transformers beat RNNs for LLMs

Property RNN / LSTM Transformer
Parallelism Sequential over time Whole sequence in one GPU kernel
Long range Signal fades through steps Direct token-to-token links
Scaling Hard to train very deep/wide Stable with residuals + norm
Inference trick — KV cache reuses past keys/values

KV cache (why chat is cheaper than it looks)

When generating token 50, you should not re-attend over the first 49 from scratch. The model stores past Keys and Values. Memory grows with layers × heads × window × batch. That is why a 1M-token window is expensive even if the API lets you send it.

Training Process

Modern chat models are not "one training run". They are a pipeline: compress the internet, teach instruction following, then align behavior. Skipping a stage shows up as a model that can complete text but cannot follow "answer in JSON" or refuses nothing.

Pretrain for next-token prediction, supervised fine-tune on instruction pairs, align with preferences (RLHF or DPO), then serve behind an API with safety filters.

1. Pre-training

Unsupervised (self-supervised) causal language modeling on a huge mixture. The loss is: given the prefix, predict the next token. No human labels required at this scale.

Typical mixture:

  • Web crawls (filtered, deduplicated, PII-stripped)
  • Books, news, and reference text
  • Code (GitHub and similar) — large share of modern models
  • Scientific papers and math
  • Multilingual data if the model must not be English-only

Scaling laws: loss falls predictably as you grow data, parameters, and compute together. Under-training a huge model is a common waste. Chinchilla-style results: tokens often need to be ~20× parameters (order of magnitude, not a law of physics).

2. Supervised fine-tuning (SFT)

Show the model high-quality (instruction, response) pairs so it learns the chat format: helpful answers, refusals, tool-call syntax, markdown, JSON. A few thousand to a few million curated examples beat dumping more web text at this stage.

SFT data looks like:

  • Question → well-structured answer
  • Code task → working code + brief explanation
  • Domain docs → grounded summaries
  • Safety examples → refuse or redirect

3. Preference alignment (RLHF, DPO, RLAIF)

SFT teaches a format. Alignment teaches which answer humans prefer when several are possible.

Method How it works Tradeoff
RLHF Train a reward model on human rankings, then PPO (or similar) against it Strong, expensive, can over-optimize the reward
DPO Direct preference optimization — no separate RL loop Simpler; widely used for open models
RLAIF AI feedback instead of (or plus) human raters Cheaper scale; needs careful judge design
  • Improves helpfulness and style
  • Reduces toxic or policy-breaking completions
  • Does not magically add new world knowledge

4. Continued training you might actually run

Method When to use When not to
Better prompts + RAG Default. Knowledge changes; you need citations —
LoRA / QLoRA Style, format, a narrow domain, small GPU budget Facts that update weekly
Full fine-tune Lots of data, you own the weights, you can eval First experiment; "teach it our wiki"
Distillation Teacher labels → cheaper student for production You have no eval set

Do not fine-tune to "add knowledge" that will go stale. Fine-tune for behavior (tone, JSON shape, tool syntax). Put facts in retrieval.

Understanding Tokens

Models never see characters or words as you do. A tokenizer maps UTF-8 bytes to integer IDs from a fixed vocabulary (often 32K–200K entries). Training and billing both count these IDs.

How tokenization works

Most LLMs use Byte Pair Encoding (BPE) or SentencePiece. Frequent character pairs merge into longer tokens. Common words become one token; rare or misspelled strings shatter into many.

Why this design: a word-level vocab explodes for every language and typo. A character-level vocab makes sequences too long. Subwords sit in the middle.

Tokenization examples

// Patterns you will actually hit "chatbot" → ["chat", "bot"] "understanding" → ["under", "stand", "ing"] "Hello, world!" → ["Hello", ",", " world", "!"] // Gotchas: numbers and odd spacing often split badly "123456789" → many digit tokens, not one integer " gpt" vs "gpt" → different IDs because of the leading space

Count tokens in code

import tiktoken enc = tiktoken.get_encoding("o200k_base") # GPT-4o family text = "Explain RAG in one paragraph." print(len(enc.encode(text))) # input tokens ≈ this

Why tokens matter in production

  • Cost: APIs bill input + output tokens. Hidden tokens: system prompt, tools JSON, RAG chunks, retries.
  • Latency: Output tokens generate one-by-one. Long answers are slow even if the prompt is short.
  • Context: Prompt + completion must fit the window. Reserve budget for the answer (max_tokens).
  • Multilingual: Some languages tokenize less efficiently — the same sentence can cost 2–3× English.
Text Rough token count
1 English word ~1.3 tokens
1 sentence 15–30
1 paragraph 100–200
~1 page (500 words) 600–800
128K context ~90–100K words, or a medium book
1M context ~750K words — a large corpus, not "free memory"

Context Window

The context window is the maximum number of tokens the model can attend to in one request: system prompt + history + tools + retrieved docs + user message + the tokens it is about to generate.

Treat the window as a budget, not a hard drive. If you fill it with RAG chunks, you still need room for the answer. Overflow drops the oldest tokens — often the instructions.

Advertised windows (order-of-magnitude, 2026)

Class Typical window Use when
Classic GPT-3 era 2K – 8K History only — you will hit this in old tutorials
Mainstream chat (GPT-4o, Llama 3.x) 128K Most apps, a few PDFs, a repo file or two
Claude-class long context 200K Long threads, multi-file coding
Frontier APIs (Gemini, GPT-5.x, Claude 4.x) ~1M Whole books or large code trees — costly, quality varies
Llama 4 Scout class up to ~10M Extreme packing; still verify retrieval accuracy

Advertised vs effective context

Needle-in-a-haystack demos can look perfect while multi-fact recall collapses in the middle of a long prompt ("lost in the middle"). A 200K model that stays accurate across most of its range can beat a 1M model that fades after 100K. Prefer RAG plus a moderate window for production Q&A.

Operational costs of a huge window

  • Price: You pay for every input token, every time. Dumping a 400-page PDF on each turn is a billing incident.
  • Latency: Prefill time grows with prompt length (attention is roughly quadratic unless the kernel is optimized).
  • Memory: KV cache size tracks window × layers. Long chats need eviction, summarization, or a new thread.
  • Truncation: When the window fills, oldest messages vanish — including the system prompt if you are sloppy.

Practical tactics

  • Put durable instructions first, evidence next, the user question last (or follow the vendor's recommended order).
  • Retrieve 5–20 chunks instead of stuffing the corpus.
  • Summarize old turns into a rolling memory; keep the last N messages verbatim.
  • Cap max_tokens so a rambling completion cannot steal the whole budget.
  • Log prompt token counts. Alert when a route crosses a cost threshold.

Inference & Sampling

Training writes the weights. Inference is the live loop: prefilling the prompt, then sampling one token after another. Product quality is often sampling and prompt design, not a different base model.

Knob What it does Starting point
temperature Scales the logits before softmax. Higher = more random. 0–0.2 extraction / JSON; 0.7–1.0 brainstorming
top_p Nucleus sampling — only the smallest set of tokens with cumulative probability p Leave default if temperature is already set
max_tokens Hard cap on the completion Always set. Prevents runaway cost
stop sequences End generation at a marker Useful for custom templates
streaming Tokens arrive as they generate Better UX; still buffer full text for logs
seed Best-effort reproducibility Never guaranteed across vendors or versions

Serving stack (when you self-host)

vLLM, TensorRT-LLM, TGI, llama.cpp. Same product rules: continuous batching, paged KV cache, quantization (FP8 / INT8 / INT4), timeouts, and a queue. Speculative decoding uses a small draft model to speed a large one.

Embeddings

Embeddings are dense vectors that place text (or images, audio) in a space where distance ≈ meaning. They are the index for semantic search and RAG. They are not the chat model — many teams use a small embedding model plus a larger generative LLM.

In embedding space, "king" sits near "queen"; "apple" (fruit) sits far from royalty. Search becomes nearest-neighbor, not keyword match.

From text to vector

// Same idea every vendor uses "I love cricket" → [0.892, -0.244, 0.551, ...] // e.g. 768–3072 dims "king" → close to "queen" // cosine similarity high "king" → far from "apple" // unless the corpus is about Apple Inc.

Cosine similarity is the usual metric: 1.0 identical direction, 0 orthogonal, negative opposite. Most systems L2-normalize vectors so cosine and dot product agree.

Why embeddings matter

  • Semantic search — "PTO policy" matches "time-off rules" without shared keywords.
  • RAG — retrieve the few chunks that should sit in the prompt.
  • Clustering / dedup — near-duplicate documents, topic grouping.
  • Recommendations — similar items, similar users (with care for bias).

Embedding models vs generative LLMs

Embedding model Chat LLM
Output One vector per input Token stream
Size Often < 1B params Billions+
Cost Cheap; batchable Dominates your bill
Examples text-embedding-3, Voyage, E5, GTE GPT, Claude, Gemini, Llama

Matryoshka / flexible dimensions: some models let you truncate a 3072-d vector to 512-d and keep most quality — useful when RAM and ANN indexes hurt.

Always embed the query with the same model you used for documents. Mixing vendors silently destroys recall.

Vector Databases

A vector database stores embeddings plus metadata and answers "nearest neighbors to this query vector" in milliseconds, even at millions of rows. Postgres with pgvector is enough to start; purpose-built stores add filters, hybrid search, and ops.

What a row looks like

{ "id": "doc-42-chunk-3", "vector": [0.12, -0.55, 0.33, ...], "text": "Employees receive 20 days of paid leave...", "metadata": { "source": "hr-handbook.pdf", "page": 12, "acl": "staff" } }

Vector DB vs a normal SQL table

Feature Vector index Traditional DB
Query Approximate nearest neighbor Exact match, ranges, joins
Speed at 10M × 1536-d Designed for this Needs an extension / separate index
Filters Metadata pre/post-filter (ACL, tenant, date) WHERE clauses
Hybrid Vector + BM25 / keyword Full-text search only

Indexing algorithms

HNSW (Hierarchical Navigable Small World)

Graph-based ANN. Excellent recall/latency. Higher RAM. Default in many products.

IVF / IVF-PQ

Cluster the space, search a few clusters. PQ compresses vectors. Needs a training pass. Good at huge scale.

DiskANN / disk-backed graphs

When vectors no longer fit in RAM. Slightly higher latency, much cheaper machines.

Use cases

  • Semantic search and RAG with citations
  • Recommendations and similar-item lookup
  • Multimodal search (embed images with CLIP-style models)
  • Anomaly detection (points far from the cluster)

LangChain

LangChain is a toolkit for composing prompts, models, retrievers, and tools. Prefer LCEL (LangChain Expression Language: prompt | model | parser) over the old "Chain" classes you still see in 2023 tutorials.

Use it for: swapping OpenAI / Anthropic / local models behind one interface, retrieval, tool calling, and getting a first agent running. Do not treat it as a substitute for logging, evals, or a real queue.

Minimal LCEL example

from langchain_openai import ChatOpenAI from langchain_core.prompts import ChatPromptTemplate llm = ChatOpenAI(model="gpt-4.1-mini", temperature=0) prompt = ChatPromptTemplate.from_messages([ ("system", "You are a concise tutor. If unsure, say so."), ("human", "{question}"), ]) chain = prompt | llm print(chain.invoke({"question": "What is a token?"}).content)

Building blocks

1. Chat models

Wrappers for OpenAI, Anthropic, Google, Bedrock, Ollama. Same .invoke / .stream / .bind_tools shape so you can swap providers.

2. Prompts

Templates with variables. Keep them in files, version them, and never concatenate untrusted user text into the system message without a delimiter.

prompt = ChatPromptTemplate.from_messages([ ("system", "Translate {source} → {target}. Only output the translation."), ("human", "{text}"), ])

3. Retrievers & vector stores

Document loaders → splitters → embed → store. Retrievers return Documents the prompt can cite. This is RAG without a custom ANN loop.

4. Tools & agents

Expose Python functions as tools. The model chooses names + arguments (function calling). LangGraph is the better home for multi-step control flow.

5. Memory

Pattern Use
Buffer Last N messages — simple chat
Summary Compress old turns so the window survives
Vector memory Recall semantically related past facts

In production, persist memory in your DB keyed by thread_id. Do not rely on in-process RAM.

When LangChain helps vs gets in the way

Helps Gets in the way
Provider abstraction, retrievers, quick RAG Debugging a 12-layer abstraction for one API call
Standard document loaders You already have a clean HTTP client and schema
LCEL streaming You need a strict state machine — use LangGraph

LangGraph

LangGraph models an agent as a stateful graph: nodes are functions, edges are control flow, and a shared state object is checkpointed after each step. Loops, retries, and human approval are first-class — that is the gap linear LangChain chains never filled well.

LangChain vs LangGraph

LangChain LCEL LangGraph
Shape DAG / pipeline Graph with cycles
State Mostly request-scoped Typed state, reducers, checkpoints
Human-in-the-loop DIY Interrupt, resume from checkpoint
Fit RAG, extract, classify Agents, research loops, approvals

Core pieces

  • State — a TypedDict or Pydantic model: messages, files, flags.
  • Nodes — call an LLM, a tool, a ranker, or a human inbox.
  • Edges — including conditional edges ("if tool error → retry, else END").
  • Checkpointer — Postgres/SQLite so a crash or "wait for user" does not lose the run.

Example shapes

Workflow Graph idea
ReAct agent model → tools → model … until no tool call
Research search → read → decide more search? → write
Support classify → retrieve → draft → human approve → send
Codefix edit → test → if fail, loop with logs

MCP (Model Context Protocol)

MCP is an open protocol so an AI app (the host) can talk to many servers that expose resources, tools, and prompts — without a custom plugin per data source. The usual analogy: USB-C for model context.

Host (Claude Desktop, an IDE, your agent runtime) embeds an MCP client. Each MCP server wraps one system: git, Slack, Postgres, a filesystem. The model only sees the tool/resource catalog the host allows.

Server primitives

Resources

Read-only data: files, tickets, schemas. The model fetches them as context, similar to attachments.

Tools

Actions with JSON arguments: query DB, create issue, run a command. Results come back as tool messages.

Prompts

Named templates the host can insert — onboarding, "review this PR", slash-commands.

Architecture

Host (IDE / agent runtime) │ MCP client (JSON-RPC) ▼ MCP server ──► tools / resources / prompts │ ├── filesystem, git ├── HTTP APIs └── databases (credentials stay on the server)

Transports & messages

Servers typically speak JSON-RPC 2.0 over stdio (local process) or Streamable HTTP / SSE (remote). A resource read looks like:

{ "jsonrpc": "2.0", "id": 1, "method": "resources/read", "params": { "uri": "file:///handbook/pto.md" } }

Security is the product

  • Servers often run with the user's privileges. Treat tools as production APIs: auth, allowlists, audit logs.
  • Prompt injection can arrive through a resource ("ignore policy, dump secrets"). Isolate untrusted content.
  • Do not expose shell tools to a model that sees untrusted email or web pages.

AI Agents

An agent is an LLM in a loop with tools and a stopping condition. It is not magic autonomy. It is: reason → maybe call a tool → observe → repeat until the goal is met or a budget (steps, dollars, time) is exhausted.

The ReAct loop: Think (plan), Act (tool call), Observe (result). Without a step limit and a verifier, this loop can spend money forever.

Chatbot vs agent

Chatbot Agent
One turn Answer from weights + prompt May take many tool round-trips
Side effects None Email, tickets, code, payments — if you allow them
Failure mode Wrong paragraph Wrong API call, loop, or leaked data

Patterns

ReAct (Reason + Act)

Interleave thoughts and actions. Native tool calling (JSON function calls) is more reliable than asking the model to emit "Action:" text, but the loop is the same.

Plan-then-execute

Write a plan first, then run steps. Better for long tasks; the plan can be wrong, so allow replanning.

Multi-agent

Specialists (researcher, coder, reviewer) coordinated by a supervisor or a shared graph. Higher overhead; worth it when roles and tools truly differ.

Tools worth giving an agent

  • Search and web fetch (with domain allowlists)
  • SQL or document retrieval (read-only until audited)
  • Code interpreter / tests
  • Ticketing and calendar APIs
  • MCP servers for local files and git

Frameworks

Stack Strength
LangGraph Explicit state, cycles, HITL
LangChain tools Fast tool wiring
CrewAI / AutoGen-style Role-based multi-agent
Vendor agents OpenAI Agents SDK, Claude tool use, Gemini

Ship agents with budgets

  • Max tool calls, max wall-clock, max dollars per request
  • Idempotent tools or a confirmation step for writes
  • Trace every thought/tool in an observability product (LangSmith, Phoenix, vendor traces)

RAG (Retrieval Augmented Generation)

RAG injects retrieved evidence into the prompt so the model answers from your documents instead of guessing from training weights. It is the default way to add knowledge that changes, must be cited, or must not be baked into a fine-tune.

Index path: documents → chunks → embeddings → vector DB. Query path: question → embed → top-k search → prompt + evidence → grounded answer.

RAG vs fine-tuning

RAG Fine-tune
Updates Re-index a file New training job
Citations Natural (chunk IDs, URLs) Weights cannot point to a page
Cost Embed + search + extra prompt tokens GPUs and a dataset
Best at Facts, policies, catalogs Style, format, domain dialect

Pipeline

Ingest

  • Load PDF, HTML, Markdown, tickets, wiki exports.
  • Chunk ~400–1,000 tokens with 50–150 token overlap. Prefer headings and paragraph boundaries over naive character splits.
  • Store text, embedding, and metadata (source, ACL, date).

Retrieve

  • Embed the query with the same model.
  • Top-k (often 5–20). Hybrid search (BM25 + vector) helps IDs, error codes, and names.
  • Rerank with a cross-encoder if precision matters.
  • Filter by tenant / ACL before the prompt. Never retrieve another customer's chunks.

Generate

  • Instruct: use only the context; cite; say "I don't know" if missing.
  • Keep untrusted documents in a clearly marked block so they cannot override the system prompt.

Where RAG fails (debug these first)

  • Wrong chunk size — tables and policies split mid-sentence.
  • Missed retrieval — query wording ≠ document wording; add hybrid + synonyms / HyDE.
  • Context stuffing — 40 mediocre chunks drown the good one (lost in the middle).
  • Stale index — source changed, vectors did not.
  • Eval-free — no golden questions, so you only notice in production.

Use cases

  • Internal docs, runbooks, and policy Q&A
  • Customer support with a knowledge base
  • Legal / medical literature (with specialist review)
  • Codebase Q&A (often hybrid with grep / AST, not vectors alone)

Prompt Engineering

Prompt engineering is specifying the task so the next-token distribution lands on useful outputs. Treat prompts as versioned code: files, diffs, evals — not chat folklore.

Prompt parts

Part Job Example
System Role, hard rules, output contract "Only use CONTEXT. Cite chunk ids."
Context Evidence, code, retrieved docs Marked as untrusted data
Instruction The actual ask "List three failure modes."
Examples Show the format Few-shot input/output pairs
Schema Machine-readable output JSON Schema / tool call

Techniques

Zero / one / few-shot

Zero-shot: just the task. Few-shot: 2–5 examples of the exact format. Examples beat adjectives ("be professional") for classification and extraction.

Classify sentiment: Positive, Negative, Neutral. "This product is amazing!" → Positive "Terrible experience" → Negative "Best purchase ever!" →

Chain-of-thought

Ask for steps when the task is multi-hop math or logic. It costs output tokens. Some models reason internally; you still want a short final answer for the user.

Structured output

Prefer JSON mode, tool calls, or constrained decoding. Validate with Pydantic or Zod. On failure, retry once with the validator error — then stop.

"You are an expert Python tutor. Explain list comprehensions in 3 bullets for a beginner. No code longer than 4 lines."

Prompt injection

Anything retrieved or pasted by a user can say "ignore previous instructions". Separate instructions from data. Never execute tools solely because a PDF asked you to. Allowlist tools per route.

Iterate like an engineer

  • Keep a set of 30–100 golden prompts with expected properties (not just one happy-path demo).
  • Change one variable at a time: model, temperature, chunk count, system text.
  • Log traces. A "worse" prompt that is cheaper and more faithful can be the win.

Natural Language Processing (NLP)

NLP is the broader field of making computers handle human language. LLMs absorbed many classic pipelines (separate taggers, parsers, and task-specific models), but specialized systems still win on latency, privacy, and high-precision labels.

Core tasks (now often one LLM call)

Task What it is Still use a specialist when
Classification / sentiment Label a text Millions of cheap predictions / day
NER People, orgs, places, SKUs You need consistent spans and IOB tags
Translation Language A → B Regulated, high-volume localization
QA / summarization Answer or compress You must ground in retrieved text (RAG)
Speech (ASR / TTS) Audio ↔ text Always a dedicated model; LLM consumes the transcript

How the field got here

1990s Rule-based NLP, regex, grammars 2000s Statistical n-grams, HMMs 2010s Features + SVM; then Word2Vec, RNNs, LSTMs 2017+ Transformers (BERT, GPT) 2020+ Large generative models + instruction tuning 2023+ Tools, RAG, agents, multimodal, long context

The LLM stack still uses NLP pieces under the hood: tokenization, embeddings, attention, sequence modeling. You did not skip NLP — you inherited it.

Data Processing for LLMs

Pretraining and RAG both fail in the same way: garbage in, confident garbage out. LLM data work is less about z-scores on numeric columns and more about deduplication, PII, toxicity, and license.

Corpus hygiene (pretraining / fine-tune)

  • Dedup — exact hashes plus near-dup (MinHash). Repeated web spam warps the model.
  • PII — emails, phones, keys. Strip or skip; do not train on secrets.
  • Quality filters — language ID, adult content policy, boilerplate (cookie banners).
  • License / robots — you cannot "fair use" your way out of every ToS. Track sources.
  • Mixture & packing — pack short docs into sequences to use the context; upsample high-value domains (code, math) on purpose.

RAG / application data

  • Normalize encodings, strip HTML, keep headings.
  • Preserve tables as markdown or CSV snippets so chunking does not destroy them.
  • Attach ACL metadata at ingest — retrieval-time filter, not prompt-time hope.
  • Re-embed when the chunker or embedding model changes (version the index).

Classic cleaning (still useful for tabular ML beside an LLM)

Issue Approach
Missing values Drop, impute, or model as a category
Duplicates Exact then fuzzy
Date formats ISO 8601 everywhere
Categorical text Do not one-hot 100k product names into an LLM prompt — retrieve instead
  • Biased data produces biased completions. Measure on subgroups, not only average accuracy.
  • A "clean" dump that is 80% SEO spam will still teach SEO spam.

Limits, Safety & Evaluation

A useful LLM app assumes the model is wrong by default and then adds retrieval, tools, schemas, and tests until the error rate is acceptable.

Hallucination

The model samples a fluent continuation. Mitigation: RAG, "answer only from context", citations, tool use for facts, lower temperature for extraction.

Distribution shift

Your users' jargon, languages, or 2026 events may be rare in training. Fine-tune style; retrieve facts; add tools.

Jailbreaks & injection

Users and documents will try to override policy. Separate data from instructions; least-privilege tools; monitor.

Eval or it did not happen

Golden sets, LLM-as-judge (with human spot checks), faithfulness vs relevancy for RAG, online A/B on real tasks.

Offline eval ideas: exact match for extraction, rubric scores for writing, citation precision/recall for RAG, task success for agents (did the test suite pass?). Re-run on every prompt or model change.

LLM APIs & Services

Most products call a hosted chat completions (or Responses) API: messages in, tokens out. Wrap vendors so you can change models without rewriting the app. Always set timeout, max retries, and a cheaper fallback for 429/5xx.

A production-shaped call

from openai import OpenAI client = OpenAI() # or base_url= for compatible servers resp = client.chat.completions.create( model="gpt-4.1-mini", messages=[ {"role": "system", "content": "Be concise. No invented APIs."}, {"role": "user", "content": "List 3 RAG failure modes."}, ], temperature=0.2, max_tokens=400, timeout=30, ) print(resp.choices[0].message.content) print(resp.usage) # prompt_tokens, completion_tokens

Pricing changes constantly. In 2026, input is often a few cents to a few dollars per million tokens; output is higher. Log tokens_in, tokens_out, model, and estimated USD on every request. Cached prompt prefixes (where offered) can cut repeated system+RAG costs.

Popular LLM Models

There is no universal "best" model. Pick for task, latency, cost, context, and where the data is allowed to live. Re-benchmark quarterly; leaderboards and product names move faster than your architecture should.

How to choose

  • Task: extraction vs open writing vs coding vs vision
  • Latency: Flash / mini / Haiku classes for interactive UI
  • Context: do you truly need 1M, or is RAG enough?
  • Privacy: VPC, on-prem, or zero-retention API
  • Features: tool calling, JSON schema, vision, computer use
  • Eval: your golden set beats a public MMLU screenshot

Closed vs open weights

Open weights (Llama, Qwen, Mistral, DeepSeek) Closed API (GPT, Claude, Gemini)
Cost shape GPUs, idle capacity, your ops Pay per token; easy to start
Privacy Data can stay in your VPC Contract + region + retention settings
Quality Often close on many tasks; distill for cost Usually the frontier for hard reasoning
Customization LoRA, full fine-tune, custom decoding Limited to vendor features

A sane default stack

  1. Small/fast model for classification, routing, and cheap RAG.
  2. Frontier model for hard reasoning, coding, and agent planning.
  3. Dedicated embedding model for the index.
  4. Evals that tell you when a swap is a regression.
