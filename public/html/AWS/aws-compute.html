📚 AWS Compute Overview

AWS Compute is the set of services that run your code. The same workload — a web API, a nightly ETL job, a GPU training run — can land on a virtual machine, a packed container host, a serverless container, or a 200-millisecond function. The hard skill is not memorizing product names. It is matching how long the work lives, how much of the stack you want to own, and what hardware you actually need.

Move right when you can give up OS and capacity planning. Move left when you need a custom kernel, GPU, or a process that must stay warm for hours.
How to think about compute

Rent time on someone else's CPU

EC2 is a lease on a virtual machine: you pick the AMI, instance family, VPC subnet, and security group. Lambda is a lease on milliseconds of a managed runtime. Fargate sits in between — you ship a container image and AWS boots an isolated microVM for that task only.

Architects usually start at the highest abstraction that still works, then drop down when they hit a hard constraint: 16-minute jobs, GPU, Windows licensing, sticky in-memory sessions, or a kernel module the platform will not load.

Start here when

  • The work is event-driven and finishes in minutes → Lambda
  • You already have a Docker image and want no hosts → Fargate
  • You need Kubernetes APIs or multi-cloud → EKS
  • You need the OS, GPU, or a long-lived process → EC2

A common mistake

  • Putting a 2-hour video encode on Lambda (15-minute cap)
  • Running always-on APIs on oversized On-Demand EC2 with no ASG
  • Choosing EKS before the team can operate Kubernetes
  • Leaving unused Elastic IPs and stopped volumes attached

Key Principle: Right-Sizing Compute

Start with the highest abstraction that meets your needs. Use Lambda for event-driven, short-lived tasks. Use Fargate when you need containers without managing servers. Use EC2 when you need full control over the OS, custom kernels, or specialized hardware (GPU, bare metal).

🖥️ Amazon EC2 (Elastic Compute Cloud)

Amazon EC2 provides resizable, scalable virtual machines (VMs) in the cloud. It is AWS's flagship Infrastructure as a Service (IaaS) offering — you get full root access to the operating system and complete control over the compute environment.

An instance is more than a CPU. At launch AWS attaches an Elastic Network Interface (ENI) in a subnet, applies a security group, boots from an AMI onto EBS or Instance Store, and (if you set an instance profile) hands the guest temporary IAM credentials through the instance metadata service. Treat that bundle as infrastructure-as-code, not a pet you SSH into forever.

Key Concept: EC2 enables businesses to quickly deploy, manage, and scale applications without worrying about physical infrastructure. You pay only for the compute time you use.

Under the Hood: The AWS Nitro System

Modern EC2 instances (C5, M5, R5 and newer) run on the AWS Nitro System. Unlike traditional virtualization where the hypervisor manages CPU, memory, and I/O, Nitro offloads networking, storage, and security to dedicated hardware cards. This delivers bare-metal-like performance in a virtualized environment with lower overhead and stronger isolation.

Production Best Practice: Immutable Infrastructure

Avoid "snowflake" servers — manually configured machines that are unique and fragile. Instead, use AMIs and User Data scripts to make every instance reproducible. In production, if a server misbehaves, terminate it and let Auto Scaling launch a fresh, verified replacement rather than SSH-ing in to patch it.

EBS vs. Instance Store — The Persistence Dilemma

  • 💾 Amazon EBS (Elastic Block Store): Network-attached persistent storage. Survives instance stop/terminate. Supports snapshots and encryption. Use for databases and critical data.
  • ⚡ Instance Store: Physically attached to the host. Offers extremely high IOPS but is ephemeral — data is lost if the instance stops or the underlying hardware fails. Use for caches, buffers, and scratch data.
  • 📁 EFS / S3: Shared file storage (EFS) and object storage (S3) accessible from EC2 for logs, assets, and shared application data.

📀 Amazon Machine Image (AMI)

An AMI is a template used to create EC2 instances containing everything needed to launch a virtual server.

What's Inside an AMI?

  • OS (Ubuntu, Amazon Linux, Windows)
  • App server (Apache, Nginx)
  • Language runtimes (Node.js, Python)
  • Pre-installed software/configs
  • Custom settings

Common Use Cases

  • Create pre-configured environments for scaling
  • Backup a working server (snapshot) - Disaster recovery
  • Launch multiple EC2s with same setup
  • Deploy web apps with Docker, Nginx, Node, etc.

Creating an AMI

1. Select EC2 instance 2. Actions → Image and templates → Create image 3. Name the AMI and configure block device mappings 4. Launch new instances from the AMI in any region (copy AMI cross-region for DR)

AMI Types

TypeDescriptionUse Case
EBS-backed Root volume is an EBS snapshot Most common — supports stop/start, persistence
Instance Store-backed Root volume is on Instance Store Fast boot, ephemeral — cannot be stopped, only terminated
Golden AMI Pattern: Build AMIs using tools like Packer or EC2 Image Builder. Bake in security patches, agents (CloudWatch, SSM), and application dependencies. Version and test AMIs in a pipeline before rolling out to Auto Scaling Groups.

📈 EC2 Auto Scaling

EC2 Auto Scaling automatically adjusts the number of EC2 instances based on demand, ensuring you have the right capacity at the right time while optimizing costs.

Key Components

ComponentDescription
Launch Template Defines AMI, instance type, security groups, user data, and IAM role for new instances
Auto Scaling Group (ASG) Collection of EC2 instances with min, max, and desired capacity
Scaling Policies Rules that trigger scale-in or scale-out (target tracking, step scaling, scheduled)
Health Checks EC2 status checks or ELB health checks — unhealthy instances are replaced

Scaling Policy Types

  • Target Tracking: Maintain a metric at a target value (e.g., average CPU at 50%)
  • Step Scaling: Scale by defined steps based on alarm breach magnitude
  • Simple Scaling: Scale by a fixed amount when an alarm triggers
  • Scheduled Scaling: Scale at predictable times (e.g., business hours)
  • Predictive Scaling: Uses ML to forecast traffic and scale proactively
Best Practice: Always use Auto Scaling Groups behind a load balancer. Set min = 2 across multiple Availability Zones for high availability. Use mixed instances policy to combine On-Demand base capacity with Spot instances for cost savings.

Warm Pools and Instance Refresh

  • Warm pool: Keep pre-initialized stopped (or running) instances so scale-out does not wait for AMI boot and user-data. Useful when user-data installs packages for minutes.
  • Instance refresh: Rolling-replace the ASG when you ship a new AMI or launch-template version. Pair with a bake time and health-check grace so you do not dump unhealthy replacements into the ALB.
  • Lifecycle hooks: Pause scale-out/in so a script can drain connections, pull logs, or register with a config store before the instance is in service or terminated.

⚖️ Elastic Load Balancing (ELB)

Elastic Load Balancing automatically distributes incoming traffic across multiple targets (EC2 instances, containers, IP addresses) in one or more Availability Zones.

Load Balancer Types

TypeLayerProtocolsBest For
Application Load Balancer (ALB) Layer 7 (HTTP/HTTPS) HTTP, HTTPS, WebSocket Web apps, microservices, path/host-based routing
Network Load Balancer (NLB) Layer 4 (TCP/UDP) TCP, UDP, TLS Ultra-low latency, millions of RPS, static IP
Gateway Load Balancer (GWLB) Layer 3 IP Third-party virtual appliances (firewalls, IDS)
Classic Load Balancer (CLB) Layer 4 & 7 HTTP, HTTPS, TCP, SSL Legacy — prefer ALB or NLB for new workloads

ALB Advanced Features

  • Path-based routing: Route /api/* to one target group, /images/* to another
  • Host-based routing: Route api.example.com vs www.example.com
  • Weighted target groups: Canary deployments and blue/green releases
  • Sticky sessions: Bind user sessions to a specific instance
  • Integration with WAF: Web Application Firewall protection at the edge
The ALB is multi-AZ. The ASG keeps min capacity in more than one zone. A failed instance is pulled from rotation and replaced — you do not SSH in to “fix the box.”
Users → Route 53 → ALB → ASG (2+ AZs) → App / RDS

High Availability Architecture Pattern

Route 53 → ALB (multi-AZ) → Auto Scaling Group (instances in 2+ AZs) → RDS Multi-AZ. The load balancer performs health checks and only routes traffic to healthy instances. Combined with Auto Scaling, this architecture self-heals when instances fail. Target-group health checks should hit a cheap /health that proves the app can reach its database — not just that nginx is listening.

Target Groups and Stickiness

  • A load balancer forwards to target groups (instances, IPs, or Lambda). One ALB can host many apps via host/path rules.
  • Deregistration delay (connection draining) lets in-flight requests finish before an instance is removed.
  • Sticky sessions (ALB cookies) hide a stateful app, but they fight even load and rolling deploys. Prefer external session stores (ElastiCache, DynamoDB).

🔄 EC2 Instance Lifecycle

Understanding instance states is critical for cost management and operational reliability.

StateBilledWhat Happens
Pending No Instance is being launched
Running Yes (compute) Instance is active and accessible
Stopping Yes Instance is shutting down (EBS-backed only)
Stopped No (compute) EBS data persists; public IP released unless Elastic IP attached
Shutting Down Yes Instance is terminating
Terminated No Instance and Instance Store data permanently deleted
Cost Tip: Stopped instances still incur EBS storage charges. Terminate unused instances and delete unattached EBS volumes. Use AWS Instance Scheduler or Lambda to stop dev/test instances outside business hours.

Stop vs. Hibernate vs. Terminate

  • Stop: Preserves EBS data. RAM contents lost. Can restart later.
  • Hibernate: Saves RAM contents to EBS root volume. Faster restart with application state intact. Requires hibernation-enabled AMI.
  • Terminate: Permanently deletes the instance. EBS volumes set to DeleteOnTermination are also deleted.

⚡ AWS Lambda - Serverless Computing

AWS Lambda is a serverless computing service that runs code without provisioning or managing servers. You upload a handler. AWS provisions an execution environment when an event arrives, runs the function, then freezes or recycles that environment. There is no instance to patch and no idle bill when nothing is invoked.

Triggers are the product. The function is a short, idempotent reaction. Design for retries — SQS and EventBridge will call you more than once.

Key Features

  • Event-Driven: Triggered by AWS services or HTTP requests
  • Automatic Scaling: Handles thousands of requests per second
  • Pay-as-You-Go: Charged only for execution time (milliseconds)
  • No Server Management: AWS handles everything

Supported Languages

Python, Node.js, Java, C#, Ruby, PowerShell, Go

How Lambda Works

  1. Create Function: Choose runtime and upload code
  2. Define Trigger: Link to event source (S3, API Gateway, DynamoDB)
  3. Execution: AWS executes and scales automatically
  4. Monitoring: CloudWatch provides logs and metrics

Use Cases

  • Data processing from Kinesis, DynamoDB, IoT
  • Real-time file processing (resize images, scan files)
  • Web & mobile API requests via API Gateway
  • Automated infrastructure management
  • Chatbots & AI integration

Example: Simple Lambda Function (Python)

import json def lambda_handler(event, context): return { 'statusCode': 200, 'body': json.dumps('Hello from AWS Lambda!') }

Limitations

  • Execution Time Limit: Maximum 15 minutes per invocation
  • Memory Constraints: 128 MB to 10,240 MB (10 GB)
  • Deployment Package: 50 MB zipped, 250 MB unzipped (use S3 for larger)
  • Concurrent Executions: 1,000 default per region (can request increase)
  • Cold Starts: Initial invocation latency when scaling from zero

Technical Deep Dive: Cold vs. Warm Starts

When Lambda is invoked after being idle, AWS provisions a new execution environment (container). This latency is a cold start. Subsequent requests reuse the warm environment and execute much faster. Mitigations include keeping functions small, using Provisioned Concurrency for latency-sensitive APIs, choosing lighter runtimes (Node.js/Python over Java), and using Lambda SnapStart for Java functions.

Common Event Sources (Triggers)

TriggerUse Case
API Gateway / Function URLREST APIs, webhooks, HTTP endpoints
S3File upload processing, image resizing
DynamoDB StreamsReal-time data processing on table changes
SQS / SNSAsync message processing, fan-out patterns
EventBridgeScheduled tasks, event-driven architectures
KinesisStream processing, log analysis
CognitoUser authentication triggers (pre-sign-up, post-auth)
CloudWatch EventsCron jobs, infrastructure automation

Lambda Pricing Model

  • Requests: Charged per invocation (first 1M/month free tier)
  • Duration: Billed in 1ms increments based on memory allocated × execution time
  • Provisioned Concurrency: Additional charge for pre-warmed environments

Lambda Layers & Extensions

Layers let you package libraries, custom runtimes, and dependencies separately from your function code — share across multiple functions. Lambda Extensions run alongside your function for monitoring, security, and configuration tools (Datadog, AppConfig, etc.).

Versions, Aliases, and Destinations

  • Publish a version to freeze code + layers. $LATEST is mutable and unsafe as a production target.
  • Aliases (live, canary) point at versions and can split traffic (5% to v12, 95% to v11) for gradual rollouts.
  • Destinations send async success or failure payloads to SQS, SNS, EventBridge, or another Lambda — cleaner than stuffing that logic in the handler.
  • VPC-attached functions get an ENI in your subnet so they can reach RDS or ElastiCache. Use Hyperplane ENIs (modern default) and put functions in private subnets with a NAT or VPC endpoints. Do not attach a VPC “just in case.”
# Package, update, and publish a version zip function.zip lambda_function.py aws lambda update-function-code --function-name orders-api --zip-file fileb://function.zip aws lambda publish-version --function-name orders-api aws lambda update-alias --function-name orders-api --name live --function-version 12 \ --routing-config AdditionalVersionWeights={"13"=0.05}
Idempotency: At-least-once delivery is the default for most async sources. Use a request id, DynamoDB conditional write, or SQS FIFO + deduplication so a retry does not charge a customer twice.

🐳 Amazon ECS (Elastic Container Service)

Amazon ECS is a fully managed container orchestration service that simplifies deployment and scaling of Docker containerized applications on AWS.

The Dockerfile is portable. The control plane is not. Pick ECS for AWS-native simplicity, Fargate to drop hosts, EKS when you need kubectl and cluster portability.

Control Plane vs. Data Plane

  • Control Plane (managed by AWS): Scheduling, cluster state, API requests, service discovery
  • Data Plane (your choice): Where containers run — EC2 instances (you manage hosts) or Fargate (serverless, AWS manages hosts)

Core ECS Concepts

ConceptDescriptionKubernetes Equivalent
Cluster Logical grouping of resources Cluster
Task Definition Blueprint: container image, CPU, memory, env vars, ports Pod spec
Task Running instance of a task definition Pod
Service Maintains desired number of running tasks Deployment + Service

Key Features

  • Fully Managed: AWS handles cluster management and orchestration
  • Two Launch Types: EC2 (more control) or Fargate (serverless)
  • Deep AWS Integration: ELB, IAM, CloudWatch, Auto Scaling

How ECS Works

  1. Define Task Definition: Specify container image, CPU, memory
  2. Choose Launch Type: EC2 or Fargate
  3. Deploy Service: Maintain desired task count
  4. Attach Load Balancer: Use ALB or NLB
  5. Monitor & Scale: ECS adjusts based on demand

ECS vs Other Services

FeatureECSEKSFargate
Orchestration ECS-native Kubernetes-native ECS/EKS
Serverless No (unless Fargate) No Yes
Complexity Low High (Kubernetes) Lowest

Use Cases

  • Microservices applications
  • Batch processing
  • Machine Learning & AI
  • CI/CD pipelines

Capacity Providers and Service Connect

  • Capacity providers split a service across Fargate, Fargate Spot, and EC2 Auto Scaling groups. You set a base of On-Demand and a weight of Spot for cheap burst capacity.
  • awsvpc mode gives each task its own ENI and security group — treat tasks like tiny instances for network policy.
  • Service Connect / Cloud Map provide service discovery and sane DNS names between tasks without standing up a full service mesh on day one.
  • ECS Exec opens a shell into a running task via SSM — no SSH daemon in the image.

☸️ Amazon EKS (Elastic Kubernetes Service)

Amazon EKS is a fully managed Kubernetes service that runs Kubernetes clusters on AWS without you managing the control plane.

Managed Control Plane

AWS manages the Kubernetes API server, etcd database, and controller manager across multiple Availability Zones. EKS automatically detects and replaces unhealthy control plane nodes and supports automated version upgrades.

ECS vs. EKS — When to Choose Which

Choose ECS for AWS-native simplicity, lower operational overhead, and tight integration with the AWS ecosystem. Choose EKS when you need the standard Kubernetes API, want portability across clouds, or are migrating existing Kubernetes workloads from on-premises.

Key Features

  • Fully Managed Control Plane: AWS manages Kubernetes master nodes
  • High Availability: Control plane across multiple AZs
  • AWS Integration: IAM, VPC, ELB, CloudWatch
  • Auto-Scaling: EC2 Auto Scaling and Kubernetes Cluster Autoscaler
  • Fargate Support: Run pods without managing EC2 instances

How EKS Works

  1. Kubernetes Control Plane: EKS manages API server, etcd, controller manager
  2. Worker Nodes: EC2 instances running your Kubernetes applications
  3. Pods and Services: Deploy using kubectl, Helm charts
  4. Networking: AWS VPC networking for pod IP addresses

Use Cases

  • Microservices architectures
  • CI/CD pipelines
  • Hybrid cloud environments
  • Data processing

Cost Considerations

  • EKS Control Plane: $0.10 per hour per cluster (~$73/month)
  • EC2 / Fargate: Charged for worker nodes or Fargate tasks
  • EBS Volumes: Storage for persistent volumes
  • Data Transfer: Between regions and Availability Zones

EKS Add-ons & Tooling

  • AWS Load Balancer Controller: Provision ALBs/NLBs via Kubernetes Ingress and Service resources
  • Cluster Autoscaler: Automatically adjust node group size based on pod demand
  • Karpenter: Faster, more flexible node provisioning than classic node groups — launches the cheapest fitting instance type in seconds when pods are pending
  • EKS Pod Identity / IRSA: Map a Kubernetes service account to an IAM role so pods never store long-lived keys
  • EKS Anywhere: Run EKS-compatible clusters on your own infrastructure
  • EKS Distro: Open-source Kubernetes distribution for on-premises use

🚀 AWS Fargate - Serverless Containers

AWS Fargate is a serverless compute engine for containers that works with both ECS and EKS — no EC2 instances to provision or manage.

Isolation: Firecracker MicroVMs

Each Fargate task (or EKS pod) runs in its own Firecracker MicroVM, providing hardware-level isolation rather than shared-kernel container isolation. This is critical for multi-tenant security in regulated environments.

Fargate vs. EC2 Launch Type

Fargate: Best for variable/bursty workloads, teams without platform engineers, and when operational simplicity outweighs cost optimization.
EC2 Launch Type: Best for steady-state, high-throughput workloads where you can optimize costs with Reserved Instances, Spot, or larger shared host utilization.

Key Concepts

  • Serverless: No need to manage VMs or EC2 instances
  • Integration: Works with both ECS and EKS
  • No Infrastructure Management: AWS provisions and scales automatically
  • Cost Efficiency: Pay only for CPU and memory used
  • Security: Isolated environment for each task/pod

Benefits

  • Simplified operations - focus on applications
  • Automatic scaling
  • Pay-per-use pricing
  • No server management
  • Improved security with isolation
  • Faster time to market

Use Cases

  • Microservices architecture
  • Batch jobs
  • Web applications
  • CI/CD pipelines
  • Event-driven applications

Fargate Spot and Sizing

  • Fargate Spot discounts interruptible tasks. Use it for workers and batch, not for the only replica of a checkout API.
  • You pick vCPU and memory pairs (they are not infinitely free-form). Oversizing memory is a silent cost leak — watch CloudWatch MemoryUtilization.
  • Ephemeral storage defaults are small; raise them for image-heavy or unpack-heavy tasks, or mount EFS for shared files.

📦 AWS Batch

AWS Batch is a fully managed service for running batch computing workloads at any scale — from tens to hundreds of thousands of concurrent jobs.

How AWS Batch Works

  1. Submit Jobs to a job queue with priority levels
  2. Job Scheduler evaluates queue and provisions compute from the compute environment
  3. Compute Environment scales EC2 or Fargate resources up/down automatically
  4. Jobs Execute using the container image and resources defined in the job definition

Key Features

  • Fully Managed: AWS handles compute resources and job execution
  • Job Queues: Submit jobs with different priorities
  • Compute Environments: Managed or unmanaged EC2/Fargate resources
  • Job Definitions: Blueprint for jobs (CPU, memory, Docker images)
  • Scalability: Automatically scales resources up/down
  • Container Support: Run jobs in Docker containers
  • Cost Efficiency: Use Spot Instances for savings

Use Cases

  • Data processing and ETL
  • Scientific simulations
  • Financial modeling
  • Image/video rendering
  • Machine learning training

🌱 AWS Elastic Beanstalk

Elastic Beanstalk is a Platform as a Service (PaaS) that makes it easy to deploy and manage applications without worrying about the underlying infrastructure. Upload your code and Beanstalk handles provisioning, load balancing, auto scaling, and health monitoring.

Supported Platforms

  • Java (Tomcat, Corretto)
  • .NET (IIS, Core)
  • Node.js, Python, Ruby, PHP, Go
  • Docker (single or multi-container)

How It Works

  1. Create an application and upload code (zip, WAR, or connect to CodePipeline)
  2. Choose a platform and environment tier (Web Server or Worker)
  3. Beanstalk provisions EC2, ELB, Auto Scaling, and security groups automatically
  4. Deploy new versions with rolling, immutable, or blue/green deployment policies

🏃 AWS App Runner

AWS App Runner is a fully managed container application service that builds and runs containerized web applications and APIs with automatic scaling — no infrastructure knowledge required.

Key Features

  • Source-based deployment: Connect directly to GitHub or ECR — App Runner builds and deploys automatically
  • Automatic scaling: Scales based on concurrent requests or active instances
  • Built-in load balancing: HTTPS endpoint provided out of the box
  • VPC connectivity: Access private resources (RDS, ElastiCache) via VPC connector
  • CI/CD integration: Automatic deployments on every code push

📋 Launch Templates

A launch template is the versioned blueprint for an EC2 instance — AMI, instance type, key pair, security groups, IAM instance profile, user data, EBS mappings, metadata options, and more. Auto Scaling Groups and EC2 Fleet consume templates. Launch configurations are legacy; do not create new ones.

Why templates beat one-off “Launch Instance” clicks

  • Versions: Ship AMI v14 as template version 14, roll back by pointing the ASG at version 13.
  • Overrides: The ASG mixed-instances policy can override instance type per pool while keeping the same AMI and user data.
  • IMDSv2 required: Set HttpTokens = required so SSRF bugs cannot steal instance-role credentials with a simple GET to 169.254.169.254.
# Require IMDSv2 and attach an instance profile aws ec2 create-launch-template \ --launch-template-name web-lt \ --version-description "al2023-hardened" \ --launch-template-data '{ "ImageId":"ami-0abc...", "InstanceType":"t3.small", "IamInstanceProfile":{"Name":"web-role"}, "MetadataOptions":{"HttpTokens":"required","HttpPutResponseHopLimit":1} }'

🔐 Systems Manager Session Manager

Prefer Session Manager over opening SSH (port 22) or RDP (3389) to the internet. The SSM Agent on the instance opens an outbound channel to AWS. Operators start a shell from the console or CLI. Audit logs go to CloudTrail and optionally CloudWatch / S3.

  • No inbound bastion if every instance has the SSM agent, an instance profile with AmazonSSMManagedInstanceCore, and a path to SSM endpoints (NAT or VPC interface endpoints).
  • Run Command patches or runs a document across a tagged fleet without logging in.
  • Patch Manager and State Manager keep agents and packages at a desired state — closer to cattle than pets.
Key pairs are not a security strategy. They leak, they do not expire cleanly, and they do not map to IAM users. Use SSM + IAM for humans; use instance/task roles for software.

🦾 Graviton, x86, and Accelerators

Instance family letters hide the CPU vendor. The suffix after the generation tells you the silicon: g = AWS Graviton (Arm), i = Intel, a = AMD. Graviton is often the first lever after “turn it off at night.”

ChoiceWhen it winsWatch-outs
Graviton (t4g, m7g, c7g, r7g…) Linux web, containers, Redis, Java 17+, Node, Python, Go — typically better price-performance Must ship Arm images/AMIs; some native binaries and old JDKs fail
Intel / AMD x86 Closed-source x86-only software, Windows, some vendor agents Higher $ for the same vCPU on many families
GPU (p / g / Inf) Training, inference, video, spatial Capacity is scarce — consider Capacity Blocks or Savings Plans
Trainium / Inferentia AWS-native ML chips via Neuron SDK Framework and model support is narrower than CUDA
Practical path: Build multi-arch container images (linux/amd64 + linux/arm64). Run Graviton in staging for a week. Flip production if p99 and error rates match.

🛠️ Operations, Rightsizing, and Cost

Weekend production story

The $4,000 idle fleet

A team left 12 m5.2xlarge instances running after a load test, plus three unused Elastic IPs and 4 TB of unattached gp3 volumes. Compute was “stopped” in their minds because traffic was zero. Billing still saw running instances, allocated EIPs, and provisioned EBS.

Fix: tag every resource with Owner and Expiry, attach the ASG (min 0) to a schedule for non-prod, and alarm on CPUUtilization < 5% for 3 days plus unattached volume age.

Tools that pay for themselves

  • Compute Optimizer: Recommends downsizing, Graviton, and idle EBS using CloudWatch history.
  • Cost Explorer + Savings Plans: Commit to $/hour of compute, not a specific instance family, when usage is steady.
  • Instance Scheduler / EventBridge + Lambda: Stop dev/test outside business hours.
  • Capacity Reservations / Capacity Blocks: Guarantee (and pay for) scarce GPU or AZ capacity when On-Demand might be short.

Operational checklist

  • IMDSv2 required on every launch template
  • No 0.0.0.0/0 on SSH; SSM only
  • ASG min ≥ 2 across two AZs for user-facing apps
  • ALB health check proves the app, not just the port
  • Lambda aliases for production; dead-letter or destinations configured
  • Container images scanned; task/function roles least-privilege
  • Auto Scaling mixed instances + Spot only where interruption is safe

🎯 Compute Service Selection Guide

Choosing the right compute service depends on your workload characteristics, team expertise, and operational requirements.

Decision Framework

RequirementRecommended Service
Run code for < 15 min, event-driven, no servers Lambda
Full OS control, custom software, GPU/bare metal EC2
Docker containers, AWS-native, simple ops ECS + Fargate
Kubernetes, multi-cloud portability EKS
Batch jobs, ETL, scientific computing AWS Batch
Simple VPS, fixed pricing, beginner-friendly Lightsail
Quick web app deploy (Java, Node, Python) Elastic Beanstalk
Containerized web app, minimal config App Runner

Cost Optimization Strategies

  • 💰 Use Spot Instances for fault-tolerant and batch workloads (up to 90% savings)
  • 📅 Purchase Reserved Instances or Savings Plans for steady production workloads
  • 📊 Right-size instances using CloudWatch metrics and AWS Compute Optimizer
  • ⏰ Schedule dev/test environments to stop outside business hours
  • 🔄 Use Graviton (ARM) instances for up to 40% better price-performance
  • 📦 Prefer serverless (Lambda, Fargate) for variable traffic to avoid paying for idle capacity

Prefer serverless when

  • Traffic is spiky or idle most of the day
  • Work is event-shaped (upload, queue, cron, webhook)
  • The team is small and does not want AMIs

Stay on EC2 / ECS-EC2 when

  • You need GPU, FPGA, or a custom kernel module
  • Processes must listen for hours with warm memory
  • Utilization is high enough that reserved hosts are cheaper

Exam & Interview Quick Reference

  • Stateful firewall: Security Groups (EC2)
  • Stateless firewall: Network ACLs (subnet level)
  • Persistent block storage: EBS
  • Ephemeral high-IOPS storage: Instance Store

  • Auto-healing web tier: ALB + Auto Scaling Group
  • Serverless containers: Fargate
  • 15-minute execution limit: Lambda

  • SSRF-safe metadata: IMDSv2 required
  • Arm price-performance: Graviton (family suffix g)
  • K8s node burst: Karpenter (not just Cluster Autoscaler)
