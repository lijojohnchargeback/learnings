AWS Complete Overview

Amazon Web Services - Cloud Computing Platform

1) Introduction to AWS

Amazon Web Services (AWS) is a collection of on-demand building blocks. Instead of buying racks, power, and cooling, you request a virtual machine, an object store, a database, or a machine-learning API and pay for what you use. The platform started with storage and compute in 2006 and now covers more than 200 services used by startups, governments, and enterprises such as Netflix, NASA, and Adobe.

One typical web app, named as real services. IAM decides who can call each hop. The VPC keeps compute and data off the public internet.

Walk the request, hop by hop

The diagram above is the mental model for the rest of this page. A user never “talks to AWS.” They talk to a name, then to an edge, then to a balancer, then to code, then to data.

  1. Users — a browser, a mobile app, or an API client issues HTTPS to a hostname such as app.example.com.
  2. Route 53 — DNS. It answers with CloudFront or a load-balancer address. Health checks can fail over to another region if you design for it.
  3. CloudFront — a CDN. Static assets (JS, images, video) should be answered at an edge location. Dynamic API calls can still pass through so the client lands on the AWS backbone sooner.
  4. ALB — Application Load Balancer. It terminates TLS, checks paths and host headers, and spreads traffic across healthy targets in more than one Availability Zone.
  5. Compute — the code. That might be EC2 virtual machines, ECS Fargate containers, or Lambda functions. Same job, different ops burden.
  6. Data — S3 for objects, RDS/Aurora for relational rows, DynamoDB for key-value items. Pick by access pattern, not by habit.

Two invisible layers wrap every hop: IAM (who is allowed to call the service) and a VPC (which packets can reach the private subnets). If those two are wrong, the pretty architecture still leaks or locks you out.

Shared responsibility — what you still own

AWS secures the cloud: data centers, hardware, hypervisor, and the managed service itself. You secure in the cloud. The line moves with the service model.

  • IaaS (EC2, VPC, EBS): you patch the OS, configure the firewall, encrypt volumes, and rotate keys. AWS keeps the building and the hypervisor healthy.
  • PaaS (RDS, Elastic Beanstalk, ECS Fargate): AWS patches the engine or the nodes. You still design schemas, IAM roles, backups, and network placement.
  • SaaS / serverless (Lambda, S3, DynamoDB): you do not SSH anywhere. You still own identity, encryption settings, bucket policies, and the data you store.
💡 The exam and production both fail here: “AWS is secure” is not a control. MFA on root, no public S3, security groups that are not 0.0.0.0/0 on SSH, and encryption you turned on — those are controls.

How to think about AWS

A toolkit, not a single product

Every AWS service solves one job: run code, store files, move packets, encrypt secrets, or train models. You compose those jobs into an architecture. A typical web app uses Route 53 (DNS), CloudFront (CDN), S3 (static files), EC2 or Lambda (compute), RDS or DynamoDB (data), and IAM (who can do what).

The rest of this page is organized the same way architects think: infrastructure first, then identity, then compute/storage/data, then security, networking, delivery, and operations.

Choose AWS when you need

  • Global reach with low latency near customers
  • Elastic capacity for traffic spikes
  • Managed databases, queues, and AI APIs
  • Enterprise compliance (HIPAA, PCI, FedRAMP, GDPR)

Think twice when

  • A single small VPS would be simpler and cheaper
  • You cannot invest in IAM, billing, and tagging hygiene
  • Data residency rules force a cloud you do not have
  • The team has no operations capacity yet

2) AWS Global Infrastructure

A Region is a geography. An AZ is a failure domain. Edge locations cache content — they are not where you put the database.

AWS is not one giant computer in one building. It is a hierarchy: Regions (geographic areas), Availability Zones (isolated campuses inside a region), data centers (the physical rooms of racks), and edge locations (hundreds of points of presence that cache content). High availability is a placement decision: if one AZ loses power, another AZ in the same region keeps serving traffic.

How to place a workload

Read the stack from the top of the diagram down. Each layer answers a different question.

  • Region — Where may the data live? GDPR, latency to users, price, and whether the service you need even exists there. us-east-1 has the newest services first; it is also a busy, expensive default. Do not pick it only because tutorials do.
  • Availability Zones — Can one campus fail without taking the app down? A Multi-AZ RDS standby, an Auto Scaling group across subnet-a and subnet-b, and an ALB with targets in two AZs are the same idea: two buildings, one region.
  • Data centers — You never choose a building. AWS maps an AZ to more than one facility so a cooling failure is not automatically an AZ failure. You still design as if the whole AZ can disappear.
  • Edge locations — CloudFront, Route 53, and AWS WAF sit here. They shrink latency for readers. They do not replace Multi-AZ for writes. A cached page can survive an origin blip; a checkout API cannot live only at the edge.
📌 Latency vs residency: Putting the API in Ireland for Berlin users is a latency choice. Keeping personal data out of us-east-1 is a legal choice. They are not the same decision, and one diagram must show both.

3) IAM - Identity and Access Management

Authentication proves identity. Authorization evaluates the policy. Least privilege means the policy names the action and the resource — not *.

Identity and Access Management is the control plane for every other AWS service. It is global (not tied to one region). You never share the root account for daily work. Humans get IAM users or, better, federated identities. Applications get roles with temporary credentials. Permissions live in JSON policies attached to users, groups, or roles. The golden rule is least privilege: start with deny-all and open only the actions a job actually needs.

Read the IAM diagram as a pipeline

Every AWS API call is a request that must survive two gates. Mix them up and you will debug “AccessDenied” for hours.

  1. Who is calling? A human signs in with a password plus MFA, or SSO (IAM Identity Center). An app does not store access keys in code — an EC2 instance profile or a Lambda execution role hands it temporary credentials from STS.
  2. What does the policy say? A statement is four ideas: Effect (Allow or Deny), Action (the API, like s3:GetObject), Resource (an ARN), and optional Condition (MFA, source VPC, encryption).
  3. Is this action allowed on this resource? Explicit Deny wins. Then AWS unions identity policies, resource policies (bucket policy, key policy), SCPs in Organizations, and permission boundaries. Missing Allow is a deny.

Roles vs users: users are long-lived people. Roles are assumed. Prefer roles for anything that runs on AWS — EC2 reading S3, Lambda writing DynamoDB, one account deploying into another. Long-lived access keys are the most common breach path in student and startup accounts.

💡 Debug AccessDenied in this order: wrong principal, wrong action name, wrong ARN (object vs bucket), missing KMS kms:Decrypt, then an SCP or permission boundary you forgot existed.

What is IAM?

IAM is essential for securing access to AWS resources. It's a global service that controls who can access what.

IAM Components

1. Root Account

  • Created by default when signing up
  • Has full access to all resources
  • ⚠️ Only use for initial setup, not daily operations
  • Secure with strong password and MFA

2. Users

  • Individual entities (human or service)
  • Each user has unique credentials
  • Can belong to multiple groups
  • Permissions defined by policies

3. Groups

  • Collections of users (e.g., Developers, Operations)
  • Users inherit group permissions
  • Easier to manage than individual user permissions
  • Example: Developers group (Alice, Charles, Lijo)

4. Policies

  • JSON documents defining permissions
  • Specify allowed/denied actions on resources
  • Follow principle of least privilege
  • Can be attached to users, groups, or roles

5. Roles

  • For AWS services, not users
  • Temporary credentials for services
  • Example: EC2 instance accessing S3
  • No long-term credentials needed

IAM Policy Example

{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "ListAllBuckets",
            "Effect": "Allow",

Policy Elements:

  • Version - Policy language version

  • Sid - Statement ID (optional)

Advanced IAM Concepts

1. IAM Roles for AWS Services

  • EC2 Instance Roles: Allow EC2 instances to access other AWS services

2. Cross-Account Access

Allow users from one AWS account to access resources in another account:

  • Create a role in the target account
  • Define trust policy allowing the source account
  • Grant permissions in the role
  • Users from source account assume the role

3. Identity Federation

  • SAML 2.0 Federation: Enterprise SSO (Active Directory, ADFS)
  • Web Identity Federation: Login with Amazon, Google, Facebook
  • AWS SSO: Centralized single sign-on service
  • Amazon Cognito: User pools for mobile/web apps

4. Temporary Security Credentials

  • Generated by AWS Security Token Service (STS)
  • Short-lived credentials (15 mins to 12 hours)
  • Used with roles and federation
  • More secure than long-term access keys

5. IAM Policy Evaluation Logic

1. By default, all requests are implicitly denied
2. Explicit allow overrides implicit deny
3. Explicit deny overrides any allow
4. Policies are evaluated: Identity-based → Resource-based → Permissions boundaries → SCPs

4) Compute Services

Left = you patch servers. Right = you ship code and accept limits (timeouts, package size, statelessness).

Compute is “where your code runs.” AWS does not have one compute product — it has a ladder of control versus convenience. EC2 is a virtual server you patch and size yourself. Lightsail wraps a VPS with simple pricing. ECS/EKS + Fargate run containers so you ship images instead of AMIs. Lambda runs a function for milliseconds and bills per request. Elastic Beanstalk and App Runner sit in the middle: you bring code, AWS runs the fleet.

How to choose a compute service

Start from the workload, not from the logo you learned first.

  • Lightsail — a blog, a student project, or a single WordPress box with a predictable monthly price. You outgrow it when you need VPCs, IAM roles, and Auto Scaling groups as first-class tools.
  • EC2 — you need a specific OS, GPU, Windows, a long-lived process, or a lift-and-shift VM. You own patching, SSH, disks, and capacity. Pair it with an Auto Scaling group and an ALB or you have a pet, not cattle.
  • ECS / EKS — the app is already a Docker image. ECS is the AWS-native orchestrator. EKS is managed Kubernetes when you need portable YAML or a large existing k8s investment. Both can run on EC2 (you manage nodes) or Fargate (you do not).
  • Fargate — same container, no instance to patch. You pay for vCPU and memory while the task runs. Good default for APIs and workers that already fit a container.
  • Lambda — short, event-driven work: HTTP via API Gateway, S3 object created, SQS message, cron via EventBridge. Max 15 minutes, no inbound SSH, state in the database. Cold starts and package size are the real constraints.
📌 A common production split: the public API on ECS Fargate or Lambda, nightly batch on AWS Batch or Fargate, and a small EC2 fleet only for software that cannot be containerized yet.

Architecture pattern

Three-tier app on compute

Put an Application Load Balancer in public subnets. Run the web/API on an Auto Scaling group of EC2 (or ECS Fargate) in private subnets. Keep RDS in a separate private subnet. Scale on CPU or request count. Use a launch template + AMI so new instances are identical. This is the default “I need a server” design before you go serverless.

5) Storage Services

S3 is not a boot disk. EBS is not a CDN. EFS is not a SQL engine. Match the API to the access pattern.

Storage on AWS is not “a hard drive in the cloud.” S3 is object storage: you PUT a file and get a URL or API handle — it scales without you provisioning disks and is designed for 11 nines of durability. EBS is a network disk that lives in one AZ and attaches to one EC2 instance (io2 Block Express and Multi-Attach are exceptions). EFS is NFS that many Linux instances can mount at once. FSx covers Windows (SMB), Lustre (HPC), and NetApp. Archives drop to Glacier classes when you can wait minutes or hours to restore.

What “access pattern” actually means

The diagram is a decision tree. Ask how the bytes are opened, not what marketing name sounds like “storage.”

  • S3 (object) — you address a whole object by key. Great for images, backups, data-lake files, static websites, and Lambda triggers. There is no POSIX open() or file lock. Change one byte and you rewrite the object (or use multipart / S3 Express for special cases).
  • EBS (block) — the OS sees a disk. This is the root volume and the volume under MySQL/Postgres on EC2. It lives in one AZ. Snapshot to S3 for backup; that snapshot is not a running disk. If you terminate the instance without keeping the volume, the data can die with it.
  • EFS (file) — many Linux instances mount the same directory over NFS. Use it for shared uploads, home directories, and lift-and-shift apps that insist on a network file system. Do not put a high-write relational database on EFS and expect RDS performance.

Durability vs availability: S3 Standard is designed for 11 nines of durability (you almost never lose the object). Availability is whether you can read it right now (S3 Standard SLA is 99.99%). Cross-Region Replication and CloudFront protect against a regional event and distant users. They do not turn S3 into a POSIX disk.

Use S3 for

  • Backups, data lakes, media, static websites
  • Logs and machine-learning training sets
  • Anything that is a file/object, not a boot disk

Do not use S3 for

  • The operating system volume of a server (use EBS)
  • A shared Linux home directory with file locks (use EFS)
  • A SQL database file that needs fsync semantics
Durability vs availability

11 nines is not the same as 100% uptime

S3 Standard is designed to not lose objects even if multiple facilities fail. That is durability. Availability is whether you can read the object right now (S3 Standard SLA is 99.99%). Cross-Region Replication and CloudFront protect against regional events and improve download speed for users far from the bucket region.

6) Database Services

Cache first for speed. SQL for relations and transactions. DynamoDB for huge item scale. Redshift for analytics questions — not checkout.

The most expensive architecture mistake is forcing every workload into one database. RDS/Aurora give you PostgreSQL or MySQL with backups, Multi-AZ failover, and read replicas. DynamoDB is a serverless NoSQL store with single-digit millisecond reads at any scale — if you design the partition key correctly. ElastiCache (Redis/Memcached) sits in front of a database to absorb hot keys. Redshift is for analytics, not OLTP. Graph, time-series, ledger, and document engines exist so you do not fake those models in SQL.

Four stores, four questions

Walk the 2×2 in the diagram. Each box is good at one question and expensive at the others.

  • RDS / Aurora — “How do these rows relate?” Orders have line items, users have addresses, money moves in a transaction. You need joins, foreign keys, and BEGIN/COMMIT. Aurora keeps a clustered storage layer and can fail over faster than classic Multi-AZ RDS; the model is still SQL.
  • DynamoDB — “Give me this item fast at any scale.” You already know the primary key (user id + cart, device id + timestamp). There is no ad-hoc join. Get the partition key wrong and you create a hot partition. Get it right and the table grows without you running a server.
  • ElastiCache — “I already computed this.” Session blobs, product pages, leaderboards. A cache miss falls through to RDS or DynamoDB. A cache is not the source of truth unless you designed it that way and accepted loss on restart.
  • Redshift — “What happened last quarter?” Columnar warehouse for scans and aggregations. Loading checkout traffic here will be slow and costly. Stream events out (Kinesis, Firehose) and query them later.
💡 If you are unsure: start with Aurora PostgreSQL plus ElastiCache for the hot path. Add DynamoDB when a single access pattern is spiky and key-based. Add Redshift when analysts keep locking the OLTP database with GROUP BY.

8) Networking & Content Delivery

Internet hits the IGW, then a public ALB. App and data stay in private subnets. Outbound updates go through NAT. Security groups are stateful; NACLs are not.

Amazon VPC is a software-defined network that feels like a traditional data center LAN. You pick a CIDR (for example 10.0.0.0/16), split it into public and private subnets across AZs, attach an Internet Gateway for public traffic, and use a NAT Gateway so private instances can call the internet without being reachable from it. Security groups are stateful instance firewalls. Network ACLs are stateless subnet firewalls. CloudFront and Global Accelerator sit in front of the VPC to pull users onto the AWS backbone sooner.

Follow a packet through the VPC

The diagram is a floor plan. Public does not mean “unsafe.” It means “has a route to the Internet Gateway.” Private means “no public IP, no direct inbound from the internet.”

  1. A client resolves the hostname and reaches the ALB in a public subnet. The ALB has a public IP (or is fronted by CloudFront). Its security group allows 443 from the world, or from CloudFront prefixes only.
  2. The ALB forwards to app tasks in a private subnet. Those instances have no public IP. Their security group allows 8080 (or whatever the target port is) only from the ALB security group — not from 0.0.0.0/0.
  3. The app opens PostgreSQL on RDS in a data subnet. RDS allows 5432 only from the app security group. There is no path from the internet to the database.
  4. When the app needs to call the public internet (OS patches, a third-party API), the route table sends 0.0.0.0/0 to a NAT Gateway in the public subnet. NAT is outbound only. That is why a bastion or SSM Session Manager exists for humans — you do not open SSH to the world.

Two firewalls: security groups remember connections (stateful). If you allow inbound 443, the reply is allowed automatically. Network ACLs are stateless — you must allow the ephemeral return ports yourself. Most teams live on security groups and keep NACLs as a coarse subnet guardrail.

Amazon VPC Components

VPC (Virtual Private Cloud) lets you provision a logically isolated section of the AWS cloud.

Core Components:

  • CIDR Block: IP address range (e.g., 10.0.0.0/16)
  • Subnets: Divide VPC into public and private subnets
  • Internet Gateway (IGW): Connect VPC to internet
  • NAT Gateway/Instance: Enable private subnets to access internet
  • Route Tables: Control traffic routing
  • Security Groups: Stateful firewall (instance level)
  • Network ACLs: Stateless firewall (subnet level)

11) Serverless Architecture

You ship functions and events. AWS runs the servers. State lives in the database — not in the function. Scale to zero when nobody calls.

A serverless design is event-driven and pay-per-use. API Gateway or Function URLs receive HTTP. Lambda runs your handler. DynamoDB or S3 holds state. SQS buffers work so spikes do not melt the function concurrency limit. Step Functions orchestrate multi-step workflows when a single Lambda would be too long or too brittle. You trade control (no SSH, 15-minute max duration on Lambda) for operations that scale to zero.

What each box in the serverless path does

Read left to right, then down. HTTP is only one trigger. The same Lambda can be reused from a queue.

  • API Gateway — the front door. It authenticates (IAM, JWT, API key), throttles noisy clients, maps paths to functions, and can validate the body before Lambda ever starts. You pay per million requests. Use HTTP APIs for simple routes; REST APIs when you need API keys, usage plans, or request validators.
  • Lambda — a stateless handler. Memory (128 MB–10 GB) also scales CPU. Timeout is 15 minutes, not “run forever.” /tmp is ephemeral. Cold starts happen when a new execution environment boots — keep packages small, avoid VPC unless you need it, and use provisioned concurrency for the p99 path that users feel.
  • DynamoDB / S3 — durable state. Put the user record or job result here. Do not store session-critical data only in the Lambda process; the next invoke may be a different environment.
  • SQS / EventBridge — the shock absorber. API Gateway can drop a message on SQS and return 202. Workers drain the queue at a rate you control. EventBridge fans one event (order placed) to email, analytics, and fulfillment without those services calling each other.
📌 When not to go serverless: a 2-hour video encode, a WebSocket-heavy game loop you already run well on ECS, or a license that requires a sticky VM. Serverless is a constraint set, not a moral upgrade.

SQS Advanced Features

1. Visibility Timeout

  • After message is polled, it becomes invisible
  • Default: 30 seconds (0 sec to 12 hours)
  • Consumer must delete or message reappears
  • Can change timeout using ChangeMessageVisibility API
  • Too short = duplicate processing, too long = delayed retries

2. Long Polling

  • Wait for messages to arrive (1-20 seconds)
  • Reduces API calls and cost
  • Preferred over short polling
  • Enable: Set ReceiveMessageWaitTimeSeconds > 0

3. Dead Letter Queue (DLQ)

  • Handle messages that fail processing
  • Set MaximumReceives threshold
  • Failed messages move to DLQ
  • Investigate and process separately
  • Good for debugging

4. Delay Queues

  • Delay message delivery (0 to 15 minutes)
  • Default: 0 seconds
  • Per-queue or per-message delay
  • Use case: Process after specific time

5. Message Deduplication (FIFO)

  • Prevent duplicate messages in 5-minute window
  • Content-based deduplication (SHA-256 hash)
  • Or provide MessageDeduplicationId

6. Message Groups (FIFO)

  • Parallel processing with ordering per group
  • Specify MessageGroupId
  • Messages in same group processed in order
  • Different groups processed in parallel

            userId: principalId,
            role: 'admin'
        }

}

16) AWS Well-Architected Framework

The Well-Architected Framework is a review method, not a product you install. You score a workload against questions in each pillar, then fix the high-risk items. Reliability asks whether you deploy across AZs. Security asks whether data is encrypted and access is least privilege. Cost asks whether you know unit economics. Sustainability asks whether you right-size and pick efficient regions. Use the Well-Architected Tool in the console to store the review and track improvement over time.

The AWS Well-Architected Framework helps you understand the pros and cons of decisions you make while building systems on AWS. It consists of six pillars:

  • Design Principles:

  • Keep people away from data
  • Prepare for security events

Key Services:

  • IAM, GuardDuty, Security Hub
  • KMS, CloudTrail, Config
  • WAF, Shield, Macie

3. Reliability

Ensure workload performs its intended function correctly

  • Design Principles:
  • Automatically recover from failure
  • Test recovery procedures
  • Scale horizontally for availability
  • Stop guessing capacity
  • Manage change through automation

Key Services:

Use computing resources efficiently

Avoid unnecessary costs

  • Stop spending on undifferentiated heavy lifting
  • Analyze and attribute expenditure

Key Services:

  • Reserved Instances, Savings Plans

Minimize environmental impact

  • Design Principles:

  • Reduce downstream impact

18) AWS Pricing Model

How the bill is built

You pay for units, not “the cloud”

EC2 bills vCPU-hours (and a stopped instance still costs for EBS). Lambda bills GB-seconds plus requests. S3 bills storage GB-month, requests, and data transfer out. Data transfer between AZs and out to the internet is often the line item people forget. The Pricing Calculator and Cost Explorer exist so you estimate before you scale.

Pay-As-You-Go Pricing

Pay only for what you use, with no upfront costs or long-term commitments.

Pricing Models:

On-Demand

  • Pay by the hour/second
  • No commitment
  • Most flexible
  • Highest cost per hour

Reserved Instances

  • 1 or 3-year commitment
  • Up to 75% discount
  • Predictable workloads

Spot Instances

  • Up to 90% discount
  • Can be interrupted
  • Flexible workloads

Savings Plans

  • 1 or 3-year commitment
  • Flexible compute usage
  • Up to 72% savings
💡 Free Tier: AWS offers a Free Tier with limited usage of many services for 12 months, plus some always-free services.
