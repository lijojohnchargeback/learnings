⚙️ Backend Systems

Complete Guide to Server-Side Architecture, APIs, and Patterns

1) Backend Principles

A typical backend sits behind DNS and a load balancer, then talks to databases, caches, and async workers.

The backend is the server-side of an application: it receives requests, enforces security, runs business rules, reads and writes data, and returns responses. Frontends render UI; backends own truth, secrets, and durability.

What a backend actually does

  • Accept traffic – HTTP/HTTPS (and sometimes WebSocket, gRPC, or queues)
  • Protect the system – auth, authorization, rate limits, input validation
  • Apply business logic – rules that must be consistent for every client
  • Persist and retrieve data – databases, caches, object storage
  • Coordinate side effects – emails, webhooks, search indexing, reports

A well-designed backend system should embody these ten core qualities:

1. Reliable

  • Error handling and recovery
  • Data integrity
  • Redundancy and failover mechanisms

2. Scalable

  • Horizontal scaling
  • Load balancing
  • Caching strategies

3. Maintainable

  • Clean and modular code
  • Consistent coding standards
  • Comprehensive documentation

4. Secure

  • Authentication and authorization
  • Data encryption
  • Regular security audits

5. Efficient

  • Optimized algorithms
  • Resource management
  • Performance monitoring

6. Testable

  • Unit and integration tests
  • Automated testing frameworks
  • CI/CD pipelines

7. Extensible

  • Modular architecture
  • Plugin systems
  • Clear APIs for future enhancements

8. Monitorable

  • Logging and alerting
  • Performance metrics
  • Health checks

9. Documented

  • API documentation
  • System architecture diagrams
  • User guides and tutorials

10. Compliant

  • Adherence to industry standards
  • Data privacy regulations
  • Regular compliance audits

2) HTTP Protocol

Every API call is an HTTP message pair: a request (method, URL, headers, body) and a response (status, headers, body).

HTTP uses port 80 (HTTP) and 443 (HTTPS). It can send HTML, JSON, files, static assets, or video. Most modern APIs speak JSON over HTTPS.

Anatomy of a Request

PartExamplePurpose
MethodGET, POSTIntent of the operation
URL / path/api/users/42Which resource
HeadersAuthorization, Content-TypeMetadata (auth, format, cache)
Query?page=2&limit=20Filters, pagination, search
BodyJSON payloadData for create/update (usually)

Request Flow

Client → DNS Server → Load Balancer → Firewall → Server

DNS turns a hostname into an IP. A load balancer spreads traffic across instances. Firewalls and reverse proxies (Nginx, ALB) terminate TLS, enforce rate limits, and forward clean requests to app servers.

Proxy Types

TypeDescription
Reverse ProxyClient redirects to an IP that indirectly connects to another server (e.g., Nginx)
Forward ProxyClient request is sent to a filter before reaching the internet

Why Use a Backend Instead of Frontend?

  • Security – Hide credentials and business logic
  • CORS – Cross-origin restrictions
  • Database – Direct DB access from browser is unsafe
  • Computing Power – Heavy processing on the server

Idempotent vs Non-Idempotent

A request is idempotent if making the same request multiple times has the same effect as making it once. Useful for safe retries on network failures.

CORS: Simple vs Preflight Requests

Simple Request

Sent directly without asking the server first. Meets certain criteria (simple methods, simple headers).

POST /submit HTTP/1.1 Host: example.com Content-Type: application/x-www-form-urlencoded name=John&age=20

Preflight Request

Browser sends an OPTIONS request first when the actual request uses custom headers or non-simple methods.

OPTIONS /submit HTTP/1.1 Host: example.com Access-Control-Request-Method: PUT Access-Control-Request-Headers: X-Custom-Header Origin: http://mywebsite.com

HTTP Caching

HTTP caching stores responses so future requests for the same resource can be served faster.

  • Cache-Control – Controls how, when, and for how long responses can be cached
  • ETag – Helps detect if a cached resource has changed
  • Last-Modified – Timestamp-based cache validation

Content Negotiation

The client and server negotiate the best representation of a resource:

HeaderPurposeExample
AcceptMedia typetext/html, application/json
Accept-LanguageLanguageen-US, fr
Accept-EncodingCompressiongzip, br, deflate

Keep-Alive & Persistent Connections

Keep-Alive keeps the TCP connection open after a request/response cycle, allowing multiple requests over the same connection. Introduced in HTTP/1.1 by default.

  • Connection: keep-alive – Keep TCP connection open
  • Keep-Alive: timeout=5 – Close if idle for 5 seconds
  • Keep-Alive: max=100 – Close after 100 requests

Server-Sent Events (SSE)

text/event-stream allows the server to push real-time updates over a single persistent HTTP connection.

HeaderPurpose
Content-Type: text/event-streamResponse is a stream of events
Cache-Control: no-cachePrevents caching the event stream
Connection: keep-aliveKeeps connection open for continuous updates

SSL, TLS & HTTPS

SSL (Secure Sockets Layer) and TLS (Transport Layer Security) encrypt data sent over the internet, ensuring:

  • Confidentiality – Data cannot be read by attackers
  • Integrity – Data cannot be tampered with
  • Authentication – Verifies server (and optionally client) identity
FeatureSSLTLS
Developed1990s1999+ (successor of SSL)
SecurityWeak, outdatedStrong, modern encryption
VersionsSSL 2.0 / 3.0TLS 1.0 → TLS 1.3
PerformanceSlower handshakesFaster and more secure

Note: TLS is the modern version of SSL. SSL is old and insecure; TLS 1.2/1.3 is standard today. TLS uses HTTPS to connect client to server.

TLS handshake (simplified)

  1. Client hello – supported cipher suites and TLS version
  2. Server hello – chosen cipher + certificate chain
  3. Client verifies certificate (CA trust, hostname, expiry)
  4. Key exchange – both sides derive a shared session key
  5. Encrypted application data flows over that session

TLS 1.3 cuts round trips and removes weak algorithms. In production, terminate TLS at a reverse proxy or load balancer and keep private keys off app servers when possible.

3) Routing

Routing determines how an application responds to a client request at a specific URL path and HTTP method.

Routing Flow

  1. URL Matching – Check incoming path and method
  2. Middleware / Preprocessing – Authenticate, validate, log
  3. Call Handler / Controller – Execute the requested task
  4. Return Response – Send data or error to client

Routing Types

TypeDescriptionExampleExpress Example
StaticFixed path/aboutapp.get('/about', handler)
DynamicPath parameters/users/:idapp.get('/users/:id', handler)
QueryQuery parameters/search?q=nodereq.query.q
NestedParent-child structure/users/:id/posts/:postIdrouter.get('/:id/posts/:postId')
RESTfulHTTP methods for resourcesGET/POST/PUT/DELETE /usersStandard CRUD routes
WildcardMatch any pattern*app.get('*', notFound)
VersionedMultiple API versions/v1/users, /v2/usersAvoid breaking clients

Route Versioning

Maintaining multiple API versions so changes don't break existing clients.

  • Backward compatibility – Old clients continue to work
  • New features – Introduce without breaking endpoints
  • Safe deprecation – Gradually retire old APIs

5) Authentication & Authorization

Authentication proves identity. Authorization decides what that identity is allowed to do.

Authentication – "Who are you?"

  • Username & password
  • OTP / MFA
  • Biometric (fingerprint, face ID)
  • OAuth (Google, GitHub login)
  • JWT / Session-based login

Authorization – "What can you do?"

  • Roles (ADMIN, USER)
  • Permissions (READ, WRITE, DELETE)
  • Policy-based access (RBAC, ABAC)
  • Scopes (OAuth scopes)

JWT in practice

A JWT has three Base64url parts: header.payload.signature. The server verifies the signature with a secret or public key, checks exp, then trusts claims like sub (user id) and roles. Prefer short-lived access tokens + refresh tokens; never put secrets or passwords in the payload (it is readable, only integrity-protected).

Authentication Types

TypeStateful/StatelessHow It WorksCommon Use
Session-basedStatefulServer stores session, sends session IDTraditional web apps
JWTStatelessSigned token sent with every requestSPAs, mobile, microservices
OAuth 2.0StatelessDelegated authorization via access tokensSocial login, API access

Auth Flow

User → Login (credentials) → Authentication ("Who are you?") → Success → Token/Session Created (JWT / Session ID) → Access Request (with token) → Authorization ("What can you do?") → Check roles/permissions → Allowed/Denied → Protected Resource

Cryptography Basics

TypeDescriptionExamples
SymmetricSame key for encrypt & decrypt. Fast.AES, DES
AsymmetricPublic key (shareable) + Private key (secret)RSA, ECC

Security Attacks to Avoid

Error Message Attacks

Attackers learn system behavior from different error messages.

❌ "User does not exist" vs "Incorrect password"
✅ Use generic: "Invalid credentials"

Timing Attacks

Attackers infer info from response time differences.

Username not found: 20ms
Password incorrect: 120ms
✅ Use constant-time comparison

7) Request Pipeline & Middleware

Every HTTP request passes through a layered pipeline. Middleware runs at specific stages — global middleware wraps the entire app, while route-specific middleware runs only for matching paths.

Think of middleware as a conveyor belt: each stage can enrich the request, reject it early, or pass it along.

Request Lifecycle Summary

  1. Client Request – Headers, body, query/path params
  2. Deserialization – JSON → native object
  3. Validation – Required fields, types, formats → 400 if fail
  4. Authentication / Authorization – → 401/403 if fail
  5. Logging / Monitoring – Request ID, timestamp, user ID
  6. Transformation – Trim, normalize, map fields
  7. Controller – Route request, call service, handle status codes
  8. Service – Core business logic, DB ops, external APIs
  9. Serialization – Native object → JSON response

Request Context is a container that holds request-specific data and travels through the entire lifecycle—from middleware to controller to service and back.

8) REST API

REST (Representational State Transfer) is an architectural style for designing scalable, stateless web services over HTTP. Introduced by Roy Fielding (2000).

Resources are nouns; HTTP methods are verbs. One resource collection can support the full CRUD set.
Client → HTTP Request (JSON) → API Endpoint → Validation → Auth → Business Logic (Service) → API Response

Resource naming examples

ActionGoodAvoid
List usersGET /usersGET /getUsers
Create userPOST /usersPOST /createUser
User's postsGET /users/42/postsGET /getUserPosts?id=42
FilterGET /users?role=admin&page=1GET /users/filter/admin

REST Methods

MethodActionIdempotent
GETRead resource✅
POSTCreate resource❌
PUTReplace resource✅
PATCHPartial update✅*
DELETERemove resource✅

Pagination, filtering, sorting

  • Offset – ?page=3&limit=20 (simple; slow on huge tables)
  • Cursor – ?cursor=eyJpZCI6MTAwfQ&limit=20 (stable for infinite scroll)
  • Sort – ?sort=-createdAt (prefix - for descending)
  • Sparse fields – ?fields=id,name,email (reduce payload size)

REST Design Best Practices

  • Make it intuitive and consistent
  • Provide sane defaults
  • Avoid abbreviations in URLs
  • Use nouns for resources (/users, not /getUsers)
  • Use HTTP status codes correctly
  • Version breaking changes (/v1, /v2 or header-based)
  • Return predictable error envelopes with a machine-readable code

9) Databases

A database stores data persistently (survives system restarts). Data is stored on HDD/SSD. Cache stores data in RAM for faster access.

SQL shines with structured relations and transactions. NoSQL shines with flexible documents and horizontal scale patterns.

DBMS Responsibilities

  • Data storage management
  • Data retrieval (with indexes)
  • CRUD operations
  • Data security (auth & access control)
  • Data integrity (PK, FK, Unique, Not Null)
  • Concurrency control
  • Transaction management (ACID)
  • Backup and recovery
  • Performance optimization
  • Data abstraction

Types of DBMS

TypeStructureExamples
RelationalTables, structured schemaMySQL, PostgreSQL
Non-relationalFlexible schema, documents/key-valueMongoDB, Redis

ACID in one breath

LetterMeaningWhy it matters
AAtomicityAll-or-nothing commits (no half-written transfers)
CConsistencyConstraints and rules stay true after each transaction
IIsolationConcurrent transactions do not corrupt each other
DDurabilityCommitted data survives crashes

Indexes & N+1

Indexes make lookups fast (B-tree / hash) but slow writes and use disk. Always index foreign keys and common filter columns. Watch for the N+1 query problem: loading a list, then querying related rows one-by-one — fix with joins, INCLUDE, or batch loaders (DataLoader).

10) Caching

Caching reduces processing effort by storing a subset of data in a faster location for easy access. It is temporary storage, typically in RAM.

Requests try fast layers first. A cache HIT returns early; a MISS loads from the database and warms the cache with a TTL.

Three Levels of Caching

1. Network Cache

TypeDescriptionExamples
CDNDistributed servers cache static content closer to usersCloudflare, CloudFront, Akamai
DNS CachingStores resolved IP addresses to avoid repeated lookupsBrowser → OS → ISP → Authoritative DNS

2. Hardware Level (CPU Cache)

LevelSpeedSizeScope
L1FastestSmallestPrivate per core
L2FastMediumUsually private per core
L3SlowerLargestShared across cores

3. Software / Application Level

Stores frequently accessed data in memory to avoid expensive DB queries or API calls.

  • Redis – Persistent, feature-rich in-memory store
  • Memcached – Simple, high-performance cache

Cache strategies

StrategyHow it worksBest for
Cache-asideApp checks cache; on miss, loads DB and fills cacheMost read-heavy APIs
Write-throughWrite to cache and DB togetherStronger read consistency
Write-behindWrite cache first; flush to DB asyncVery high write throughput
TTL + invalidationExpire keys or delete on updateProfiles, product pages, configs

Cache Flow

Request → Check cache (Redis/Memcached) → Cache HIT → return immediately → Cache MISS → fetch from DB → store in cache (with TTL) → return

Gotchas: stampede (many misses at once), stale data after updates, and caching personalized responses. Use locks/singleflight for hot keys, short TTLs for volatile data, and include user/tenant in the cache key when needed.

11) Background Tasks

Any task not part of the request-response cycle.

Producers enqueue work; workers pull jobs asynchronously. Failed jobs retry, then land in a dead-letter queue.

Why Background Tasks?

  • Latency Reduction – Return response immediately
  • Resource Management – Prevent heavy tasks from starving the server
  • Fault Tolerance – Automatic retries and dead-letter queues
  • Decoupling – Separate business logic from side effects

Common Examples

  • Sending transactional emails or SMS
  • Image resizing and video transcoding
  • Generating large CSV/PDF reports
  • Syncing data to search indexes (Elasticsearch)

Task Queue Architecture

Producer (app creates task) → Message Broker (Redis/RabbitMQ/SQS) → Consumer/Worker (pulls & executes) → Completion signal

Task Types

TypeDescriptionExample
One-offProcessed oncePassword reset email
RecurringFixed intervals (cron)Weekly analytics report
ChainedSequential tasksUpload → Transcode → Thumbnail → Notify
BatchGrouped operations100 activity logs in one transaction
PriorityProcessed by importanceSecurity alert before newsletter

Best Practices

  • Idempotency – Process only once even on retry
  • Error Handling & Retries – Exponential backoff (1s, 5s, 30s)
  • Dead-letter Queues – Failed tasks after max retries
  • Visibility Timeouts – Prevent duplicate processing
  • Monitoring – Track queue depth and worker health

BullMQ Example (Node.js + Redis)

// Producer: Adding a task const { Queue, Worker } = require('bullmq'); const emailQueue = new Queue('emails', { connection: { host: 'localhost', port: 6379 } }); async function signupUser(user) { await emailQueue.add('send-welcome', { email: user.email, name: user.name }); return { message: "Account created, email will be sent shortly." }; } // Consumer: Processing in background const worker = new Worker('emails', async (job) => { if (job.name === 'send-welcome') { console.log(`Sending welcome email to ${job.data.email}...`); } }, { connection: { host: 'localhost', port: 6379 } });

12) Elasticsearch

A distributed, RESTful search and analytics engine built on Apache Lucene, designed for horizontal scalability and reliability.

Why Elasticsearch?

  • Speed – Near real-time search and indexing
  • Full-Text Search – Fuzzy matching, stemming, relevance scoring
  • Scalability – Handle petabytes by adding nodes
  • Analytics – Powerful aggregation framework

Inverted Index

A data structure that stores the locations of a specific term in a document collection. Enables fast full-text search.

Example: User searches "iphne" → system returns "iPhone" results using fuzzy matching.

Where it sits in a backend

Write path: App → Primary DB (source of truth) → async indexer → Elasticsearch Read path: Search UI → Elasticsearch query → ranked hits → hydrate details from DB if needed

Keep the primary database as source of truth. Index into Elasticsearch asynchronously (queue/worker) so API writes stay fast and search stays eventually consistent.

14) API Design

An API (Application Programming Interface) is a set of rules that allows software applications to communicate. It acts as a messenger between systems.

API Roles in Architecture

  • Client-Server Communication – Interface between frontend and backend
  • Microservices – Independent services talk to each other
  • External Integrations – Third-party services (Stripe, Google Maps)
  • Abstraction – Hide internal implementation
