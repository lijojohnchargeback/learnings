🔀 Concurrency & Parallelism

Node, Chrome, await, and PM2 are software. Cores and logical processors are hardware. The OS scheduler is the only bridge between them.

1) Software is not the CPU

The easy mistake — and the one this lesson used to make — is treating a Node process, a Chrome tab, or a “worker” as if it were a processor. Those are software. They ask for CPU time. They do not execute machine instructions themselves.

Left column = software. Right column = hardware. The scheduler is the only thing that connects them.

Once that split is clear, sync / async / threads / processes answer two software questions. Hardware answers a third:

1. How does software wait?

Sync vs async. Does this function sit idle, or can other JavaScript run while I/O is outstanding?

2. How is software structured?

Process vs software thread. Isolated program, or another execution path inside the same memory?

3. Where does it actually run?

Hardware. The OS maps software threads onto 20 logical processors and 14 physical cores. That is the only place work executes.

Waiting and structuring work are software decisions. They still have to pass the OS scheduler to reach a core.

The rule this whole page uses

await, Promise.all(), worker threads, and PM2 change software — how many processes/threads exist, and how they wait. They never create extra physical cores. Parallelism only happens after the scheduler places a software thread on a hardware thread, on a core, and the CPU executes.

2) The four pictures

Imagine you have 10 API calls to make. These four pictures are software shapes. None of them is a CPU. Hardware comes after the scheduler.

Synchronous

API 1 → wait → finish API 2 → wait → finish API 3 → wait → finish ... API 10

Everything happens sequentially. The next call cannot start until the previous one returns.

Asynchronous

API 1 ───────────────→ API 2 ───────→ API 3 ─────────→ API 4 ──→ ↓ results

While API 1 is waiting on the network, you can start API 2, 3, and 4.

Multithreading

One process │ ├── Software thread 1 → API 1 ├── Software thread 2 → API 2 ├── Software thread 3 → API 3 └── Software thread 4 → API 4 ↓ OS scheduler ↓ hardware threads / cores

Multiple software threads inside one process. They share memory. The OS may run them at the same time — or time-slice them — on hardware.

Multiprocessing

Process 1 ─┐ Process 2 ─┼── software (own memory) Process 3 ─┤ Process 4 ─┘ ↓ OS scheduler ↓ 14 cores / 20 hardware threads

Independent programs. Each has its own memory. They are still software. Isolation does not mean “this process owns that core.”

3) First: your CPU — 14 cores and 20 threads

Task Manager on this machine reports something like:

14
Physical cores

Actual CPU execution units on the chip.

20
Logical processors

Hardware threads the OS can schedule onto.

PHYSICAL CPU │ ┌─────────────┼─────────────┐ ↓ ↓ ↓ Core 1 Core 2 Core 3 ... │ │ Threads Threads

There are 14 physical CPU cores. The CPU exposes 20 logical processors to the operating system.

14 cores + 20 threads = 14 physical cores and 20 total hardware threads
14 cores × 20 threads = 280 threads ❌

Those 20 threads are the total hardware execution contexts on the chip — not 20 threads per core.

4) Physical core vs hardware thread

A physical core is an actual CPU execution unit. A hardware thread is a logical execution context that the CPU exposes to the OS.

A simpler textbook CPU often looks like this — one core, two hardware threads:

Core 1 → Thread 1 → Thread 2 Core 2 → Thread 3 → Thread 4 ... 8 cores → 16 threads (classic “8 cores / 16 threads”)

That marketing line exists because each core supports 2 hardware threads (SMT / Hyper-Threading).

Your 14 / 20 CPU is not 2 threads on every core. 14 cores and 20 logical processors usually means a hybrid chip: some performance cores have 2 hardware threads, efficiency cores have 1. Do not assume every core has the same thread count just from 14 / 20.
Typical hybrid mapping (example, not a guarantee): 6 P-cores × 2 hardware threads = 12 8 E-cores × 1 hardware thread = 8 ──── Logical CPUs = 20

The exact split depends on the processor. What you can trust from Task Manager is the totals: 14 cores, 20 logical processors.

5) What does the OS see?

Windows / Linux does not simply see “14 CPUs.” It sees something like:

Operating System │ ┌─────────────┼──────────────┐ ↓ ↓ ↓ CPU 0 CPU 1 CPU 2 ... ... ↓ CPU 19

So 20 logical processors are available for scheduling. The OS scheduler places software threads onto those 20 slots. Only about 20 hardware threads can truly execute at once — extra software threads wait or get time-sliced.

6) Now introduce a process

A process is a running program with its own memory and resources.

Node.js application ↓ Process node app.js ↓ OS creates Process 1234

Conceptually a process owns:

Process 1234 │ ├── Code ├── Heap ├── Stack ├── Environment ├── File handles └── Threads

Your Node app is one process (until you start more). Everything below — the event loop, worker threads, libuv — lives inside that process unless you spawn another one.

7) A process can have many threads

A process does not have only one thread. Node can look like this:

Node Process │ ├── Main Thread ├── Worker Thread 1 ├── Worker Thread 2 ├── Worker Thread 3 └── Worker Thread 4

These are software / OS threads created by the application or runtime. They are different from the CPU’s 20 hardware threads.

You can have 100 software threads even though you only have 20 logical CPUs. The extra threads do not create extra cores. The OS multiplexes them onto the 20 logical processors.

8) Three different “thread” concepts

When people say “thread”, they can mean three different things. Mixing them up is how “Node is single-threaded” and “async creates threads” both get oversimplified.

1. Hardware thread

CPU capability. Your chip: 14 cores, 20 hardware threads.

2. OS / software thread

Created by apps and runtimes. Task Manager’s “Threads” count (thousands) is this — not your 20 logical CPUs.

3. JavaScript async work

await fetch(url) is not “create a new CPU thread.” It is an in-flight I/O operation.

9) Context switching

Suppose you have 20 logical CPUs and 100 software threads. The OS has to schedule them:

Time 1: CPU 1 → Thread A CPU 2 → Thread B ... CPU 20 → Thread T Time 2: CPU 1 → Thread U CPU 2 → Thread V ...

Switching a CPU from one software thread to another is context switching. The scheduler saves one thread’s registers / stack pointer and restores another’s.

More threads does not automatically mean more performance. Past a point you pay for switching, cache disruption, and lock contention — while still only executing on ~20 logical processors at a time.
100 software threads ↓ OS scheduler ↓ 20 logical CPUs

10) Synchronous programming

Synchronous = do one thing and wait for it before continuing.

const result1 = await callAPI1(); const result2 = await callAPI2(); const result3 = await callAPI3();

This snippet uses await, so it is async syntax, but it is still sequential execution: each call waits for the previous one. If each API takes 2 seconds:

Sequential execution — total ≈ 6 seconds

API 1
0–2s
API 2
2–4s
API 3
4–6s
0s2s4s6s

Restaurant analogy

Customer 1 orders ↓ Wait for food ↓ Food delivered ↓ Customer 2 orders ↓ Wait ↓ Food delivered

Very simple, and often the right choice for a short script. It becomes inefficient when most of the time is spent waiting.

11) Asynchronous programming

Async = don't block while waiting for something. The program starts work, continues with other work, and comes back when the result is ready.

Important: Using async/await does not automatically run things together. This is still sequential:
const result1 = await callAPI1(); const result2 = await callAPI2(); const result3 = await callAPI3();
Each await pauses this function until that promise settles, so the next call does not start yet.

Start all three calls first, then wait together:

const p1 = callAPI1(); const p2 = callAPI2(); const p3 = callAPI3(); const results = await Promise.all([p1, p2, p3]);
This is software waiting. Overlapping API calls does not mean three hardware threads started.

Concurrent async — total ≈ max(2, 2, 2) = 2 seconds

API 1
~2s
API 2
~2s
API 3
~2s
0s2s4s6s
The payoff: Sequential time is 2 + 2 + 2 ≈ 6s. Concurrent async is max(2, 2, 2) ≈ 2s. That is one of the biggest wins of async programming for I/O-bound work.

Why async is useful

Suppose MongoDB takes 100 ms.

Blocking

Request ↓ MongoDB ↓ WAIT 100ms ↓ Continue

During that wait, this execution path is stuck on that operation.

Async

Request ↓ MongoDB request ↓ “Tell me when finished” ↓ Do other work ↓ MongoDB result arrives ↓ Continue

Powerful for MongoDB, APIs, HTTP, Redis, S3, network, and file I/O.

12) Async does not create 20 threads

This is one of the biggest misconceptions — especially after looking at “20 logical processors” in Task Manager.

If you write:

const result = await fetch(url);

you should not think: fetch() → new CPU thread.

JavaScript ↓ Start I/O ↓ Event loop can handle other work ↓ I/O completes ↓ Promise continuation executes

1,000 users sending requests does not mean Node creates 1,000 software threads, and it certainly does not mean 1,000 hardware threads. The event loop keeps many I/O operations in flight on one main JavaScript software thread.

13) I/O-bound vs CPU-bound

Choosing a model starts with the kind of work you have.

What is I/O?

I/O means Input/Output — waiting on something outside the CPU:

  • Calling an API
  • MongoDB / MySQL / Redis queries
  • Reading or writing a file
  • S3 upload/download
  • HTTP requests and waiting for a response
Node.js | | HTTP request (CPU is mostly idle here) ↓ External API | | processing ↓ Response | ↓ Node.js continues

During that wait, Node.js can handle other work. That is why Node.js is very good for I/O-heavy applications.

CPU-bound work

CPU-bound means the processor itself is busy. There isn't much waiting on a network or disk:

  • Image / video processing
  • Encryption and compression
  • Large calculations and complex algorithms
  • Machine learning inference
  • PDF generation
  • Parsing huge datasets
for (let i = 0; i < 10_000_000_000; i++) { // heavy calculation — the CPU is occupied }
Async alone does not fix CPU-bound work. The event loop is busy computing, so other requests stall. For that, you need worker threads, child processes, or multiple Node processes.

14) Concurrency vs parallelism

This is one of the most common interview traps. Async is usually concurrency. It is not automatically parallelism.

Concurrency

“Multiple tasks are in progress during the same period.” They may take turns on one core. Example: API A, MongoDB B, and API C all outstanding at once.

Parallelism

“Multiple tasks execute at the same time” on different CPU cores / logical processors.

Concurrency (in progress, not necessarily simultaneous CPU): A ────────────────→ B ────────→ C ─────────────→ Parallelism (simultaneous execution): CPU Core 1 → Task A CPU Core 2 → Task B CPU Core 3 → Task C CPU Core 4 → Task D
Concurrency is a software story. Parallelism is a hardware story. The scheduler is how one becomes the other.

Async concurrency — overlapping waits

Task A
Task B
Task C

Parallelism — same time, different cores

CPU 1
CPU 2
CPU 3

Concurrency = dealing with multiple tasks in the same period.
Parallelism = executing multiple tasks simultaneously.

You can have concurrency without parallelism: one software thread, many in-flight I/O operations (await / Promise.all()). Parallelism needs more than one hardware thread actually executing at the same instant. Extra Node processes or Workers only help if the scheduler can place them on different cores.

15) Multithreading

A software thread is an execution path inside a process. It is not a hardware thread and not a core.

Application Process ← software │ ├── Software thread 1 → Task A ├── Software thread 2 → Task B ├── Software thread 3 → Task C └── Software thread 4 → Task D │ ↓ OS scheduler │ ↓ hardware threads / cores

The OS schedules these software threads onto your 20 logical processors. They share the process's memory. They may run at the same time if the scheduler places them on different hardware threads — or they may take turns on one.

Threads and processes are both software. The OS scheduler — not the process — decides which core runs them.
Process │ ├── Thread 1 ──┐ ├── Thread 2 ──┤ ├── Thread 3 ──┤── Shared memory └── Thread 4 ──┘

Shared memory makes communication cheap. It also introduces:

  • Race conditions
  • Deadlocks
  • Locks and contention
  • Hard-to-reproduce synchronization bugs

16) Multithreading vs async

These are often confused because both can "handle more than one thing." They focus on different problems.

Async Multithreading
Main idea Don't block while waiting Have multiple execution threads
Best at I/O waits (network, disk, DB) Overlapping work, some CPU/I/O mixes
Typical cost Low — callbacks / promises / event loop Higher — stacks, context switches, locks
Shared state Usually one JS thread, fewer data races Shared memory — races are common

Async without extra threads

Node.js event-loop style: one JavaScript thread, many in-flight I/O operations.

Threads without async

A Java servlet or a Python thread pool that blocks on I/O inside each thread.

You can also combine them: async I/O on the main thread, worker threads for CPU work.

17) Multiprocessing

Multiprocessing means running multiple independent processes. Each process has its own memory space.

Server │ ├── Process 1 → Heap A ├── Process 2 → Heap B ├── Process 3 → Heap C └── Process 4 → Heap D

This gives stronger isolation than threads. A crash in process 3 usually does not take down process 1. Isolation is a software property. It does not pin Process 1 to Core 1.

Why use it?

A CPU-heavy JavaScript job in one Node process mostly occupies one software thread (the main JS thread). The scheduler can only keep one hardware thread busy with that JavaScript. Several processes create several runnable software threads, so the scheduler has a chance to use several cores:

SOFTWARE HARDWARE Process 1 (main JS thread) ─┐ Process 2 (main JS thread) ─┼──→ OS scheduler ──→ 14 cores / 20 HTs Process 3 (main JS thread) ─┤ Process 4 (main JS thread) ─┘ Not: Process 1 = Core 1

This is especially useful for CPU-bound workloads: image processing, PDF generation, encryption, ML, huge parses — because those jobs need real cores, not just more async.

14-core machine example

Machine: 14 CPU cores / 20 logical processors, 16 GB RAM. Job: process 1 million images, each CPU-heavy.

Single process

One main JS software thread does the heavy work. The scheduler has little else from this app to place on the other cores.

Multiple processes

More software threads for the scheduler to spread across cores. Better hardware utilization if the work is actually CPU-heavy.

19) Node.js architecture

A simplified Node.js process looks like this:

Node.js Process │ ┌────────┴────────┐ │ │ Main JS Thread libuv │ │ Event Loop Thread Pool │ │ ┌────────┼──────┐ ┌────┼────┐ ↓ ↓ ↓ ↓ ↓ ↓ HTTP DB Timer T1 T2 T3

Your JavaScript primarily executes on the main JavaScript thread. The event loop manages asynchronous work. libuv’s pool handles some blocking OS work (file I/O, some crypto/DNS) so that main thread can stay free.

20) What is the event loop?

Node.js primarily uses an event loop for JavaScript execution. While one operation waits on I/O, Node can keep handling other requests. That is why it can serve many concurrent HTTP connections without creating one JavaScript thread per request.

One JavaScript thread drives the event loop. In-flight I/O does not block that thread.
Event Loop │ ┌────────────┼─────────────┐ ↓ ↓ ↓ Request 1 Request 2 Request 3 │ │ │ ↓ ↓ ↓ MongoDB API Redis │ │ │ └────────────┼─────────────┘ ↓ Results

21) Node.js is not simply "single-threaded"

People often say: Node.js is single-threaded. More accurately:

JavaScript execution is primarily handled by a single event-loop thread, while Node.js itself can use additional threads internally and can also use worker threads or multiple processes.

Node.js Process │ ├── Main JavaScript Thread │ └── Event Loop │ ├── libuv worker threads (fs, crypto, DNS, etc.) │ └── OS resources

libuv's thread pool handles some blocking OS work so the event loop stays free. For your own CPU-heavy JavaScript, use worker_threads or extra processes — the main thread will not magically parallelize a tight for loop. Even with 20 logical CPUs, one CPU-heavy JavaScript function still occupies the main thread.

22) Worker Threads in Node.js

Node’s worker_threads module gives you extra JavaScript threads inside the same process.

Node Process │ ├── Main Thread │ ├── HTTP requests │ ├── MongoDB │ └── API │ ├── Worker 1 → Image processing ├── Worker 2 → PDF processing └── Worker 3 → Large calculation

The main event loop stays more responsive because the heavy CPU work is not running on it. Workers are the right tool when the bottleneck is JavaScript computation, not waiting on the network.

23) Does this create a thread?

This is the Node.js rule that ties async, libuv, and worker_threads together. await and Promise.all() change when JavaScript continues. They do not, by themselves, create OS threads.

1. await — no new thread

const a = await getData1();

await does not create a thread. It pauses this function and lets the main JavaScript OS thread run other work until the promise settles.

Node.js Process │ └── Main JS OS Thread │ ├── start async operation ├── await → pause this function │ └── later → resume

The main thread is free to run other JavaScript while waiting. That is concurrency, not a new thread.

2. Promise.all() — concurrent operations, not automatically new threads

await Promise.all([ getData1(), getData2(), getData3() ]);

This starts the operations without waiting for each one sequentially.

Main JS Thread │ ├── getData1 ──┐ ├── getData2 ──┼──→ operations happen concurrently └── getData3 ──┘
Promise.all() ≠ 3 new threads

Whether threads are involved depends on what getData1 / getData2 / getData3 actually do — network I/O, a libuv pool job, or a Worker. Promise.all() only says “run these operations together and wait for all of them.”

3. worker_threads — creates a new OS thread

For CPU-heavy JavaScript you create a Worker yourself:

const { Worker } = require("node:worker_threads"); new Worker("./calculation.js");
Node.js Process │ ├── Main JS OS Thread │ ├── event loop │ └── normal JS │ └── Worker OS Thread ← NEW └── heavy calculation

That is an explicit new Node.js Worker on a separate OS thread. The main event loop can keep serving requests while the worker computes.

4. Where does libuv fit?

libuv is the fourth piece. Some Node APIs offload blocking work to an internal thread pool. Those are OS threads Node already owns — not await, and not new Worker().

Node.js Process │ ┌───────────────┴────────────────┐ │ │ Main JavaScript OS Thread libuv Thread Pool │ │ │ Worker OS Threads │ ├── Worker 1 │ ├── Worker 2 │ ├── Worker 3 │ └── Worker 4 (default pool size) │ └────── node:worker_threads │ NEW OS Thread (your Worker)

Default libuv pool size is 4 (override with UV_THREADPOOL_SIZE). Typical pool users: some fs calls, crypto.pbkdf2, some DNS lookups. fetch() / network I/O generally does not sit on that pool — the OS and event loop handle the socket.

The simple rule

You do New OS thread?
await No
Promise.all() Not by itself
fs.readFile() May use a libuv pool worker
crypto.pbkdf2() Uses a libuv pool worker
fetch() / network I/O Generally not a libuv pool thread
new Worker() Yes — a new Node.js Worker thread

Then every OS thread still competes for hardware

OS Threads │ ├── Chrome threads ├── Node main thread ├── libuv workers ├── Node Worker threads └── Other application threads │ ↓ OS Scheduler │ ↓ CPU hardware threads (20 on this machine) │ ↓ CPU cores (14 on this machine)

The most important distinction

Concurrent JavaScript (await, Promise.all()) overlaps waiting. It does not spawn threads.

libuv pool threads are Node’s hidden OS threads for some blocking C/C++ work. You did not write new Worker().

worker_threads is when you create another JavaScript OS thread for CPU-heavy JS.

All of those OS threads still go through the Windows scheduler onto the CPU’s 20 hardware threads and 14 cores. Creating threads is not the same as getting more cores.

24) Worker Thread vs process

Worker Thread

Same Process │ ├── Main Thread ├── Worker 1 └── Worker 2

Memory can be shared in controlled ways (SharedArrayBuffer, message passing). Less isolation. Cheaper to start than a full process.

Process

Process 1 → Memory 1 Process 2 → Memory 2

Separate memory spaces. More isolation. A worker crash can still hurt the process; a process crash usually stays contained.

25) Node.js multiprocessing and PM2

Because one Node process has a main JavaScript software thread, CPU-heavy JS or high traffic can bottleneck that thread. Extra processes do not add cores. They add more software the scheduler can place on the cores you already have.

SOFTWARE HARDWARE Node Process 1 ─┐ Node Process 2 ─┼── OS scheduler ──→ 20 hardware threads Node Process 3 ─┤ ──→ 14 physical cores Node Process 4 ─┘

PM2 cluster mode (or Node’s cluster module, or multiple containers) runs multiple instances and puts a load balancer in front:

Load │ Load Balancer │ ┌──────────┼──────────┐ ↓ ↓ ↓ Node 1 Node 2 Node 3 ↓ ↓ ↓ Event Event Event Loop Loop Loop

Each process handles I/O efficiently with async. Together they can use multiple cores for JavaScript. One process dying does not take the whole service down.

Why multiple Node processes? One busy main JS thread can stall every request in that process. Several processes let Process 1, 2, 3, 4 do CPU work (or serve traffic) at the same time.

26) Apply your 14-core / 20-thread CPU

The machine has 14 physical cores and 20 logical processors. A Node process is software. It does not become 20 processors, and its main JavaScript thread does not automatically use all 20 logical CPUs.

Scenario A — normal Node.js

Node Process │ Main JS Thread │ Event Loop

Your main JavaScript execution does not automatically spread one CPU-heavy operation across 20 logical CPUs.

Scenario B — many API calls

Node │ Event Loop │ ├── API 1 ─────→ ├── API 2 ─────→ ├── API 3 ─────→ ├── ... └── API 100 ───→

This is excellent for I/O. You do not need 100 threads.

Scenario C — 100 CPU-heavy tasks

Async alone is not the magic solution for image processing or heavy math. Use worker threads or multiple processes so the CPU can actually be utilized.

Do not blindly create 20 workers because Task Manager says 20 threads. The right count depends on physical vs SMT/hybrid cores, memory, I/O waiting, worker overhead, garbage collection, and other services on the machine. For CPU-heavy work, start with a sensible count (often near physical cores) and benchmark.

27) Combining async + threads + processes

These are not competitors. They solve different problems and can all coexist:

SOFTWARE (you control this) HARDWARE (fixed) │ Node 1 / Node 2 / Node 3 processes │ Event loops + async I/O + Workers │ ↓ OS scheduler │ ↓ 20 hardware threads → 14 cores → CPU executes

WRM / mixed workload

Imagine 10,000 URLs. Each needs an HTTP request, a screenshot, HTML processing, and a MongoDB update.

  • HTTP / MongoDB — mostly I/O-bound → async
  • Screenshot — potentially CPU / memory heavy
  • HTML processing — CPU-heavy depending on complexity
Queue │ ┌───────────┼───────────┐ ↓ ↓ ↓ Worker Worker Worker Node Node Node │ │ │ Async Async Async │ │ │ ┌────┼────┐ ┌────┼────┐ ┌────┼────┐ ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓ API Mongo S3 API Mongo S3 API Mongo S3

CPU-heavy screenshot / processing can be isolated into worker threads if the main loop starts to stall.

One example showing everything

1,000 URLs │ ↓ Queue │ ┌──────────────┼──────────────┐ ↓ ↓ ↓ Node Process 1 Node Process 2 Node Process 3 │ │ │ Event Loop Event Loop Event Loop │ │ │ Async HTTP Async HTTP Async HTTP │ │ │ MongoDB MongoDB MongoDB │ │ │ └──────────────┼──────────────┘ ↓ CPU-heavy work │ ┌───────┼───────┐ ↓ ↓ ↓ Worker 1 Worker 2 Worker 3
  • Multiprocessing → multiple Node processes
  • Multithreading → worker threads where appropriate
  • Async → HTTP / DB / network
  • Concurrency → many websites in progress
  • Parallelism → CPU-heavy jobs across CPU resources
  • Queue → controls how much work enters the system

28) Why queues are important

Do not send 10,000 jobs directly into the process. Put them on a queue and let a controlled number of workers pull:

10,000 URLs ↓ Queue │ ├── Job 1 ├── Job 2 ├── Job 3 ... └── Job 10000 ↓ Controlled workers take jobs at a safe rate

That gives you concurrency control, retries, fault tolerance, backpressure, scaling, and monitoring. Tools people actually use: BullMQ, RabbitMQ, SQS, and similar.

30) Don't do unlimited async

A very common mistake:

await Promise.all( 100000.map(url => processURL(url)) );

That can create huge pressure on external APIs, MongoDB, memory, network connections, CPU, and file descriptors.

Use controlled concurrency. Keep a fixed number of operations in flight (for example 20), and start the next one only when one finishes.
250 URLs ↓ Concurrency = 20 ↓ 20 running ↓ completed ↓ next 20 Batch 1 → 20 Batch 2 → 20 Batch 3 → 20 ...

This is almost always safer in production than firing every promise at once. A job queue is the same idea at system scale.

Read it top to bottom

  1. Application. You start a program — node app.js, Chrome, VS Code. That is still just a file until the OS loads it.
  2. Process. Windows creates a process: its own memory (code, heap, stack), file handles, and environment. Node is usually one process. Chrome is many processes (browser + GPU + a process per tab), which is why a crashed tab does not kill the whole browser.
  3. Software threads. Inside each process the runtime creates OS threads — Node’s main JS thread, libuv pool threads, worker threads; Chrome’s UI, compositor, and renderer threads. These are not the 20 hardware threads in Task Manager. You can have thousands of software threads on this machine.
  4. OS scheduler. Windows decides, many times per second, which software threads get a turn. Node and Chrome do not pick a core themselves. They ask the scheduler for CPU time. This is the bridge between the software column and the hardware column.
  5. Hardware threads (logical processors). The scheduler places a runnable software thread onto one of your 20 logical CPUs (HT1…HT20). Only about 20 software threads can truly execute at the same instant. The rest wait or get time-sliced.
  6. Physical core. Each hardware thread sits on a real core. Your chip has 14 physical cores. Some cores expose two hardware threads, some expose one. Two hardware threads on the same core share that core’s execution units — they interleave, they are not two full extra cores.
  7. CPU executes instructions. The core fetches and runs machine instructions. That is the only place work actually happens. Everything above it — processes, threads, async, PM2 — is about who is allowed to reach this step, and when.

Why this picture matters

Async, worker threads, and PM2 all sit on the software side. They change how many processes/threads exist and how they wait. They do not create extra physical cores.

The Windows scheduler and the 20 hardware threads sit in the middle. They are why 100 software threads do not mean 100× speed.

The 14 cores sit on the hardware side. That is the real parallelism budget for CPU-heavy work.

Software column

Applications, processes, software threads, async work, worker threads, PM2 instances. Cheap to create relative to cores. Easy to over-create.

Hardware column

14 physical cores, 20 hardware threads, the execution units that run instructions. Fixed for this machine. The ceiling for true parallel CPU work.

32) How to remember it

The hierarchy

Application → Process → Software Threads → OS Scheduler → Hardware Threads → Physical Core → CPU executes PHYSICAL MACHINE │ ├── SOFTWARE: Node / Chrome processes + threads └── HARDWARE: 14 cores / 20 logical processors │ ↓ Windows Scheduler │ ┌─────┴─────┐ ↓ ↓ Process 1 Process 2 │ │ Threads Threads │ ↓ Node.js │ Main JS Thread │ ↓ Event Loop │ ↓ Async I/O operations │ ↓ Worker threads / PM2 processes when CPU or traffic needs them
Waiters = software threads. Separate restaurants = processes. Kitchen stations = hardware cores. Extra waiters do not build extra kitchens.

Synchronous

One waiter: take order → wait in the kitchen → deliver → next customer. Simple, slow when the kitchen is the bottleneck.

Async

One waiter takes order A, gives it to the kitchen, takes B and C, then delivers food as it is ready. No standing around.

Multithreading

Several waiters in the same restaurant, sharing the same kitchen and floor.

Multiprocessing

Completely separate restaurants, each with its own kitchen and staff.

SYNC

"Wait until I'm done."

ASYNC

"Don't wait; let me do other work."

SOFTWARE THREAD

"Another execution path inside a process. Not a core."

PROCESS

"Another independent program. Still software."

CONCURRENCY

"Handle multiple things in the same period."

PARALLELISM

"Execute multiple things at the same time."

The 5 lines

SOFTWARE ↓ Processes, software threads, await, Promise.all, libuv pool, Worker, PM2 ↓ Ask for CPU time. Do not execute silicon. OS SCHEDULER ↓ The only bridge HARDWARE ↓ 14 physical cores 20 hardware threads / logical processors ↓ The only place instructions run NODE ASYNC ↓ Concurrent I/O on one software thread ↓ Not new hardware WORKER / EXTRA PROCESSES ↓ More software for the scheduler to place on cores MULTIPROCESSING + ASYNC ↓ Multiple Node processes (PM2), each efficiently handling I/O

For Node.js specifically

I/O-heavy

Async / event loop → API + MongoDB + S3 + HTTP

CPU-heavy

Worker threads / processes → images, PDFs, compression, heavy math

High traffic

PM2 cluster / multiple Node processes or containers → load balancer

The key rule

Async improves how software waits. Software threads and processes change how software is structured. Only hardware executes in parallel — after the OS scheduler maps a software thread onto a core.

That is why "async vs multithreading" is not an apples-to-apples comparison. They sit on different axes:
