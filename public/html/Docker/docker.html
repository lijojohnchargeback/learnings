🐳 Docker Complete Guide

Containerization & Application Deployment

📚 Introduction to Docker

Docker is a container technology that packages code and dependencies together, making applications portable across any operating system.

What Problem Does Docker Solve?

  • 🔧 Environment Inconsistency: "It works on my machine" problem
  • 🔧 Version Conflicts: Dev uses Node 14, production uses Node 16
  • 🔧 Complex Setup: Different team members have different environments
  • 🔧 Deployment Issues: Manual configuration on servers

Docker Components

  • 🐳 Docker Engine: Core runtime that runs containers
  • 🐳 Docker Desktop: GUI application for managing Docker
  • 🐳 Docker CLI: Command-line interface to control Docker
  • 🐳 Docker Hub: Cloud registry to share Docker images
  • 🐳 Docker Compose: Tool for multi-container applications

Key Benefits

  • ✅ Portability: Run anywhere - dev, staging, production
  • ✅ Isolation: Each container is isolated from others
  • ✅ Lightweight: Faster than virtual machines
  • ✅ Scalability: Easy to scale up or down
  • ✅ Consistency: Same environment everywhere

Docker Architecture (Client-Server Model)

Docker uses a client-server architecture. You interact with the Docker CLI (client), which sends commands to the Docker Daemon (server) that actually builds, runs, and manages containers.

Component Role Details
Docker Client User interface docker CLI commands you type in terminal
Docker Daemon Background service Listens for API requests, manages images, containers, networks, volumes
REST API Communication layer Interface between client and daemon
Container Runtime Execution engine containerd + runc — actually runs containers using Linux namespaces & cgroups
Registry Image storage Docker Hub, AWS ECR, or private registries

How Containers Work Under the Hood

Containers are not mini virtual machines. They share the host OS kernel and use:

  • Namespaces — isolate process IDs, network, filesystem, users
  • Cgroups — limit CPU, memory, and I/O per container
  • Union File Systems — layer images on top of each other (overlay2)

⚙️ Installing Docker

Windows

  1. Download Docker Desktop from docker.com
  2. Enable WSL 2 backend (recommended) during installation
  3. Restart your computer if prompted
  4. Verify: docker --version and docker run hello-world

macOS

  1. Download Docker Desktop for Mac (Apple Silicon or Intel)
  2. Drag Docker to Applications folder and launch
  3. Grant permissions when prompted
  4. Verify with docker run hello-world

Linux (Ubuntu/Debian)

# Remove old versions sudo apt-get remove docker docker-engine docker.io containerd runc # Install prerequisites sudo apt-get update sudo apt-get install ca-certificates curl gnupg lsb-release -y # Add Docker's official GPG key sudo mkdir -p /etc/apt/keyrings curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg # Set up repository echo \ "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu \ $(lsb_release -cs) stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null # Install Docker Engine sudo apt-get update sudo apt-get install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin -y # Add user to docker group (no sudo needed) sudo usermod -aG docker $USER newgrp docker # Verify installation docker --version docker compose version docker run hello-world

Post-Installation Checklist

Check Command Expected Result
Docker version docker --version Docker version 24.x or higher
Daemon running docker info Server section shows running status
Pull image docker pull nginx Image downloads successfully
Run container docker run --rm hello-world "Hello from Docker!" message

🆚 Docker vs Virtual Machines

Understanding the difference between containers and VMs is fundamental to choosing the right deployment strategy.

Aspect Virtual Machine Docker Container
OS Full guest OS per VM (GBs) Shares host OS kernel
Startup Time Minutes Seconds (often < 1s)
Size GBs (10-20GB+ per VM) MBs (10-500MB typical)
Performance Hypervisor overhead Near-native performance
Isolation Strong (hardware-level) Process-level (good for most apps)
Density 10-20 VMs per host 100+ containers per host
Best For Legacy apps, different OS types, strict isolation Microservices, CI/CD, cloud-native apps

When to Use What?

  • 🐳 Use Docker for application packaging, microservices, dev environments, CI/CD pipelines
  • 🖥️ Use VMs when you need a full OS, run Windows on Linux host, or meet strict compliance isolation
  • ☁️ Use both in production — VMs host Docker, containers run inside them (common in AWS ECS, EKS)

📦 Containers & Images

What is a Container?

A container is a running instance of an image. It's like a lightweight, isolated environment that runs your application.

What is an Image?

An image is a blueprint/template that contains your application code, dependencies, and configuration.

Feature Image Container
Nature Template/Blueprint Running instance
State Static Dynamic
Analogy Class Object
Multiple One image Many containers from one image

Image Types

  • 📦 Official Images: Node, MongoDB, Redis, MySQL (from Docker Hub)
  • 📦 Custom Images: Your application with its dependencies
  • 📦 Base Images: Minimal OS layers — alpine, debian, ubuntu
  • 📦 Multi-stage Images: Build in one stage, copy artifacts to a smaller final image

🔄 Container Lifecycle

Every container goes through a defined lifecycle. Understanding these states helps with debugging and orchestration.

State Description Command to Reach
Created Container exists but hasn't started docker create image
Running Container is actively executing docker start or docker run
Paused Processes frozen (rarely used) docker pause <name>
Stopped (Exited) Container finished or was stopped docker stop <name>
Removed Container deleted permanently docker rm <name>

Restart Policies

Control what happens when a container exits or Docker daemon restarts:

Policy Behavior Use Case
no Never restart (default) One-off tasks, batch jobs
on-failure Restart only on non-zero exit code Apps that may crash temporarily
always Always restart, even after manual stop Critical services (use carefully)
unless-stopped Restart unless manually stopped Most common for production
# Production database — restart unless manually stopped docker run -d \\ --name mongodb \\ --restart unless-stopped \\ -v mongodb_data:/data/db \\ -p 27017:27017 \\ mongo:7 # Check container status and exit code docker ps -a docker inspect mongodb --format='{{.State.Status}} {{.State.ExitCode}}' # View why a container stopped docker logs mongodb docker inspect mongodb --format='{{.State.Error}}'

📄 Dockerfile

A Dockerfile is a text file with instructions to build a Docker image.

Basic Dockerfile Structure

# Start from base image FROM node:20 # Set working directory WORKDIR /app # Copy package.json first (for better caching) COPY package.json . # Install dependencies RUN npm install # Copy rest of application code COPY . . # Expose port EXPOSE 8000 # Command to run app CMD ["node", "index.js"]

React Application Dockerfile

FROM node:20 WORKDIR /app COPY package.json . RUN npm install COPY . . EXPOSE 3000 CMD ["npm", "start"]

Docker Layer Caching

Docker builds images in layers. Each instruction creates a new layer.

Why Layer Order Matters:

  • ✅ Copy package.json first, then npm install
  • ✅ Copy application code last
  • ✅ If code changes but dependencies don't, Docker reuses cached layers
  • ✅ Faster builds!

.dockerignore File

Prevent unnecessary files from being copied into the image

node_modules .git .env *.log .DS_Store README.md

Production Node.js Dockerfile (Multi-Stage)

# Stage 1: Build FROM node:20-alpine AS builder WORKDIR /app COPY package*.json ./ RUN npm ci COPY . . RUN npm run build # Stage 2: Production FROM node:20-alpine WORKDIR /app RUN addgroup -g 1001 -S nodejs && adduser -S nodejs -u 1001 COPY --from=builder /app/dist ./dist COPY --from=builder /app/package*.json ./ RUN npm ci --only=production && npm cache clean --force USER nodejs EXPOSE 3000 HEALTHCHECK --interval=30s --timeout=3s CMD wget -qO- http://localhost:3000/health || exit 1 CMD ["node", "dist/index.js"]

Python Flask Dockerfile

FROM python:3.12-slim WORKDIR /app COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt COPY . . EXPOSE 5000 CMD ["gunicorn", "--bind", "0.0.0.0:5000", "app:app"]

Nginx Static Site Dockerfile

# Build React app FROM node:20-alpine AS build WORKDIR /app COPY package*.json ./ RUN npm ci COPY . . RUN npm run build # Serve with Nginx FROM nginx:alpine COPY --from=build /app/dist /usr/share/nginx/html COPY nginx.conf /etc/nginx/conf.d/default.conf EXPOSE 80 CMD ["nginx", "-g", "daemon off;"]

CMD vs ENTRYPOINT

Instruction Purpose Can Override?
CMD Default command to run Yes — replaced by docker run args
ENTRYPOINT Main executable (container's purpose) No — args append to it
# ENTRYPOINT + CMD pattern (flexible CLI tools) ENTRYPOINT ["python", "app.py"] CMD ["--port", "8000"] # docker run myapp --port 9000 → python app.py --port 9000

📋 Dockerfile Instructions Reference

Complete reference of every Dockerfile instruction and when to use it.

Instruction Description Example
FROM Base image (required, must be first) FROM node:20-alpine
WORKDIR Set working directory inside container WORKDIR /app
COPY Copy files from host to image COPY package.json .
ADD Like COPY + can extract tar archives ADD app.tar.gz /app (prefer COPY)
RUN Execute command during build (creates layer) RUN npm install
CMD Default command when container starts CMD ["node", "index.js"]
ENTRYPOINT Main executable (not overridden easily) ENTRYPOINT ["python", "app.py"]
EXPOSE Document which port the app listens on EXPOSE 3000
ENV Set environment variable in image ENV NODE_ENV=production
ARG Build-time variable (not in final image) ARG VERSION=1.0
VOLUME Declare mount point for persistent data VOLUME /data
USER Run subsequent commands as non-root user USER nodejs
HEALTHCHECK Define how to test if container is healthy HEALTHCHECK CMD curl -f http://localhost/ || exit 1
ONBUILD Trigger when image is used as base ONBUILD COPY . .
LABEL Add metadata to image LABEL version="1.0" maintainer="you@email.com"

Best practice: Use exec form CMD ["node", "app.js"] instead of shell form CMD node app.js. Exec form runs PID 1 directly, allowing proper signal handling (SIGTERM for graceful shutdown).

💾 Volumes & Data Management

Types of Data in Containers

  • 📝 Application Code: Read-only (rebuild image to change)
  • 📝 Temporary Data: Deleted when container stops
  • 📝 Permanent Data: Needs to persist (databases, uploads)

1. Named Volumes

Managed by Docker, best for persistent data

# Create and use named volume docker run -d \\ -p 27017:27017 \\ -v mongodb_data:/data/db \\ --name mongodb \\ mongo # List volumes docker volume ls # Remove volume docker volume rm mongodb_data

2. Bind Mounts

Map host machine folder to container folder

# Windows docker run -d -p 3000:80 \\ -v "%cd%"/src:/app/src \\ --name react-app \\ myapp # Linux/Mac docker run -d -p 3000:80 \\ -v $(pwd)/src:/app/src \\ --name react-app \\ myapp

3. Read-Only Volumes

# Make volume read-only with :ro docker run -d \\ -v "$(pwd)":/app:ro \\ -v /app/node_modules \\ --name myapp \\ myimage

Environment Variables

# Method 1: In Dockerfile ENV PORT=80 EXPOSE $PORT # Method 2: Command line docker run -e PORT=8000 -e NODE_ENV=production myapp # Method 3: Environment file docker run --env-file ./.env myapp

⚠️ Security: Never commit .env files with sensitive data to version control!

🌐 Docker Networking

Network Scenarios

  • 🌍 Container → Internet: Works by default
  • 💻 Container → Host Machine: Use host.docker.internal
  • 🐳 Container → Container: Use Docker networks

Network Drivers

Driver Scope Use Case
bridge Single host (default) Containers on same machine communicating
host Single host Container uses host's network directly (no isolation)
none Single host Disable networking entirely
overlay Multi-host (Swarm) Containers across multiple Docker hosts
macvlan Single host Assign MAC address, appear as physical device

DNS Resolution in Docker Networks

Containers on the same user-defined network can reach each other by container name as hostname. Docker's embedded DNS server resolves names automatically.

# backend can connect to mongodb using hostname "mongodb" MONGO_URL=mongodb://mongodb:27017/mydb # Inspect network and connected containers docker network inspect my-network # List all networks docker network ls # Connect running container to network docker network connect my-network existing-container # Disconnect container from network docker network disconnect my-network existing-container

Creating Docker Networks

# Create network docker network create my-network # Run containers on same network docker run -d \\ --name mongodb \\ --network my-network \\ mongo docker run -d \\ --name backend \\ --network my-network \\ -e MONGO_URL=mongodb://mongodb:27017/mydb \\ backend-image # Containers can communicate using container names as hostnames

Real-World Example: MERN Stack

# 1. Create network docker network create mern-network # 2. Start MongoDB docker run -d \\ --name mongodb \\ --network mern-network \\ -v mongodb_data:/data/db \\ mongo # 3. Start Backend (Node.js) docker run -d \\ --name backend \\ --network mern-network \\ -p 8000:8000 \\ -e MONGO_URL=mongodb://mongodb:27017 \\ backend-image # 4. Start Frontend (React) docker run -d \\ --name frontend \\ -p 3000:3000 \\ frontend-image

🎼 Docker Compose

Docker Compose is a tool for defining and running multi-container Docker applications using a YAML file.

Benefits of Docker Compose

  • ✅ Define all services in one file
  • ✅ Start all containers with one command
  • ✅ Automatic network creation
  • ✅ Easy to share with team

docker-compose.yml Example

version: "3.8" services: mongodb: image: mongo ports: - "27017:27017" volumes: - mongodb_data:/data/db backend: build: ./backend ports: - "8000:8000" env_file: - ./.env volumes: - ./backend:/app - /app/node_modules depends_on: - mongodb frontend: build: ./frontend ports: - "3000:3000" volumes: - ./frontend/src:/app/src stdin_open: true tty: true depends_on: - backend volumes: mongodb_data:

Docker Compose Commands

# Start all services docker-compose up # Start in detached mode docker-compose up -d # Rebuild images and start docker-compose up --build # Stop all services docker-compose down # Stop and remove volumes docker-compose down -v # View logs docker-compose logs # View specific service logs docker-compose logs backend

Advanced Compose Features

services: backend: build: ./backend restart: unless-stopped healthcheck: test: ["CMD", "curl", "-f", "http://localhost:8000/health"] interval: 30s timeout: 10s retries: 3 start_period: 40s depends_on: mongodb: condition: service_healthy deploy: resources: limits: cpus: '0.5' memory: 512M mongodb: image: mongo:7 healthcheck: test: echo 'db.runCommand("ping").ok' | mongosh localhost:27017/test --quiet interval: 10s timeout: 5s retries: 5 debug-tools: image: nicolaka/netshoot profiles: [debug] # Only starts with: docker compose --profile debug up network_mode: service:backend

docker-compose.override.yml

Docker Compose automatically merges docker-compose.yml with docker-compose.override.yml if present. Use this for dev-specific settings without changing production config.

# docker-compose.override.yml (auto-loaded in dev) services: backend: volumes: - ./backend:/app - /app/node_modules environment: - NODE_ENV=development command: npm run dev

💓 Health Checks & Monitoring

Health checks tell Docker (and orchestrators like Kubernetes) whether your container is actually working, not just running.

HEALTHCHECK in Dockerfile

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \\ CMD curl -f http://localhost:3000/health || exit 1 # Options: # --interval How often to run check (default: 30s) # --timeout Max time for check to complete (default: 30s) # --start-period Grace period on startup (default: 0s) # --retries Consecutive failures before unhealthy (default: 3)

Health Check Status

Status Meaning
starting Within start-period, not yet evaluated
healthy Check passed
unhealthy Check failed retries times
# View health status docker ps docker inspect --format='{{.State.Health.Status}}' myapp # View health check log history docker inspect --format='{{json .State.Health}}' myapp | jq # Monitor all running containers in real-time docker stats # Monitor with custom format docker stats --format "table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}\t{{.NetIO}}"

Simple Health Endpoint (Node.js)

// Add to your Express app app.get('/health', (req, res) => { res.status(200).json({ status: 'ok', uptime: process.uptime(), timestamp: Date.now() }); });

🎂 Image Layers & Caching

Docker images are built in layers. Each instruction in a Dockerfile creates a new layer.

How Layer Caching Works

Key Concept: Docker caches each layer and reuses it if nothing has changed

  • ✅ If a layer hasn't changed, Docker uses the cached version
  • ✅ Once a layer changes, all subsequent layers are rebuilt
  • ✅ This makes builds much faster!

Optimal Layer Order

# ❌ BAD - Code changes rebuild everything FROM node:20 WORKDIR /app COPY . . # Copies everything first RUN npm install # Installs dependencies CMD ["npm", "start"] # ✅ GOOD - Dependencies cached separately FROM node:20 WORKDIR /app COPY package.json . # Copy package.json first RUN npm install # Cache this layer COPY . . # Copy rest of code CMD ["npm", "start"]

Layer Commands

# View image layers docker image inspect image_id # View layer history docker history image_id # Remove all unused images (free up space) docker image prune # Remove all images not used by containers docker image prune -a

Understanding Image Size

Each Docker image includes:

  • 🔹 Base OS layer (Linux)
  • 🔹 Application runtime (Node, Python, etc.)
  • 🔹 Dependencies
  • 🔹 Your application code
  • 🔹 Configuration files

Important: If a container is running or stopped, you cannot delete its image. Remove the container first!

🚫 .dockerignore File

The .dockerignore file tells Docker which files and directories to exclude when copying files.

Why Use .dockerignore?

  • ✅ Reduces image size
  • ✅ Faster builds (less data to copy)
  • ✅ Prevents sensitive data from being included
  • ✅ Improves security

Common .dockerignore Content

# Dependencies node_modules npm-debug.log # Git .git .gitignore # Environment files (security!) .env .env.local .env.production # Logs *.log logs # Documentation README.md *.md docs # IDE .vscode .idea *.swp .DS_Store # Test files __tests__ *.test.js coverage # Docker files Dockerfile docker-compose.yml # Build artifacts dist build *.zip

⚠️ Security Warning: Always add .env files to .dockerignore to prevent exposing sensitive credentials!

📁 Bind Mounts Deep Dive

Bind mounts map a folder on your host machine directly to a folder in the container.

Volumes vs Bind Mounts

Feature Named Volumes Bind Mounts
Management Managed by Docker Managed by you
Location Unknown (Docker decides) You specify exact path
Best For Persistent data (databases) Live code updates (development)
Syntax volume_name:/container/path /host/path:/container/path

Bind Mount Examples

# Linux/Mac - Current directory docker run -d \\ -v $(pwd):/app \\ -p 3000:3000 \\ myapp # Windows - Current directory docker run -d \\ -v "%cd%":/app \\ -p 3000:3000 \\ myapp # Absolute path (Windows) docker run -d \\ -v D:\\project\\myapp:/app \\ -p 3000:3000 \\ myapp

Excluding node_modules

Common problem: Host's node_modules conflict with container's

# Solution: Anonymous volume for node_modules docker run -d \\ -v "$(pwd)":/app \\ -v /app/node_modules \\ -p 3000:3000 \\ myapp # This tells Docker: # - Map current directory to /app # - BUT keep /app/node_modules from the container

Read-Only Bind Mounts

Prevent container from modifying host files

# Make bind mount read-only with :ro docker run -d \\ -v "$(pwd)":/app:ro \\ -v /app/node_modules \\ -v /app/logs \\ -p 3000:3000 \\ myapp # Container can: # - Read from /app (read-only) # - Write to /app/node_modules (writable anonymous volume) # - Write to /app/logs (writable anonymous volume)

Live Reload Configuration

# React app with hot reload docker run -d \\ -e CHOKIDAR_USEPOLLING=true \\ -v "$(pwd)/src":/app/src \\ -p 3000:3000 \\ --name react-app \\ myreactapp # Node app with nodemon docker run -d \\ -v "$(pwd)":/app \\ -v /app/node_modules \\ -p 8000:8000 \\ --name backend \\ mybackend

🔐 Environment Variables & Arguments

Three Ways to Set Environment Variables

1. In Dockerfile (Build-time)

FROM node:20 WORKDIR /app # Set environment variable ENV PORT=80 ENV NODE_ENV=production # Use in EXPOSE EXPOSE $PORT COPY . . CMD ["node", "server.js"]

2. Command Line (Runtime)

# Single variable docker run -e PORT=8000 -e NODE_ENV=production myapp # Short form docker run --env PORT=8000 myapp # Multiple variables docker run \\ -e PORT=8000 \\ -e NODE_ENV=production \\ -e DB_HOST=mongodb \\ -e DB_PORT=27017 \\ myapp

3. Environment File (Recommended for Production)

# Create .env file PORT=8000 NODE_ENV=production DB_HOST=mongodb DB_PORT=27017 DB_NAME=mydb JWT_SECRET=your-secret-key # Use with Docker docker run --env-file ./.env myapp

🔒 Security Best Practices:

  • ❌ Never commit .env files with sensitive data to Git
  • ✅ Add .env to .gitignore
  • ✅ Use .env.example with placeholder values
  • ✅ Store production secrets in secure vaults (AWS Secrets Manager, Azure Key Vault)

Build Arguments (ARG)

Variables available only during image build

☸️ Introduction to Kubernetes

Kubernetes (K8s) is an open-source system for automating deployment, scaling, and management of containerized applications.

Problems Kubernetes Solves

  • 🔧 Container Crashes: Automatically restart failed containers
  • 🔧 Traffic Distribution: Load balance across multiple containers
  • 🔧 Auto-Scaling: Scale up/down based on traffic
  • 🔧 Self-Healing: Replace unhealthy containers
  • 🔧 Rolling Updates: Deploy new versions without downtime

Kubernetes Architecture

Component Description
Cluster Set of nodes that run containerized applications
Master Node Controls the cluster (orchestration)
Worker Nodes Run your containerized applications
Pod Smallest deployable unit (contains 1+ containers)
Service Exposes pods to network traffic
Deployment Manages desired state of pods

Docker vs Kubernetes

Aspect Docker Kubernetes
Purpose Containerization platform Container orchestration
Scaling Manual Automatic
Load Balancing Manual setup Built-in
Self-Healing No Yes
Best For Development, small deployments Production, large-scale apps

When to Use Kubernetes

  • ✅ Large-scale applications
  • ✅ High-traffic websites
  • ✅ Microservices architecture
  • ✅ Need auto-scaling
  • ✅ Complex deployment requirements

Kubernetes Alternatives

  • 🔹 Docker Swarm: Docker's built-in orchestration
  • 🔹 Amazon ECS: AWS container orchestration
  • 🔹 AWS Fargate: Serverless containers
  • 🔹 Google Cloud Run: Serverless container platform

Basic Kubernetes Commands

# Deploy application kubectl apply -f deployment.yaml # View running pods kubectl get pods # View services kubectl get services # View logs kubectl logs <pod-name> # Scale deployment kubectl scale deployment myapp --replicas=5 # Port forward to local machine kubectl port-forward pod/myapp 8080:80

Sample deployment.yaml

apiVersion: apps/v1 kind: Deployment metadata: name: myapp spec: replicas: 3 selector: matchLabels: app: myapp template: metadata: labels: app: myapp spec: containers: - name: myapp image: username/myapp:1.0.0 ports: - containerPort: 3000 resources: limits: memory: "256Mi" cpu: "500m"

Deploy to AWS EC2 (Full Workflow)

✨ Docker Best Practices

Dockerfile Best Practices

1. Use Official Base Images

# ✅ GOOD FROM node:20-alpine # ❌ BAD - Use tagged versions FROM node:latest

2. Optimize Layer Order

# ✅ GOOD - Copy package.json first COPY package.json . RUN npm install COPY . . # ❌ BAD - Installs deps on every code change COPY . . RUN npm install

3. Use .dockerignore

Exclude unnecessary files (node_modules, .git, logs)

4. Multi-Stage Builds

# Build stage FROM node:20 AS build WORKDIR /app COPY package.json . RUN npm install COPY . . RUN npm run build # Production stage FROM node:20-alpine WORKDIR /app COPY --from=build /app/dist ./dist COPY package.json . RUN npm install --production CMD ["node", "dist/index.js"]

5. Minimize Layers

# ✅ GOOD - Combine RUN commands RUN apt-get update && \\ apt-get install -y curl vim && \\ apt-get clean # ❌ BAD - Creates 3 layers RUN apt-get update RUN apt-get install -y curl vim RUN apt-get clean

Security Best Practices

  • 🔒 Never store secrets in images
  • 🔒 Use environment variables for sensitive data
  • 🔒 Run containers as non-root user
  • 🔒 Keep images updated (security patches)
  • 🔒 Scan images for vulnerabilities
  • 🔒 Use private registries for production images

Running as Non-Root User

# Create user in Dockerfile FROM node:20-alpine RUN addgroup -g 1001 -S appgroup && \\ adduser -S appuser -u 1001 -G appgroup WORKDIR /app COPY --chown=appuser:appgroup . . USER appuser CMD ["node", "index.js"] # Or run as specific user at runtime docker run --user 1001:1001 myapp

Performance Best Practices

  • ⚡ Use Alpine Linux base images (smaller)
  • ⚡ Leverage build cache effectively
  • ⚡ Remove unnecessary files in same layer
  • ⚡ Use multi-stage builds
  • ⚡ Limit container resources (CPU, memory)

Development Best Practices

  • 💡 Use Docker Compose for multi-container apps
  • 💡 Use bind mounts for live code updates
  • 💡 Tag images with meaningful versions
  • 💡 Document your Docker setup (README)
  • 💡 Use .env files (don't commit them!)
  • 💡 Test containers before pushing to production

Container Naming Convention

# Good naming practices docker run --name frontend-prod myapp docker run --name backend-staging mybackend docker run --name mongodb-dev mongo # Image tagging docker build -t myapp:1.0.0 . docker build -t myapp:latest . docker build -t myapp:dev .

Resource Management

# Limit CPU and memory docker run -d \\ --cpus="1.5" \\ --memory="512m" \\ --name myapp \\ myimage # View resource usage docker stats # Clean up unused resources docker system prune -a

Common Pitfalls to Avoid:

  • ❌ Using :latest tag in production
  • ❌ Not using .dockerignore
  • ❌ Storing secrets in images
  • ❌ Running containers as root
  • ❌ Not cleaning up old images/containers
  • ❌ Copying entire project including node_modules
