📚 GCP Compute Overview

GCP Compute is the set of services that run your code. The same workload — a web API, a nightly ETL job, a GPU training run — can land on a virtual machine, a Kubernetes pod, a serverless container, or an event-driven function. The hard skill is matching how long the work lives, how much of the stack you want to own, and what hardware you actually need.

How to think about compute

Rent time on someone else's CPU

Compute Engine is a lease on a virtual machine: you pick the image, machine type, VPC subnet, and firewall tags. Cloud Run is a lease on request-driven container instances. GKE sits in between — you ship workloads to a Kubernetes control plane Google operates (and optionally nodes Google operates in Autopilot).

Architects usually start at the highest abstraction that still works, then drop down when they hit a hard constraint: GPUs, custom kernels, Windows, sticky in-memory sessions, or daemonsets that need host networking.

Start here when

  • HTTP service in a container → Cloud Run
  • Event glue (GCS, Pub/Sub) → Cloud Functions
  • Kubernetes APIs / multi-service platform → GKE
  • Custom OS, GPU, or long-lived process → Compute Engine

A common mistake

  • Choosing GKE before the team can operate Kubernetes
  • Running always-on APIs on oversized VMs with no MIG
  • Stuffing a multi-hour batch job into Cloud Functions
  • Leaving idle GPUs and unattached disks billed overnight

AWS comparison

  • EC2 ↔ Compute Engine — VMs; GCP custom machine types let you dial vCPU/RAM finely.
  • Lambda ↔ Cloud Functions — event functions; long HTTP containers often prefer Cloud Run (Fargate-adjacent).
  • EKS ↔ GKE — managed Kubernetes; Autopilot reduces node toil further.
  • Elastic Beanstalk ↔ App Engine — PaaS with opinions.
  • AWS Batch ↔ Batch — managed batch scheduling.

🧭 Decision Guide

Ask these questions in order

  1. Is it HTTP and packageable as a container? Prefer Cloud Run.
  2. Is it a short event handler with a simple runtime? Cloud Functions is fine (often still Cloud Run underneath).
  3. Do you need Kubernetes primitives (CRDs, DaemonSets, complex service mesh)? GKE.
  4. Do you need the OS, GPU drivers, or Windows? Compute Engine (or GKE with GPU node pools).
  5. Is it embarrassingly parallel batch? Batch or Cloud Run jobs; Spot VMs for cost.

🖥️ Compute Engine

Compute Engine provides virtual machines on Google’s infrastructure. You choose machine type, boot disk image (public OS images, custom images, or Container-Optimized OS), network tags, service account, and whether the VM is preemptible/Spot.

Core concepts

  • Instances — individual VMs (zonal).
  • Images — boot disk templates; use image families for rolling golden images.
  • Instance templates — reusable blueprints for MIGs.
  • Network tags — apply firewall rules without hard-coding IPs.
  • Metadata / startup scripts — bootstrap config (prefer OS Login + IaC over snowflake VMs).
  • Sole-tenant nodes — dedicated hardware for compliance isolation.

Pricing modes

  • On-demand — flexible, highest unit price.
  • Spot / preemptible — deep discount; can be reclaimed with notice.
  • Committed use discounts — 1- or 3-year commitments for steady baselines.
  • Sustained use — automatic discounts for long-running GCE usage in some cases (know current billing docs).
💡 EC2 parallel: Spot ≈ Spot/preemptible; Reserved Instances / Savings Plans ≈ CUDs (mechanics differ — read the commitment terms).

📈 Managed Instance Groups & Autoscaling

A Managed Instance Group (MIG) maintains a fleet of VMs from an instance template: auto-healing, rolling updates, and autoscaling.

Why MIGs matter

  • Autohealing — recreate unhealthy VMs based on health checks.
  • Autoscaling — CPU, load-balancing serving capacity, custom metrics, schedules.
  • Rolling updates — surge/unavailable controls for safe rollouts.
  • Regional MIGs — spread across zones for HA.
💡 AWS parallel: Auto Scaling Group + Launch Template ≈ MIG + instance template.

Use MIGs when

  • Stateless web/app tiers on VMs
  • You need zone redundancy
  • You want automated rollouts

Skip MIGs when

  • Single stateful snowflake (prefer redesign)
  • Workload belongs on Cloud Run/GKE instead

⚖️ Load Balancing with Compute

Compute Engine backends commonly sit behind Cloud Load Balancing:

  • Global external HTTP(S) — Anycast VIP, URL maps, SSL certs, Cloud CDN/Armor optional.
  • Regional external / internal — TCP/UDP passthrough or HTTP proxy for private services.
  • Backend services — attach MIGs, NEGs (for GKE/Cloud Run), health checks, session affinity.

Unlike stitching many regional ALBs + CloudFront, a single global HTTP(S) LB often covers multi-region frontend design. Details live in the Networking guide.

🏃 Cloud Run

Cloud Run runs stateless containers on a fully managed platform. Scale to zero. Pay when requests (or job tasks) run. Supports services (request-driven) and jobs (run-to-completion).

Key knobs

  • Concurrency — how many requests per instance (tune for CPU-bound vs IO-bound).
  • CPU allocation — CPU always allocated vs only during requests.
  • Min / max instances — fight cold starts; cap cost.
  • VPC connectors / Direct VPC egress — reach private IPs / Cloud SQL.
  • Service identity — dedicated runtime service account (least privilege).
  • Ingress — all / internal / internal-and-cloud-load-balancing.

When Cloud Run shines

  • APIs and webhooks with uneven traffic
  • Sidecar-free microservices that already build Docker images
  • Background jobs via Cloud Run jobs + Scheduler / Eventarc
💡 vs Lambda/Fargate: If you think “container + HTTP + scale to zero,” Cloud Run is often the first GCP answer — more than Cloud Functions.

⚡ Cloud Functions (2nd gen)

Cloud Functions 2nd gen deploys functions backed by Cloud Run. Triggers include HTTP, Pub/Sub, Cloud Storage, Firestore, and Eventarc sources.

TopicDetail
Timeouts Up to 60 minutes on 2nd gen (far beyond classic 1st gen limits)
Runtimes Node, Python, Go, Java, .NET, Ruby, PHP (check current list)
Networking Same VPC patterns as Cloud Run
Use when Small event handlers; team wants function DX over Dockerfile
Prefer Run when Custom container, sidecars-ish needs, or non-function packaging

🔄 Serverless Flow

Trigger → authenticated invoke → instance assign/scale → handler → response/logs → scale toward zero.

Operational checklist

  1. Use a dedicated service account; never the default compute SA for prod.
  2. Ship structured logs; correlate with Cloud Trace.
  3. Set max instances to protect downstream databases.
  4. Store secrets in Secret Manager; mount or access at runtime.
  5. Load-test cold starts if SLOs are tight; set min instances only when needed.

☸️ Google Kubernetes Engine (GKE)

GKE is Google’s managed Kubernetes. The control plane is Google’s responsibility. Node management depends on mode.

ModeNodesBest for
Standard You manage node pools Custom machine types, daemons, GPUs, fine control
Autopilot Google manages nodes Most microservices; pay per pod requests

GKE building blocks

  • Clusters (zonal/regional), node pools, release channels.
  • Workload Identity — map K8s SAs to IAM service accounts (prefer over JSON keys).
  • Binary Authorization — only signed images deploy.
  • GKE Gateway / Ingress — integrate with Cloud Load Balancing.
  • Anthos / multi-cluster patterns for hybrid (advanced).
💡 Don’t choose GKE for a single containerized API unless you already run Kubernetes. Cloud Run is less ops.

🧱 App Engine

App Engine is GCP’s original PaaS: Standard (sandboxed runtimes, rapid scale) and Flexible (containers on GCE under the hood).

  • Great for teams standardized on app.yaml workflows.
  • Newer greenfield HTTP services often pick Cloud Run instead for portability.
  • Still excellent when you want App Engine’s traffic splitting, versions, and runtime constraints.

📦 Batch

Batch schedules and runs batch jobs on Compute Engine resources (including Spot) without you writing a custom scheduler.

  • Define job resource requirements, parallel tasks, and retry policies.
  • Ideal for genomics-style pipelines, renders, large transforms.
  • AWS Batch analogue — same problem space.

💸 Ops & Cost

Practices that save money and outages

  • Prefer Cloud Run/GKE Autopilot when utilization is spiky.
  • Put steady VM baselines on CUDs; put flexible capacity on Spot.
  • Delete orphan disks, IPs, and idle load balancers.
  • Use committed GPUs only with measured utilization.
  • Align region with data — egress is a silent killer.

✅ Summary

Exam & interview quick reference

  • Default HTTP container: Cloud Run
  • Event function DX: Cloud Functions 2nd gen
  • Kubernetes: GKE (Autopilot unless you need node control)
  • VMs + HA: Regional MIG + global/regional LB
  • Ephemeral fast disk: Local SSD
  • Persistent boot/data: PD / Hyperdisk
  • EC2 ↔ GCE, Lambda ↔ Functions/Run, EKS ↔ GKE
  • Workload Identity over SA keys on GKE
