☁️ VPC Fundamentals

A Virtual Private Cloud (VPC) on GCP is a global software-defined network. Unlike AWS, where a VPC is regional, a GCP VPC spans all regions; you create regional subnets inside it. That single difference reshapes how you draw diagrams and share networks across teams.

GlobalVPC scope
RegionalSubnet scope
StatefulFirewall rules
AnycastGlobal HTTP(S) LB

Core VPC objects

  • VPC network — global container for subnets and routes.
  • Subnet — regional IP range (primary + optional secondary ranges for GKE/alias IPs).
  • Routes — system-generated + custom; define packet next hops.
  • Firewall rules — allow/deny based on tags, service accounts, or ranges.
  • Peering / Shared VPC / PSC — connect networks and managed services privately.
💡 AWS parallel: VPC ≈ VPC, but AWS VPC is regional. AWS AZ subnets ≈ GCP regional subnets spanning the region’s zones. Security groups ≈ firewall rules targeting tags/SAs (not identical).

Design defaults that work

  • One Shared VPC host for many service projects (enterprises)
  • Private VMs + Cloud NAT for egress
  • Global HTTP(S) LB for public HTTPS apps

Avoid

  • Flat 0.0.0.0/0 allow on SSH/RDP
  • Public IPs on every VM “for convenience”
  • Overlapping CIDRs before peering needs appear

🗺️ Subnets (Regional)

Subnets are regional: resources in any zone of that region can use the subnet. You can enable private Google access so VMs without public IPs reach Google APIs.

TopicDetail
Primary range VM primary NICs / primary pod routing as designed
Secondary ranges Alias IPs — critical for GKE pods/services
Auto vs custom mode Auto creates subnets per region; custom is preferred for production
Expansion You can expand subnet ranges carefully; plan CIDRs early

CIDR planning tips

  • Leave headroom for GKE secondary ranges.
  • Avoid ranges that collide with on-prem or partner networks.
  • Document allocations in a central IPAM sheet or product.

🔥 Firewall Rules

VPC firewall rules are stateful allow/deny rules evaluated on ingress/egress. Targets can be all instances, network tags, or service accounts.

Practical patterns

  • Prefer service account targets for identity-aware microsegmentation.
  • Use tags for coarse roles (web, data) when SAs are heavy-handed.
  • Implicit deny ingress; default egress allow — tighten egress when threats require it.
  • Priority numbers matter (lower number = higher priority).
  • Enable VPC Flow Logs on subnets that need forensics.
💡 vs Security Groups / NACLs: GCP firewall rules cover much of what AWS SGs do. Hierarchical Firewall Policies add org-level guardrails similar in spirit to centralized control.

📐 VPC Layout Illustration

Public HTTPS hits a global LB; backends live in private subnets; NAT handles egress; Interconnect/VPN reaches on-prem.

Reference layout

  1. Global external HTTP(S) load balancer + Cloud Armor.
  2. Backends: Cloud Run / GKE / MIGs in private subnets across zones.
  3. Cloud SQL / Memorystore on private IP via PSC or private services access.
  4. Cloud NAT + Cloud Router for controlled egress.
  5. Cloud VPN or Interconnect for hybrid.

🚪 Cloud NAT

Cloud NAT lets private VMs and private GKE nodes initiate outbound connections without public IPs. Pair with Cloud Router.

  • Choose automatic or manual NAT IP allocation; watch port exhaustion under high concurrency.
  • Logs help debug who talked outbound.
  • AWS NAT Gateway analogue (mechanics differ).

🛰️ Cloud Router

Cloud Router exchanges BGP routes for Cloud NAT, Cloud VPN, and Cloud Interconnect. It is the control-plane piece that keeps hybrid and dynamic NAT topologies alive.

  • Advertise custom IP ranges carefully.
  • Use dual routers / dual tunnels for HA VPN designs.

🔒 Private Google Access & Private Services

Options you’ll actually use

  • Private Google Access — VMs without public IPs reach googleapis.com / Restricted Google APIs.
  • Private Google Access for on-prem — via hybrid connectivity + DNS.
  • Private services access — allocated peering range for managed services (classic Cloud SQL private IP).
  • Private Service Connect (PSC) — consumer endpoints to producer services without VPC peering sprawl; preferred modern pattern.

🤝 VPC Peering, Shared VPC & PSC

PatternWhat it doesWhen
VPC Network Peering Connect two VPC networks (no transitive peering) Simple project-to-project private reachability
Shared VPC Host project owns network; service projects attach Central networking team + many app teams

💡 Enterprise default: Shared VPC for internal east-west; PSC for managed service consumption; minimize mesh peering.

⚖️ Cloud Load Balancing

GCP’s load balancing portfolio is a major differentiator: global external HTTP(S) uses Anycast to front backends in one or many regions.

TypeScopeUse
Global external HTTP(S) Global Web/API, URL maps, SSL, CDN, Armor
Regional external HTTP(S) Regional Region-scoped HTTP needs / proxy
TCP/UDP external passthrough Regional / global variants Non-HTTP, gaming, custom TCP
Internal HTTP(S) / passthrough Regional East-west microservices, internal VIPs
Proxy Network LB Regional / global options TLS/TCP proxy use cases

Building blocks

  • Forwarding rules, target proxies, URL maps.
  • Backend services + health checks + NEGs / MIGs / serverless NEGs.
  • Certificate Manager or classic SSL certs on HTTPS proxies.
💡 AWS mapping: ALB+CloudFront+sometimes Global Accelerator often collapse toward global HTTP(S) LB + Cloud CDN on GCP.

🧭 Cloud DNS

Managed authoritative DNS for public and private zones. Supports split views, peering of private zones, and routing policies.

  • Public zones for internet names (Route 53 public analogue).
  • Private zones visible inside specified VPCs.
  • Use DNS peering / forwarding for hybrid name resolution.

🌍 Cloud CDN (Brief)

Enable Cloud CDN on backend services behind the global external HTTP(S) load balancer to cache at the edge. Prefer versioned static assets; invalidate carefully. See the Storage guide for object-origin patterns.

🔗 Hybrid Connectivity

OptionCharacteristicsWhen
Cloud VPN (HA VPN) IPsec over internet; HA with dual tunnels Quick hybrid, moderate bandwidth
Dedicated Interconnect Physical circuits into Google High bandwidth, consistent latency
Partner Interconnect Via service provider When dedicated colo is impractical

Hybrid checklist

  • Non-overlapping CIDRs.
  • Redundant tunnels/circuits in separate failure domains.
  • Cloud Router BGP timers and advertisements understood by both sides.
  • DNS resolution strategy agreed (forwarding vs conditional).

🛡️ Cloud Armor

Cloud Armor attaches security policies to HTTP(S) load balancers: IP allow/deny, WAF rules, bot management, adaptive protection / DDoS-related controls.

  • AWS WAF + Shield-like capabilities in one policy surface (not a perfect 1:1).
  • Start with preview/logging before enforce mode on production traffic.
  • Combine with Identity-Aware Proxy when you need user identity at the edge for internal apps.

✅ Best Practices

Do this by default

  • Custom-mode VPC; planned CIDRs; Shared VPC for multi-team orgs.
  • No public IPs on backends; LB + NAT only where needed.
  • Firewall by service account; Hierarchical policies for org deny lists.
  • PSC for private service consumption.
  • Flow logs + Packet Mirroring selectively for incident response.
  • Global HTTP(S) LB for public web; don’t reinvent multi-region Anycast.

Exam & interview quick reference

  • VPC is global; subnets are regional
  • Firewall rules — stateful; tags or service accounts
  • Cloud NAT — egress without public IPs
  • Shared VPC — host + service projects
  • PSC — modern private service endpoints
  • Global HTTP(S) LB — Anycast frontend
  • Cloud Armor — WAF on HTTP(S) LB
  • HA VPN / Interconnect — hybrid paths
  • AWS VPC ↔ GCP VPC (scope differs)
