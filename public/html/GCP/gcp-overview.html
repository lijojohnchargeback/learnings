GCP Complete Overview

Google Cloud Platform — Compute, Data, AI & Global Infrastructure

1) Introduction to GCP

Google Cloud Platform (GCP) is a collection of on-demand building blocks. Instead of buying racks, power, and cooling, you request a virtual machine, an object bucket, a Kubernetes cluster, or a BigQuery dataset and pay for what you use. The platform grew out of Google’s internal infrastructure — the same networking, Borg-derived orchestration, and data systems that power Search, YouTube, and Gmail — and is now used by startups, governments, and enterprises for web apps, analytics, and machine learning.

One typical web app, named as real services. IAM decides who can call each hop. The VPC keeps compute and data off the public internet when you design it that way.

Walk the request, hop by hop

The diagram above is the mental model for the rest of this page. A user never “talks to GCP.” They talk to a name, then to an edge, then to a balancer, then to code, then to data.

  1. Users — a browser, mobile app, or API client issues HTTPS to a hostname such as app.example.com.
  2. Cloud DNS — authoritative DNS. It answers with a Cloud CDN or global load-balancer address. Health-based routing and geo policies are available when you need them.
  3. Cloud CDN — edge cache. Static assets (JS, images, video) should be answered near the user. Dynamic API calls can still enter Google’s network early via the global HTTP(S) load balancer.
  4. Cloud Load Balancing — global Anycast front end. It terminates TLS, matches host/path rules, and spreads traffic across healthy backends in one or many regions.
  5. Compute — the code. That might be Compute Engine VMs, GKE pods, Cloud Run services, Cloud Functions, or App Engine. Same job, different ops burden.
  6. Data — Cloud Storage for objects, Cloud SQL / Spanner for relational rows, Firestore or Bigtable for document/wide-column, BigQuery for analytics. Pick by access pattern, not by habit.

Two invisible layers wrap every hop: IAM (who is allowed to call the service) and a VPC (which packets can reach private subnets and Private Google Access). If those two are wrong, the pretty architecture still leaks or locks you out.

How to think about GCP

A toolkit built on Google’s network

Every GCP service solves one job: run code, store files, move packets, encrypt secrets, or train models. You compose those jobs into an architecture. A typical web app uses Cloud DNS, Cloud CDN / global HTTP(S) LB, Cloud Storage, Cloud Run or GKE, Cloud SQL or Firestore, and IAM.

GCP’s differentiators show up early: a software-defined global network with Anycast load balancing, BigQuery as a default analytics engine, and Vertex AI as a unified ML surface. The rest of this page is organized the way architects think: infrastructure first, then hierarchy and identity, then compute/storage/data, then delivery and operations.

Choose GCP when you need

  • Global HTTP(S) load balancing without stitching regional balancers
  • Analytics and ML (BigQuery, Vertex AI, Dataflow)
  • Managed Kubernetes (GKE) as a first-class product
  • Strong data analytics + Google Workspace / identity integrations

Think twice when

  • A single small VPS would be simpler and cheaper
  • You cannot invest in IAM, billing accounts, and project hygiene
  • Compliance forces a cloud or region you do not have
  • The team has no operations capacity yet

What is GCP?

Google Cloud Platform is Google’s public cloud: IaaS, PaaS, serverless, data, and AI services exposed through the Cloud Console, gcloud CLI, client libraries, and Terraform.

Key facts

  • ☁️ Roots: Public services from ~2008 (App Engine); Compute Engine GA in 2013
  • 📦 Products: 100+ services spanning compute, storage, networking, data, and AI
  • 🌍 Reach: 40+ regions, 120+ zones, plus edge POPs for CDN and media
  • 🏆 Strengths: Data analytics, ML, Kubernetes, global networking
  • 💼 Used by: Spotify, Twitter/X (historically), Snap, Shopify, and many enterprises
  • 🔒 Compliance: Broad portfolio (ISO, SOC, HIPAA, PCI, FedRAMP where applicable)
💡 GCP vs “Google”: Gmail and Drive are Google Workspace. GCP is the developer/ops cloud: projects, billing accounts, VPCs, and APIs. They share Google identity patterns, but your production workloads live in GCP projects.

AWS comparison callout

If you know AWS, map the mental model — then learn the differences that matter:

  • Account ≈ Project for day-to-day resource isolation (with Org/Folders above).
  • EC2 ≈ Compute Engine, S3 ≈ Cloud Storage, IAM ≈ IAM (policy language differs).
  • Lambda ≈ Cloud Functions; long-running containers often land on Cloud Run (closer to a mix of Lambda + Fargate for HTTP).
  • EKS ≈ GKE; GKE Autopilot reduces node management further.
  • Regional ALBs + CloudFront often collapse into global external HTTP(S) LB + Cloud CDN on GCP.

2) Global Infrastructure

Regions hold zones. Zones are isolated failure domains. Edge locations terminate CDN and media traffic closer to users.

GCP’s physical footprint is organized as regions, zones, and edge points of presence. Understanding this hierarchy is the foundation of high availability and latency design.

Regions

A region is a geographic area (for example us-central1, europe-west1, asia-south1). Pick regions for:

  • Latency — put compute near users and data near compute.
  • Data residency — legal requirements for where data may live.
  • Service availability — not every product launches in every region on day one.
  • Price — some regions are cheaper for the same SKU.

Zones

A zone is an isolated deployment area inside a region (us-central1-a, us-central1-b, …). Zones have independent power, cooling, and networking failure domains.

  • Spread Managed Instance Groups and GKE node pools across zones.
  • Regional Persistent Disks and multi-zone MIGs survive a single-zone outage.
  • Zonal resources (many VMs, zonal disks) die with their zone — design accordingly.
💡 Common mistake: Deploying everything in one zone “because it’s cheaper to think about,” then discovering a maintenance event takes the whole app offline.

Edge / Points of Presence

Google’s edge network terminates Cloud CDN, Media CDN, and global load-balancing Anycast IPs. Users hit the nearest edge; traffic then rides Google’s backbone toward your backends. That is why a single global external HTTP(S) load balancer can front backends in multiple regions without you operating a separate CDN product for basic cases.

ConceptGCPAWS analogueDesign tip
Region us-central1 us-east-1 Choose for latency + residency

Use multi-zone when

  • You need zone-level HA for VMs or GKE
  • RTO cannot wait for a full rebuild
  • Load balancers can health-check across zones

Multi-region only when

  • You truly need cross-region failover or global data
  • You accept higher cost and consistency tradeoffs
  • You have tested failover — not just drawn it

3) Resource Hierarchy

GCP organizes resources in a tree: Organization → Folders → Projects → Resources. Billing attaches via billing accounts. Get this wrong and IAM, quotas, and cost allocation become chaos.

Organization

The Organization resource is the root, usually tied to a Cloud Identity / Google Workspace domain. Organization Policy Service sets guardrails (allowed regions, disable public IPs, restrict SA key creation).

Folders

Folders group projects by business unit, environment, or compliance boundary. IAM bindings and org policies inherit downward. Typical pattern: Company / Engineering / prod and Company / Engineering / nonprod.

Projects

A project is the primary unit of isolation, quota, and enablement. APIs are enabled per project. Most resources (VMs, buckets, datasets) live in a project. Think of a project as closer to an AWS account than to an AWS “project tag.”

  • One app / one environment per project is a common enterprise pattern.
  • Shared VPC host projects own the network; service projects attach.
  • Project IDs are globally unique strings; project numbers are numeric IDs used by APIs.

Billing accounts

Billing accounts pay for one or more projects. Use labels and folders for chargeback. Budgets and anomaly alerts live at the billing-account or project level. Never put production spend on a personal credit card without budgets.

💡 Inherited IAM: A role granted on the org or folder applies to all child projects unless you carefully constrain with conditions. Audit inheritance before granting roles/owner high in the tree.
LevelPurposeTypical owners
Organization Root policies, domain binding Cloud admins / security
Folder Delegation, environment grouping Platform / BU leads
Project APIs, quotas, resources App / platform teams
Billing account Payment, budgets FinOps / finance

4) Shared Responsibility

Google secures the cloud: data centers, hardware, hypervisor, and the managed service control plane. You secure in the cloud. The line moves with the service model.

Where the line sits

  • IaaS (Compute Engine, VPC, Persistent Disk): you patch the OS (unless using container-optimized / managed images carefully), configure firewall rules, encrypt disks, and rotate keys. Google keeps the building and hypervisor healthy.
  • PaaS / containers (GKE standard nodes, Cloud SQL): Google patches much of the platform. You still design schemas, IAM, backups, network placement, and (on GKE standard) node security.
  • Serverless (Cloud Run, Cloud Functions, BigQuery, Cloud Storage): you do not SSH anywhere. You still own identity, encryption settings, bucket IAM, and the data you store.
💡 Production fails here: “GCP is secure” is not a control. MFA on privileged users, no public buckets by accident, firewall rules that are not 0.0.0.0/0 on SSH, CMEK where required, and audit logs you actually read — those are controls.

6) Compute Snapshot

From VMs to functions: pick by how long work lives and how much of the stack you want to own.

GCP compute spans IaaS through fully managed serverless:

  • Compute Engine — VMs with custom machine types, MIGs, GPUs. Closest to EC2.
  • Google Kubernetes Engine (GKE) — managed Kubernetes; Autopilot mode manages nodes for you.
  • Cloud Run — container-based serverless HTTP/async services. Scale to zero. Often the default for new APIs.
  • Cloud Functions (2nd gen) — event-driven functions built on Cloud Run under the hood.
  • App Engine — PaaS with standard and flexible environments; still strong for certain Google-centric stacks.
  • Batch — managed batch/HPC-style job scheduling on Compute Engine capacity.

Default picks

  • HTTP microservice → Cloud Run
  • Event glue / webhooks → Cloud Functions
  • K8s platform / multi-service mesh → GKE
  • Custom OS / GPU / long-lived → Compute Engine

Common mistakes

  • Choosing GKE before the team can operate Kubernetes
  • Leaving idle VMs without committed use discounts or autoscaling
  • Forcing everything into Functions when Cloud Run fits better

8) Networking Snapshot

VPCs are global; subnets are regional. Firewall rules and Cloud Armor sit on the path to backends.
  • VPC — global private network; subnets are regional (unlike AWS AZ-scoped subnets).
  • Firewall rules — stateful allow/deny at VPC level (think security groups + more).
  • Cloud Load Balancing — global and regional HTTP(S), TCP/UDP, internal passthrough and proxy.
  • Cloud NAT / Cloud Router — egress without public IPs; dynamic routing for hybrid.
  • Private Google Access / PSC — reach Google APIs and services without public IPs.
  • Cloud Interconnect / Cloud VPN — hybrid connectivity.
  • Cloud Armor — WAF / DDoS policies on HTTP(S) LBs (Shield-ish + WAF-ish).

Deep dive: Networking guide in this category.

9) Databases

Pick databases by consistency needs, scale shape, and operational appetite — not by which logo is trending.

ServiceModelBest forWatch-outs

Firestore Document (Native / Datastore mode) Mobile/web apps, real-time sync Query limitations; composite indexes
Bigtable Wide-column NoSQL High throughput time-series / analytics ops Row-key design is everything
Memorystore Redis / Memcached Cache, sessions, low-latency state Not a system of record

AWS mapping (databases)

  • RDS / Aurora → Cloud SQL (Aurora-like global SQL → often Spanner)
  • DynamoDB → Firestore (document) or Bigtable (wide-column / massive throughput)
  • ElastiCache → Memorystore

Start with Cloud SQL when

  • You already have Postgres/MySQL schemas
  • Traffic fits a managed primary + replicas
  • Team knows relational ops

Reach for Spanner when

  • You need multi-region strong consistency
  • Horizontal write scale is a hard requirement
  • You accept Spanner’s pricing and constraints

10) BigQuery & Analytics

BigQuery is GCP’s serverless data warehouse: SQL over columnar storage, separated compute (slots) and storage, with streaming inserts, scheduled queries, BI Engine, and tight links to Looker, Dataflow, and Vertex AI.

Analytics building blocks

  • Pub/Sub — durable messaging / event ingestion (SQS + SNS-ish, with streaming DNA).
  • Dataflow — managed Apache Beam (batch + stream).
  • Dataproc — managed Spark / Hadoop when you need that ecosystem.
  • BigQuery — warehouse / lakehouse SQL.
  • Looker / Looker Studio — BI and governed metrics.
💡 Cost tip: BigQuery charges for bytes scanned (on-demand) or slots (capacity). Partition and cluster tables. Avoid SELECT * on multi-TB fact tables in dashboards.

11) AI / ML — Vertex AI

Vertex AI is the unified ML platform: datasets, training (custom and AutoML), Feature Store, Model Registry, prediction endpoints, pipelines, and generative AI (Gemini and model garden) under one governance model.

What teams actually use

  • Gemini / generative APIs — for assistants, summarization, code, multimodal.
  • Vertex Prediction — host custom containers or frameworks.
  • Vertex Pipelines — Kubeflow-style MLOps.
  • Specialized APIs — Vision, Speech-to-Text, Translation, Natural Language when a turnkey API beats a custom model.

Compared with AWS: SageMaker ≈ much of Vertex training/hosting; Bedrock-like generative access appears via Vertex Model Garden / Gemini APIs.

Prefer serverless when

  • Traffic is spiky or idle most of the day
  • Work is event-shaped (upload, queue, cron, webhook)
  • The team is small and does not want node pools

Stay on GCE / GKE when

  • You need GPUs, sidecars, or complex networking
  • Processes must stay warm with large memory for hours
  • Utilization is high enough that reserved VMs win on cost

13) DevOps — Build, Deploy, Artifacts

  • Cloud Build — CI pipelines as code (build, test, push images). Analogy: CodeBuild + bits of CodePipeline.
  • Artifact Registry — container images, language packages, and more (successor to Container Registry).
  • Cloud Deploy — managed continuous delivery to GKE, Cloud Run, and Anthos targets with release promotions.
  • Infrastructure as Code — official Terraform providers; Config Connector / infra from Kubernetes; Deployment Manager legacy.

Minimal delivery path

  1. Commit to Git (GitHub, GitLab, Cloud Source Repositories).
  2. Cloud Build builds and pushes to Artifact Registry.
  3. Cloud Deploy (or Cloud Build deploy step) rolls out to Cloud Run / GKE.
  4. Cloud Monitoring alerts on SLOs; Error Reporting catches crashes.

15) Cost & Pricing Models

GCP pricing mixes pay-as-you-go, committed use discounts (CUDs), sustained use discounts (on some GCE), spot/preemptible VMs, and flat or capacity pricing (BigQuery editions/slots).

Levers that actually move the bill

  • Rightsizing — custom machine types; don’t buy 16 vCPU for a 2-vCPU app.
  • Committed use — 1- or 3-year CUDs for steady GCE/GKE baselines.
  • Spot VMs — fault-tolerant batch and stateless MIGs.
  • Egress awareness — internet and cross-region egress add up; design data locality.
  • BigQuery hygiene — partition/cluster; prefer capacity for steady warehouses.
  • Labels + budgets — every resource labeled; budget alerts before the CFO calls.

16) Getting Started Practically

First week checklist

  1. Create (or join) a Cloud Identity / Google account tied to a billing account.
  2. Create a nonprod project; enable only the APIs you need (Compute, Storage, Run, Logging).
  3. Install gcloud; run gcloud auth login and gcloud config set project ….
  4. Deploy a hello-world to Cloud Run from a container or source.
  5. Put a private bucket in the same region; grant the Cloud Run SA roles/storage.objectViewer only.
  6. Create a budget alert at 50% / 90% of a small monthly cap.
  7. Turn on Essential Contacts and ensure Admin Activity audit logs flow to a sink you control.

Useful gcloud mental model

  • gcloud services enable … — APIs are per project; forgotten enables cause mysterious 403s.
  • gcloud iam … / Console IAM — bindings, not AWS-style JSON identity policies.
  • gcloud run deploy — fastest path from container to HTTPS URL.
  • gcloud compute … — VMs, MIGs, disks, firewalls.
  • Prefer Terraform for anything that must survive beyond a demo.
💡 Identity tip: Use Google groups for humans and dedicated service accounts for workloads. Never share a personal user as the runtime identity for production.

Three starter architectures

  • Static + API: Cloud Storage + Cloud CDN for frontend; Cloud Run for API; Cloud SQL private IP via PSC connector.
  • Event pipeline: GCS land → Pub/Sub → Dataflow → BigQuery; alerting via Cloud Monitoring.
  • Platform: Shared VPC host; GKE Autopilot service projects; Artifact Registry; Cloud Deploy promotions prod←staging.

17) Best Practices

Architecture

  • Prefer regional HA (multi-zone) before jumping to multi-region.
  • Start at the highest compute abstraction that fits (Cloud Run → GKE → GCE).
  • Keep secrets in Secret Manager; never in images or env vars checked into git.
  • Use least-privilege IAM; prefer service accounts per workload over shared “god” SAs.
  • Enable VPC Flow Logs and Cloud Audit Logs for production projects.

Organization hygiene

  • Separate prod / nonprod projects (and preferably folders).
  • Enforce org policies: restrict public IPs, constrain resource locations, disable SA key creation when possible.
  • Centralize networking with Shared VPC if many teams ship services.
  • Require MFA / security keys for privileged Google identities.

Common mistakes

  • One giant project for everything — blast radius and IAM hell.
  • Public Cloud Storage buckets “just for testing” that never get locked down.
  • Long-lived service account JSON keys on laptops.
  • No budgets — surprise bills from egress, BigQuery scans, or forgotten GPUs.
  • Copying an AWS diagram literally without adapting to global VPC / global LB strengths.

19) Summary

Takeaways

  • GCP is a full public cloud with distinctive strength in global networking, Kubernetes, analytics, and AI.
  • Learn the hierarchy: org → folder → project → resources, with billing accounts attached.
  • Compose architectures from VPC + IAM + compute + data; start managed (Cloud Run, Cloud SQL, Cloud Storage, BigQuery).
  • Use the AWS mapping as a bridge, then re-learn defaults (global VPC, global LB, IAM bindings).
  • Shared responsibility never disappears — identity, data, and configuration remain yours.
