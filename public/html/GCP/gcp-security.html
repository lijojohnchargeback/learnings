🔒 GCP Security

Complete Guide to IAM, Encryption, Detection & Best Practices

🎯 Security Overview

GCP security is not a single product. It is IAM for who can do what, network controls for who can talk to what, encryption for data at rest and in transit, and detection products for when something slips. AWS veterans will recognize the shapes — IAM, KMS, Secrets Manager, WAF, GuardDuty-like findings — but the binding model and org-policy toolkit are distinctly Google Cloud.

IAMWho × can do × what
Org policyGuardrails
CMEKCustomer keys

Security baseline

  • MFA / security keys for humans
  • Least-privilege roles; no primitive roles in prod
  • No long-lived SA JSON keys when WI/WIF works
  • Org policies restricting public IPs and public buckets

Smell tests

  • roles/owner on folders for convenience
  • Shared “deploy” SA across all apps
  • Secrets in source control or disk images
  • Audit logs disabled or never reviewed

👤 IAM Basics

GCP IAM answers: who (principal) can do what (role / permissions) on which resource (binding), optionally under what conditions.

ConceptMeaningAWS rough analogue
Principal User, group, service account, domain, workforce/workforce federation identities IAM user/role principal
Role Bundle of permissions (basic, predefined, custom) Managed / custom policies attached as permissions sets
Binding Role ↔ members on a resource Policy statement attachment
Condition CEL expression limiting when binding applies IAM condition keys
Policy Collection of bindings on a resource Resource-based / identity policies (different structure)

Role types

  • Basic (primitive): Owner, Editor, Viewer — too coarse for production app access.
  • Predefined: curated jobs like roles/run.developer, roles/storage.objectViewer.
  • Custom: least privilege when predefined is still too wide.
💡 Inheritance: Bindings on org/folder/project inherit downward. A folder-level Editor is Editor on every child project — treat high-tree grants as radioactive.

IAM Conditions (examples)

  • Allow access only from specific IP ranges.
  • Allow a role only during a change window.
  • Limit to resources with certain tags / attributes where supported.

🔄 IAM Flow Illustration

Principal presents credentials → Resource Manager finds applicable policies → roles expand to permissions → allow or deny the API call.

Walk an API call

  1. A Cloud Run service uses its runtime service account.
  2. It calls storage.objects.get on a bucket.
  3. IAM collects bindings from org → folder → project → bucket.
  4. If any binding grants a role containing that permission (and conditions pass), the call succeeds.
  5. Cloud Audit Logs records the access (when data access logs are enabled for the service).

🤖 Service Accounts

Service accounts are non-human identities for applications and VMs. Each should represent one workload or function.

Hard rules

  • One SA per application / environment — never a company-wide “god” SA.
  • Prefer attached SA on GCE/GKE/Cloud Run over downloaded JSON keys.
  • If keys are unavoidable, rotate, restrict with org policy, and monitor key usage.
  • Disable automatic reliance on the default Compute Engine SA in new projects when you can.
  • Grant roles on the resources needed, not roles/editor on the project.
💡 AWS parallel: Instance profiles / task roles ≈ attaching a service account to a runtime. Long-lived access keys ≈ SA JSON keys (both are smellful).

🔗 Workload Identity

FlavorPurpose
Workload Identity (GKE) Map Kubernetes service accounts to IAM service accounts — no node JSON keys
Workload Identity Federation Exchange external IdP tokens (AWS, Azure AD, GitHub OIDC, etc.) for short-lived GCP credentials

Federation kills the “CI pipeline stores a GCP key forever” anti-pattern. GitHub Actions → WIF → deploy to Cloud Run is a modern default.

🏛️ Organization Policies

Organization Policy Service sets guardrails inherited down the resource hierarchy — independent of who has IAM roles.

High-value constraints

  • Restrict resource locations (data residency).
  • Disable service account key creation.
  • Restrict public IP creation on VMs.
  • Enforce uniform bucket-level access / prevent public buckets.
  • Require OS Login; disable legacy metadata SSH keys.
  • Domain-restricted sharing for Cloud Storage / BigQuery.
💡 Think: IAM says what a principal may do. Org policy says what the organization allows to exist, even for Owners.

📁 Resource Manager

Resource Manager APIs govern organizations, folders, projects, and liens. Security teams use them to:

  • Structure blast-radius boundaries (prod vs nonprod folders).
  • Apply IAM and org policies at the right altitude.
  • Prevent accidental project deletion with liens.
  • Inventory projects for shadow IT.

🤝 Shared Responsibility

You still own

  • Identity lifecycle, MFA, and access reviews.
  • Firewall rules, public exposure, and Shared VPC hygiene.
  • Encryption settings (CMEK), secret storage, and key rotation policies.
  • Patching guest OS on GCE (unless using managed runtimes).
  • Application vulnerabilities and dependency risk.
  • Log retention, monitoring, and incident response playbooks.

Google owns physical security, hypervisor, and the managed control planes. “We are on GCP” is never the control narrative in an audit.

🔐 Secret Manager

Store API keys, passwords, and certificates as versioned secrets with IAM on each secret.

  • Pin or alias versions (latest carefully in prod).
  • Rotate by adding versions; update consumers; disable old versions.
  • Audit access; prefer CMEK for sensitive secrets.
  • AWS Secrets Manager analogue (Parameter Store-ish overlap too).

🗝️ Cloud KMS & Cloud HSM

OptionDetail
Cloud KMS Hosted key management; symmetric/asymmetric keys; CMEK integrations across GCS, BigQuery, PD, etc.
Cloud HSM FIPS 140-2 Level 3 HSM-backed keys for higher assurance
EKM External key manager patterns for keys outside Google

CMEK practice

  • Separate key rings per environment; limit cryptoKeyEncrypterDecrypter.
  • Turn on key rotation schedules where supported.
  • Remember: destroying keys can destroy data access — governance required.

📜 Certificate Manager

Manage SSL/TLS certificates for load balancers at scale: Google-managed certs, DNS authorizations, and maps for many hostnames.

  • Prefer Google-managed certs when DNS can be validated automatically.
  • Use Certificate Manager maps instead of per-proxy classic cert sprawl.

📡 Security Command Center

Security Command Center (SCC) centralizes security findings across assets: misconfigurations, vulnerabilities, threats.

  • Standard / Premium tiers unlock deeper detectors and compliance reporting.
  • Integrate findings into ticketing / SIEM via Pub/Sub exports.
  • Closest portfolio analogue to Security Hub + bits of GuardDuty/Inspector findings aggregation.

🧱 VPC Service Controls

VPC Service Controls create security perimeters around Google-managed services (GCS, BigQuery, etc.) to mitigate data exfiltration — even by principals who have IAM permission but are outside the perimeter context.

  • Essential for sensitive data platforms on GCP.
  • Requires careful dry-run mode — easy to break legitimate analytics pipelines.
  • Complements, does not replace, IAM.

🛡️ Cloud Armor

Edge WAF / Layer 7 filtering on HTTP(S) load balancers: IP rules, preconfigured WAF signatures, rate limiting, bot management, adaptive protection.

  • Deploy in preview → log → enforce.
  • Pair with global LB for internet-facing apps.
  • AWS WAF / Shield conceptual overlap.

📦 Binary Authorization

Enforce that only trusted, signed container images deploy to GKE (and supported Cloud Run configurations).

  • Attestors sign images after CI policy checks.
  • Breakglass procedures for incidents — document them.
  • Pairs with Artifact Analysis / vulnerability scanning.

📝 Audit Logs

TypeContentsNotes
Admin Activity Config changes On by default; retain carefully
Data Access Reads/writes of user data Enable where compliance needs; can be high volume
System Event Google-generated system events Infrastructure happenings
Policy Denied VPC SC / policy denials Gold for perimeter debugging
💡 Forensics tip: Export audit logs to a dedicated logging project/bucket with immutable retention. Don’t keep your only copy in the same project an attacker can edit.

✅ Best Practices

Identity

  • Google groups for humans; bind groups to roles, not individuals, when possible.
  • Security keys / phishing-resistant MFA for admins.
  • Regular access reviews; remove Editor/Owner sprawl.

Workload

  • Workload Identity / WIF everywhere practical.
  • Secret Manager + CMEK for sensitive material.
  • Binary Authorization on production GKE.
  • Private networking + Cloud Armor on public HTTP.

Governance

  • Org policies before the first public bucket incident.
  • SCC Premium (or equivalent tooling) with owned SLAs on findings.
  • VPC SC for regulated data domains.
  • Separate prod/nonprod; separate break-glass accounts.

  • SCC for centralized findings
  • VPC SC against exfiltration from managed services
