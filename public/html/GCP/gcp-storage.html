Complete Guide to Persistent Disk, Filestore, Cloud Storage, CDN & More

📦 Storage Types

Storage underpins every cloud architecture. GCP offers three primary models: block, file, and object. Pick by access pattern — random disk I/O, shared POSIX filesystem, or HTTP-addressable objects — not by which service launched first.

Block for boot/data disks, Filestore for shared NFS, Cloud Storage for objects and lakes.

Choose quickly

  • Boot disk / DB data dir on one VM → PD / Hyperdisk
  • Many VMs need same POSIX files → Filestore
  • Images, backups, lake files, static site → Cloud Storage

Common mistakes

  • Using GCS like a disk (high-churn random writes)
  • Storing critical state only on Local SSD
  • Public buckets left open after a demo

🧭 Decision Guide

Questions to ask

  1. Does the app need a block device (/dev/sdX)? → PD/Hyperdisk/Local SSD.
  2. Do multiple instances need a shared directory tree? → Filestore.
  3. Is access via HTTPS/API with eventual-ish large-object semantics OK? → Cloud Storage.
  4. Is latency measured in microseconds for scratch space? → Local SSD (accept ephemerality).

💿 Persistent Disk

Persistent Disk (PD) is durable network block storage for Compute Engine and GKE. Disks outlive VM terminate/stop (unless deleted with the instance).

TypeProfileTypical use
pd-standard HDD-backed, cheaper Bulk cold data, sequential workloads
pd-balanced Cost/performance SSD balance Most general boot + data disks
pd-ssd Higher IOPS/throughput Databases, I/O heavy apps
pd-extreme Provisioned high performance (where offered) Demanding enterprise DBs

Operational facts

  • Zonal vs regional: regional PD replicates across two zones for HA of the disk itself.
  • Snapshots: incremental, stored in Cloud Storage under the hood; schedule and test restores.
  • Resize: grow disks online; plan filesystem growth (ext4/xfs tools).
  • Encryption: encrypted at rest by default; CMEK optional via Cloud KMS.
  • Attach limits: know per-VM disk count and IOPS caps for your machine type.
💡 AWS parallel: EBS gp3/io2 ≈ pd-balanced/pd-ssd/extreme territory; EBS snapshots ≈ PD snapshots.

🚀 Hyperdisk

Hyperdisk is Google’s next-generation block storage with more flexible provisioning of IOPS and throughput on supported machine series.

  • Choose Hyperdisk variants ( Balancer, Extreme, Throughput, ML, etc. as catalogued) based on workload.
  • Decouple capacity from performance more cleanly than classic PD tiers.
  • Confirm machine-type compatibility before designing around Hyperdisk.
💡 Migration path: New high-I/O designs should evaluate Hyperdisk first; existing PD remains fully valid.

⚡ Local SSD

Local SSDs are physically attached to the host — extremely high IOPS and low latency, but ephemeral.

  • Data is lost on stop, terminate, or host maintenance migration (unless using features that preserve in narrow cases — design as ephemeral).
  • Ideal for caches, scratch, well-replicated databases (e.g. local scratch with replication).
  • AWS Instance Store analogue.

Use Local SSD when

  • Scratch space for ETL / ML feature materialization
  • Distributed DB that replicates its own data
  • Cache tiers you can rebuild

Never use alone when

  • It is the only copy of customer data
  • You cannot tolerate rebuild after preemption

📁 Filestore

Filestore provides managed NFS file shares for GCE, GKE, and on-prem clients over VPN/Interconnect.

TopicDetail
Protocol NFSv3 / NFSv4.1 (tier dependent)
Tiers Basic, Enterprise, High Scale — capacity & performance bands
Use cases Lift-and-shift apps needing shared files, CMS, home dirs, HPC shared data
AWS analogue EFS (Linux NFS); FSx covers other protocols GCP Filestore does not
💡 Design tip: If you only need object semantics, prefer Cloud Storage — cheaper and simpler than operating a file share.

🗄️ Cloud Storage (GCS)

Cloud Storage is GCP’s object store: buckets hold objects addressed by key. It underpins static assets, backups, data lakes, BigQuery external tables, and many pipeline landings.

Object storage mindset

Blobs with metadata, not a filesystem

There are no true directories — only key prefixes. List operations and rename patterns differ from POSIX. Design keys for listing locality and lifecycle rules.

Durability is extreme by design; availability depends on location type (regional vs dual/multi-region) and your access path (CDN, signed URLs, Private Google Access).

Bucket location choices

  • Region — lowest latency to compute in that region; good default for apps.
  • Dual-region — geo-redundant within a geo pair for higher availability.
  • Multi-region — broader geo redundancy for content serving across a continent.
💡 AWS parallel: S3 ≈ Cloud Storage. Bucket policies ≈ IAM + bucket IAM. Storage classes ≈ GCS classes. CloudFront ≈ Cloud CDN.

🌡️ Storage Classes

ClassAccess patternNotes
Standard Frequent Hot data, websites, streaming ingest
Nearline ~monthly Backups, lightly touched analytics
Coldline ~quarterly Disaster recovery, colder archives
Archive yearly / rare Lowest storage price; higher retrieval cost/latency

Autoclass can automatically move objects between classes based on observed access — useful when patterns are unknown. Always model retrieval fees before bulk-restoring cold data.

🕘 Versioning & Lifecycle

Object versioning

Enable versioning to retain noncurrent versions on overwrite/delete. Pair with lifecycle rules or you will pay for forever-growing version piles.

Lifecycle examples

  • Transition to Nearline after 30 days, Coldline after 90, Archive after 365.
  • Delete noncurrent versions older than N days.
  • Expire incomplete multipart uploads.
  • Abort abandoned resumable uploads.

Soft delete / retention

  • Bucket soft-delete windows recover accidentally deleted objects.
  • Retention policies and Bucket Lock support compliance holds (know legal implications — locks can be irreversible).

🔐 IAM, ACLs & Signed URLs

MechanismUseGuidance
Uniform bucket-level IAM All objects inherit bucket IAM Prefer for new buckets
Fine-grained ACLs Per-object ACLs Legacy; harder to audit
Signed URLs Time-limited access without Google account Uploads/downloads for end users
Signed Policy Documents Constrained browser uploads Limit size/prefix/content-type

Security checklist

  • Prevent public allUsers grants unless the bucket is intentionally public static content.
  • Use org policies to restrict public access.
  • Encrypt with CMEK when required; default Google-managed encryption otherwise.
  • Log data access for sensitive buckets.
  • Prefer Uniform access + IAM Conditions over sprawling ACLs.

🌐 Cloud CDN

Cloud CDN caches HTTP(S) content at Google’s edge, typically in front of Cloud Storage backends or compute backends via the global external HTTP(S) load balancer.

  • Configure cache modes, TTLs, and negative caching carefully.
  • Invalidate sparingly — prefer versioned object names (app.abc123.js).
  • Media CDN exists for large streaming / video-scale catalogs.
  • AWS CloudFront analogue.

🚚 Transfer Service

Move data into Cloud Storage without writing one-off copy scripts:

  • Storage Transfer Service — from S3, HTTP/HTTPS, or another GCS bucket on schedules.
  • Transfer Appliance — physical appliance for multi-hundred-TB / PB offline migration.
  • gsutil / gcloud storage — ad hoc and scripted copies; use parallel composite uploads wisely.
💡 Migration tip: Validate checksums, plan bandwidth, and freeze writes or use sync strategies so cutover does not lose late mutations.

✅ Best Practices

Architecture

  • Colocate buckets with compute to cut egress and latency.
  • Use lifecycle + Autoclass deliberately; monitor class transition costs.
  • Version keys for static assets; put Cloud CDN in front.
  • Separate buckets by sensitivity and environment (prod logs ≠ public assets).
  • For databases, snapshot PD/Hyperdisk; don’t pretend GCS is a block device.

Exam & interview quick reference

  • S3 ↔ Cloud Storage
  • EBS ↔ Persistent Disk / Hyperdisk
  • Instance Store ↔ Local SSD
  • EFS ↔ Filestore
  • Prefer uniform bucket IAM
  • Standard / Nearline / Coldline / Archive classes
  • Signed URLs for temporary access
  • Cloud CDN on global HTTP(S) LB
