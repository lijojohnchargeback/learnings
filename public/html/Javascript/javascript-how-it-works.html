⚙️ How JavaScript Works

The engine, the heap, the call stack, and the event loop — what actually happens when your code runs.

🗺️ The Big Picture

JavaScript does not “just run.” A runtime — the browser, or Node.js — hosts an engine that executes your code, plus extra machinery for timers, the DOM, the network, and a scheduler called the event loop.

Engine
Runs your JavaScript

Parses source, allocates memory, and executes line by line. V8 in Chrome/Node, SpiderMonkey in Firefox, JavaScriptCore in Safari.

Runtime
Gives JS a world

Web APIs (setTimeout, DOM, fetch) or Node APIs (fs, http). The engine alone cannot talk to the network or the page.

Event loop
Decides what runs next

When the call stack is empty, it pulls the next job from a queue. That is how async work comes back.

Engine on the left. Host APIs on the right. Queues at the bottom. The event loop is the traffic cop between them.

Synchronous work

Lives on the call stack. A function runs to completion. Nothing else in your JavaScript can interleave until it returns.

Asynchronous work

Is handed to a host API. When that work finishes, a callback is queued. The event loop only runs it after the stack is clear.

The rule this whole page uses

JavaScript is single-threaded for your code. One call stack. One thing executing at a time. Concurrency comes from the runtime (queues + host APIs), not from two JS functions running in parallel on the same stack.

🧵 One Thread

People say “JavaScript is single-threaded.” That means: your JavaScript shares one call stack. It does not mean the browser or Node process has only one OS thread.

Wrong: setTimeout or fetch creates a second JavaScript thread that runs beside your code.
Right: the host does the waiting. When it is done, a function is scheduled. Your JS still runs one function at a time.

Why this design exists

  • The browser UI and the DOM are shared. Two JS threads mutating the same page would need locks everywhere.
  • A long synchronous loop still blocks rendering and input — because it never empties the stack, so the event loop cannot run.
  • True parallelism in JS is opt-in: Worker in the browser, worker_threads in Node. Those are other JS engines with their own stacks.
// This freezes the page. The stack never empties. const start = Date.now(); while (Date.now() - start < 5000) { // busy-wait for 5 seconds } console.log("UI was frozen the whole time");

🏭 The JavaScript Engine

An engine turns source text into something a CPU can run. Chrome and Node.js use V8. You do not need every V8 name, but the pipeline is the mental model:

Source.js text
→
Parsetokens + AST
→
Interpretbytecode
→
Profilehot functions
→
JIT compilemachine code
Cold code is interpreted. Functions that run a lot get optimized. If assumptions break, the engine deoptimizes and falls back.
  1. Lexing / parsing. The source is split into tokens, then built into an Abstract Syntax Tree (AST) — a tree of “this is a function, this is an if, this is a call.”
  2. Interpretation. V8’s Ignition walks the AST and produces bytecode. That starts running quickly. You do not wait for a full compile of the whole file.
  3. Profiling. While bytecode runs, the engine watches which functions are “hot” (called often, or sit in a tight loop).
  4. JIT (TurboFan). Hot functions are compiled to optimized machine code. Types seen so far are assumed to stay stable.
  5. Deoptimization. If a function suddenly gets a different type, the optimized version is thrown away and bytecode takes over again.

Why this is fast

Most of a program is not hot. Interpret first, optimize later. You get startup speed and peak speed.

Why types matter

Hidden classes and inline caches assume obj.x stays the same shape. Mixing types in a hot path can make the JIT give up.

What you write still wins

Readable, predictable code is easier to optimize than clever type-switching. Write for humans; the engine will follow.

// Friendly to the JIT: same shape, same types function area(w, h) { return w * h; } area(10, 20); area(3, 4); // Harder: the engine must handle numbers AND strings area("10", "20");

🧠 Heap vs Call Stack

The engine keeps two kinds of memory. Mixing them up is the source of most “how does this even work?” moments.

The stack is a tower of frames. The heap is a warehouse of objects. A frame holds references; the objects live on the heap.

Call stack

Structured, fast, LIFO. Each function call pushes a frame: parameters, local bindings, and where to resume. When the function returns, the frame is popped and those locals are gone.

Memory heap

Unstructured pool for objects, arrays, functions, closures. Size is not known in advance. Values here live until nothing references them, then garbage collection can reclaim them.

function greet(name) { const message = { text: "Hi " + name }; // object → heap return message.text; // primitive copy on return } greet("Ada"); // Stack: [GEC] → [greet] → pop greet // Heap: { text: "Hi Ada" } until nothing points at it

Primitives vs references. Numbers, strings, booleans, null, undefined, and symbols behave as values. Objects and functions are references into the heap. That is why two variables can share one object, and why mutating an object inside a function is visible outside.

📚 Execution Context

An execution context is the environment where a piece of JavaScript is evaluated. The engine creates one for the whole program (the Global Execution Context) and a new one for every function call.

Memory component

Also called the variable environment. Stores bindings: variables, function declarations, and arguments as key → value.

Code component

The thread of execution. Runs the body line by line: assigns values, calls functions, evaluates expressions.

Phase 1 allocates bindings. Phase 2 fills them in. That split is why hoisting exists.

The example those boxes describe

var n = 2; function square(num) { var answer = num * num; return answer; } var square1 = square(2); var square2 = square(3);
  1. Global context is created. n, square1, square2 are undefined. square already holds the whole function.
  2. Line n = 2 runs. The binding is updated. No function has been called yet.
  3. square(2) creates a child context. Memory: num and answer start as undefined. Then num = 2, answer = 4, return 4. That context is destroyed. square1 becomes 4.
  4. square(3) repeats the same story with a fresh context. Contexts do not reuse each other’s locals.

📚 Call Stack

The call stack is the order of execution contexts. It is LIFO: last in, first out. The frame on top is the only one running.

Stack overflow happens when frames are pushed faster than they are popped — usually infinite recursion with no base case.
function recursive() { recursive(); // no base case } // recursive(); // RangeError: Maximum call stack size exceeded

A stack overflow is not “the heap is full.” It is “too many frames.” A memory leak is the opposite problem: heap objects that are never released because something still references them.

🎯 How this Is Decided

this is not the function. It is a binding set for that call, stored on the execution context. The same function can see a different this every time you invoke it.

Look at the call site, not the function body. That is where this is chosen.

1. Default

A bare call: fn(). In sloppy mode this is the global object. In "use strict" it is undefined.

2. Implicit

The object before the dot: user.greet() binds this to user. Detach the method and you lose that object.

3. Explicit

fn.call(obj), fn.apply(obj, args), fn.bind(obj) force the binding. bind returns a new function.

4. new

new User() creates an object, binds this to it, and returns it (unless the constructor returns another object).

const user = { name: "Ada", greet() { return "Hi " + this.name; } }; console.log(user.greet()); // "Hi Ada" — implicit const detached = user.greet; console.log(detached()); // undefined / window.name console.log(detached.call(user)); // "Hi Ada" — explicit const bound = user.greet.bind(user); console.log(bound()); // "Hi Ada" — locked in

Arrow functions do not get their own this. They close over the this of the surrounding scope. That is why they are the default inside React handlers and setTimeout callbacks — they keep the outer object instead of becoming window.

🔁 The Event Loop

The engine only runs whatever is on the call stack. The event loop is the runtime’s scheduler: when the stack is empty, it asks “is there work waiting?” and moves the next job onto the stack.

Empty the stack. Drain every microtask. Take one macrotask. The browser may paint. Repeat.
1
Run JS

Execute until the call stack is empty. No event loop work happens while a function is still running.

2
Microtasks

Drain the entire microtask queue: Promise jobs, queueMicrotask, MutationObserver.

3
One macrotask

Take a single callback: timer, I/O, UI event, setImmediate (Node).

4
Maybe render

The browser may paint, then the loop starts over. A busy stack delays paint.

while (runtime is alive) { run everything on the call stack while (microtaskQueue is not empty) { run next microtask // Promises always cut in line } if (browser wants to paint) render() run next macrotask // one timer / I/O / click }
console.log("A"); setTimeout(() => console.log("B timeout"), 0); Promise.resolve().then(() => console.log("C promise")); console.log("D"); // A // D // C promise ← microtask, before any timer // B timeout ← macrotask, even with 0ms

Walk it: A and D are synchronous, so they print first. setTimeout(..., 0) is not “run now” — it is “hand this to the timer API, then queue a macrotask.” The promise job is a microtask, so it runs as soon as the stack clears, before the timer.

🌐 Web APIs (and Node APIs)

The engine cannot wait on the network or the clock by itself. The host provides APIs. Those APIs may use OS threads, thread pools, or the operating system’s I/O. When they finish, they only enqueue a function. They do not jump onto your stack.

Timers

setTimeout, setInterval. The delay is a minimum. The callback still waits for an empty stack and its turn in the macrotask queue.

Network

fetch, XHR, WebSockets. The socket work happens outside JS. Your .then is a microtask after the response is ready.

DOM & events

Clicks, input, addEventListener. The browser notices the event, then queues a task that calls your listener.

📬 Macrotasks vs Microtasks

Two waiting rooms. Same event loop. Very different priority.

Microtask queue

Runs to completion after the stack

  • promise.then / catch / finally
  • queueMicrotask()
  • MutationObserver
  • async function resumes after await

If a microtask queues another microtask, that one also runs before the next macrotask. A tight microtask loop can starve rendering.

Macrotask / callback queue

One task per loop turn

  • setTimeout / setInterval
  • UI events (click, keydown)
  • I/O completion callbacks
  • setImmediate (Node), MessageChannel

After each macrotask, microtasks are drained again. That is why a promise scheduled inside a timeout still beats the next timeout.

setTimeout(() => console.log("macro 1"), 0); Promise.resolve() .then(() => { console.log("micro 1"); return Promise.resolve(); }) .then(() => console.log("micro 2")); setTimeout(() => console.log("macro 2"), 0); // micro 1 // micro 2 // macro 1 // macro 2

Interview trap: setTimeout(fn, 0) is not “next line.” It is “soonest macrotask.” Anything in the microtask queue still goes first. Nested awaits are also microtasks.

⏳ Promises and async / await

async/await is syntax. Under the hood it is still promises, and promise reactions are still microtasks.

What you write

async function loadUser(id) { const res = await fetch(`/users/${id}`); const user = await res.json(); return user.name; }

What the engine roughly does

function loadUser(id) { return fetch(`/users/${id}`) .then(res => res.json()) .then(user => user.name); }
  1. async functions always return a Promise. Even return 5 becomes Promise.resolve(5).
  2. await pauses only this function. The rest of the program keeps going. The paused function is resumed as a microtask when the awaited promise settles.
  3. Rejection becomes throw. try/catch around await is the same idea as .catch().
  4. It is still not a thread. While you await fetch, other JS can run. While you compute a huge loop after the data arrives, nothing else can.
async function demo() { console.log("2 inside async before await"); await null; // same as Promise.resolve() console.log("4 resumed as a microtask"); } console.log("1 sync"); demo(); console.log("3 sync after calling demo"); // 1 sync // 2 inside async before await // 3 sync after calling demo // 4 resumed as a microtask

⏳ Temporal Dead Zone

The Temporal Dead Zone is the stretch of time from entering a scope until a let / const / class binding is initialized. The name exists in memory. Using it throws.

Scope entered

Binding exists. Access is a ReferenceError.

Still in the TDZ

Even typeof x throws for let / const.

Initializer runs

let x = 10 — TDZ ends.

Safe to use

x is 10. Reads and writes are normal.

console.log("before"); // console.log(x); // ReferenceError: Cannot access 'x' before initialization let x = 10; console.log(x); // 10 // var has no TDZ console.log(a); // undefined var a = 5;

Why TDZ exists. It makes const honest (no half-created constant), and it catches “I used this before I meant to” instead of silently handing you undefined. That silent undefined from var is a classic bug source.

🔍 Scope and the Scope Chain

Scope is which bindings a line of code is allowed to see. Lookup walks outward: local → outer function → … → global. It never walks inward.

Inner scopes can read outer bindings. Outer scopes cannot see names declared inside.
Global scope

const taxRate = 0.08; — visible everywhere below

Function scope

function checkout(cart) { const fee = 2; }

Can read taxRate + cart + fee

Block scope

if (vip) { let discount = 0.2; }

Can read all of the above + discount. discount is invisible outside the if.

Three scopes you will use

const globalVar = "everywhere"; function test() { const functionVar = "only in test"; if (true) { let blockVar = "only in this block"; console.log(globalVar, functionVar, blockVar); } // console.log(blockVar); // ReferenceError } // var ignores block scope — it leaks to the function if (true) { var leaked = "I escape the if"; } console.log(leaked); // works — and that is the problem
let cartTotal = 0; function addToCart(price) { const tax = price * 0.08; const itemTotal = price + tax; cartTotal += itemTotal; return itemTotal; } function displayCart() { console.log(`Cart Total: $${cartTotal.toFixed(2)}`); // tax and itemTotal are not in this scope } addToCart(29.99); addToCart(15.50); displayCart();

🎁 Closures

A closure is a function plus the lexical environment it was created in. When a function is born inside another function, it keeps a live reference to those outer bindings — even after the outer function has returned and its stack frame is gone.

function makeCounter() { let count = 0; ← lives on the HEAP (closed over) return function next() { count += 1; ← still sees the same count return count; }; } makeCounter() returns next ──scope chain──► { count: 0 } (not popped with the stack)
function makeCounter() { let count = 0; return function next() { count += 1; return count; }; } const a = makeCounter(); const b = makeCounter(); console.log(a(), a()); // 1 2 console.log(b()); // 1 — separate heap environment

Why the heap matters

If count lived only on the stack, it would vanish when makeCounter returned. Because next still references it, the engine keeps that environment on the heap.

Where you already use this

React state setters, module-level caches, partial application, and “private” variables in factories are all closures. They are not a special syntax — they are scope that outlived its stack frame.

🌐 The Global Object

In a browser the global object is window (also reachable as globalThis). In Node it is global / globalThis. It is created with the Global Execution Context.

var and function declarations

Become properties of the global object in browsers. window.foo and foo are the same binding.

let / const / class

Are global bindings, but they do not become window properties. That is why they do not collide with window.name the same way.

var a = 10; function addNumber() { var x = 10; } console.log(window.a); // 10 console.log(a); // 10 — same binding addNumber(); console.log(window.x); // undefined — x was function-local let globalLet = "not on window"; console.log(window.globalLet); // undefined console.log(globalLet); // works — still a global binding
// Host APIs also live here — these are window methods console.log(window.innerWidth); console.log(window.location.href); window.setTimeout(() => {}, 0); // Prefer globalThis when code might run in the browser AND Node console.log(globalThis === window); // true in a browser page

Do not pollute the global object. A stray var or an implicit global (oops = 1 without a declaration, in sloppy mode) becomes a property everyone can clash with. Modules, const/let, and wrapping code in functions keep bindings private.

⚖️ var vs let vs const

These three keywords are three different rules for when a binding exists, where it is visible, and whether you may reassign it.

Which one should you type?

Will the binding be reassigned?

No → const. URLs, config, functions, and object/array references you will mutate in place.

Does the value need to change?

Yes → let. Loop counters, accumulators, values you pick in an if/else.

Avoid var unless you are reading or patching pre-ES6 code. It leaks out of blocks and has no TDZ.

The loop bug that made let famous

// One shared var binding for the whole function for (var i = 0; i < 3; i++) { setTimeout(() => console.log(i), 0); } // 3, 3, 3 — the timer runs after the loop; i is already 3 for (let i = 0; i < 3; i++) { setTimeout(() => console.log(i), 0); } // 0, 1, 2 — each iteration has its own block-scoped i
const API_URL = "https://api.example.com"; const items = []; let total = 0; items.push({ name: "Book", price: 29.99 }); // allowed — same array // items = []; // TypeError — cannot rebind const items.forEach(item => { total += item.price; });

♻️ Garbage Collection

You do not free() memory in JavaScript. The engine’s garbage collector finds heap values that are no longer reachable from the roots (the stack, globals, and closures still in use) and reclaims them.

Mark and sweep

Start from roots. Mark everything you can reach. Sweep the rest. This is the core idea in modern engines (with generations and incremental marking so pauses stay short).

What a leak looks like

A forgotten global, a detached DOM node still referenced, a closure that captured a huge array, or an event listener you never removed. Reachable = not collected.

Roots: Global object · current stack frames · open closures │ ▼ mark objects you can still walk to → keep objects with no path from roots → sweep (memory reused)
function leakyHandler() { const huge = new Array(1e6).fill("x"); window.addEventListener("resize", () => { console.log(huge.length); // closure keeps huge alive }); } function cleanHandler() { const onResize = () => console.log(window.innerWidth); window.addEventListener("resize", onResize); return () => window.removeEventListener("resize", onResize); }

Rule of thumb: if you still have a reference, the collector cannot help you. Drop the reference (or remove the listener) when you are done. Closures are useful — they are also the most common way a large object stays reachable by accident.

🧩 Put It Together

One program, every piece of this page in motion. Read it as a timeline, not as magic.

console.log("1 sync start"); function double(n) { return n * 2; } const result = double(21); setTimeout(() => console.log("4 timeout", result), 0); Promise.resolve(result).then(value => { console.log("3 microtask", value); }); console.log("2 sync end");
  1. Engine starts. Parse → AST → bytecode. A Global Execution Context is pushed onto the call stack. Memory phase registers double (full function) and result (TDZ until its line).
  2. Sync work. "1 sync start" prints. double(21) pushes a new context, returns 42, pops. result is assigned. setTimeout hands a callback to the timer API. The promise schedules a microtask. "2 sync end" prints. Stack is empty.
  3. Microtasks first. The event loop drains the promise job: "3 microtask" 42.
  4. Then one macrotask. The timer callback runs: "4 timeout" 42. result is still visible because the callback closed over the global binding.
  5. Heap cleanup. When nothing references leftover objects, mark-and-sweep can reclaim them. The global bindings stay until the page unloads.
Call stack [ GEC ] → [ double ] → [ GEC ] → empty Web APIs timer holds fn until 0ms elapses Microtasks [ then → log 3 ] Macrotasks [ timeout → log 4 ] Event loop empty stack → drain micro → one macro → maybe paint

📌 How to Remember

If you can tell this story out loud, you understand how JavaScript works.

ENGINE

Parse into an AST, interpret bytecode, optimize hot functions. Memory heap holds objects. The call stack holds frames.

CONTEXT

Every program and every call gets an execution context: bindings, scope chain, and this. Two phases: allocate, then run.

STACK

LIFO. One JS function at a time. When it returns, its frame is gone. Overflow = too many frames, not a full heap.

EVENT LOOP

Stack empty → drain every microtask → take one macrotask → maybe render. Promises beat timers. Async is not a second thread.

SCOPE

Lookup walks outward. Closures keep outer bindings on the heap. let/const are blocked and have a TDZ. Prefer const.

THIS

Decided by the call site: default, dot, call/apply/bind, or new. Arrows inherit this. They do not get their own.

One sentence

JavaScript runs one stack frame at a time; the engine stores objects on the heap; the host waits on I/O; the event loop only feeds the stack when it is empty — microtasks first.
