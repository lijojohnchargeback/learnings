📬 Message Queues Complete Guide

Queues, pub/sub, and event streams — from a Node.js / backend architecture view

🏠 What is a Message Queue?

A message queue lets one application send work or data to another without both sides being online and talking at the same time. The broker sits in the middle. The producer can finish. The consumer can process later.

SQS, Kafka, and RabbitMQ are not the same kind of “message queue.” Some are work queues, some are pub/sub, and Kafka is a distributed event log.

Basic hop:

Producer | | message v +----------------+ | Message System | +----------------+ | | message v Consumer

In a typical order flow, the message system is what keeps services from calling each other directly:

Order Service | | "Order #123 created" v Queue | +------> Email Service | +------> Payment Service | +------> Inventory Service

The sentence to remember

Do not classify everything as “a message queue.” Classify it as a queue, a pub/sub system, or an event stream / log. They overlap, but the core mental models are different.

⚡ Why We Need Queues

Without a queue, the Order API waits on every downstream service. If Email is down, the whole request can fail or become slow.

The API returns quickly. Workers do the slow or unreliable work later. That is the whole point of a work queue.
Synchronous chain
User → Order API → Payment → Email → Inventory → Shipping. One slow or down hop hurts the user request.
Queued work
User → Order API → Queue → Email / Payment / Inventory workers. The API acknowledges the order. Workers catch up.

A queue also absorbs backpressure. If producers write 10,000 messages/sec and consumers handle 2,000/sec, the backlog grows instead of melting the API. That lag is expected. You scale workers, not the request path.

🧭 Queue vs Pub/Sub vs Streaming

This is the most important distinction. People mix these three together:

Queue = one competing worker gets the job. Pub/Sub = every subscription gets a copy. Stream = the event stays in a log and each consumer reads at its own offset.

Queue

A message is generally processed by one competing worker. Use for background jobs, emails, image resizing, order processing.

Pub/Sub

Multiple independent subscribers each receive the event. Use for notifications, microservice fan-out, “tell everyone interested.”

Streaming / Log

Consumers keep their own position in an append-only log. Replay is a first-class feature. Kafka is the classic example.

The “delete message” difference

Traditional queue

Consumer processes → ACK → message is removed. Examples: SQS, RabbitMQ, Azure Service Bus.

Kafka-style log

Consumer A can be at offset 10 while Consumer B is at offset 5. The record stays until retention expires. Processing does not delete it.

🟧 Amazon SQS

Amazon SQS (Simple Queue Service) is primarily a queue. A producer sends a message. A consumer receives it. After successful processing, the consumer deletes it.

Order Service | | OrderCreated v SQS | v Email Worker

Visibility timeout

This is the most important SQS idea. When a worker receives a message, SQS temporarily hides it. If the worker crashes before deleting the message, the timeout expires and the message becomes visible again for another worker.

Visibility timeout is failure recovery. Hidden while a worker is busy. Visible again if that worker dies.

Standard vs FIFO

Standard

Optimized for high throughput. Design consumers to tolerate duplicate delivery. The consumer should be idempotent.

FIFO

First In, First Out. Stronger ordering and deduplication within a message group. Use when order of related messages matters.

SQS is not a broadcast system

If three competing consumers listen to one SQS queue, a given message is generally taken by one of them. That is a work queue, not fan-out.

SQS | message X | +-----+-----+ | | | A B C Only one gets X

📣 Amazon SNS

SNS (Simple Notification Service) is primarily publish/subscribe. One publish can reach many subscribers. That is fan-out.

Publisher | v SNS | +----> Subscriber A | +----> Subscriber B | +----> Subscriber C

SNS + SQS is the common AWS pattern

SNS alone can push to HTTP, email, Lambda, and more. For reliable independent processing, subscribe one SQS queue per service to the topic.

One OrderCreated event becomes three independent queues. Email can be slow without blocking inventory.

Amazon EventBridge sits nearby: it is an event bus with rules, schema, and SaaS integrations. Think “routed events across an account,” not “a simple work queue.”

☁️ Google Cloud Pub/Sub

Google Cloud Pub/Sub is a managed publish/subscribe system. Publishers write to a topic. Each subscription is an independent consumption path.

Publisher | v Topic (orders) | +------ email-subscription -----> Email consumer | +------ inventory-subscription -> Inventory consumer | +------ analytics-subscription -> Analytics consumer

SQS

One queue. Competing workers. One worker gets a given message.

Pub/Sub

One topic. Many subscriptions. Each subscription can receive its own copy.

Ordering can be enabled for use cases that need it. Treat it as configured, not as a free global guarantee.

🪵 Apache Kafka

Kafka is not a traditional message queue. It is a distributed append-only event log / streaming platform.

Kafka does not think “I delivered this, therefore delete it.” It thinks “this event exists at offset X.”

Retention, not delete-on-ack

A traditional queue removes a message after ACK. Kafka keeps records according to retention. Consumers can go back and reread old events. That is why analytics, search, fraud, and a data warehouse can all consume the same UserClickedProduct stream independently.

Partitions

A topic is split into partitions. Each partition is an ordered log. More partitions generally allow more parallelism inside one consumer group.

orders topic | +-- Partition 0 → Consumer C0 +-- Partition 1 → Consumer C1 +-- Partition 2 → Consumer C2 +-- Partition 3 → Consumer C3

Consumer groups

Inside a group, partitions are distributed so each partition is assigned to one consumer at a time. Another group can independently read the same topic. That is how Kafka can act like both a work queue (one group) and pub/sub (many groups).

Interview point: ordering

Kafka guarantees order within a partition, not a global order across the whole topic. Put related events (same order id, same user id) in the same partition key if their sequence must stay intact.

Scaling is different

4 partitions + 4 consumers can map 1:1. 4 partitions + 10 consumers means some consumers sit idle. You scale a Kafka consumer group by adding partitions first, then consumers — not by blindly adding processes.

🐰 RabbitMQ

RabbitMQ is a traditional message broker. Producers usually publish to an exchange, not directly to a queue. The exchange routes.

SQS is producer → queue → consumer. RabbitMQ is producer → exchange → routing → queues.

Direct

Route by exact routing key. email goes to the email queue.

Topic

Pattern routing: order.created, order.*, payment.completed.

Fanout

Broadcast to every bound queue. Ignore the routing key.

Headers

Route on message headers instead of a routing key.

🔷 Azure Service Bus

Azure Service Bus is Microsoft’s enterprise messaging service. It supports both models:

  • Queues — competing consumers, one consumer gets a message
  • Topics + subscriptions — pub/sub, each subscription is an independent path

FIFO-style ordering is available through sessions. Dead-lettering is a first-class feature. If you are already in Azure and need enterprise queues plus topics, this is the default pick — not Event Hubs.

📡 Azure Event Hubs & Amazon Kinesis

These are closer to Kafka than to RabbitMQ. They ingest high-volume streams: IoT, logs, telemetry, clickstreams.

Azure Event Hubs

High-volume event ingestion. Partitioned. Often the front door into stream processing, analytics, and storage.

Amazon Kinesis

AWS streaming platform. Think “Kinesis ≈ AWS stream,” not “Kinesis ≈ SQS.” Use for data pipelines, not simple background jobs.

⚡ Redis Streams, NATS, ActiveMQ

Redis Streams

A log/stream abstraction with consumer groups. Useful when Redis is already in the stack and you need lightweight streaming — not a replacement for Kafka at huge volume.

NATS / JetStream

Lightweight, low-latency messaging. Core NATS is pub/sub. JetStream adds persistence and streaming. Popular in fast distributed systems.

ActiveMQ

Traditional enterprise broker (often JMS / Java). Queues and topics. More common in older enterprise architectures than in new cloud-native Node.js stacks.

🎯 Delivery Guarantees

Most brokers need an ACK: “I successfully processed this.” If the worker crashes before ACK, the message can become available again.

At-most-once

Deliver, then forget. A crash can lose the message. You prioritize avoiding duplicates.

At-least-once

The common default. A crash before ACK can redeliver. Your app should be idempotent.

Exactly-once

Be careful with the phrase. Broker “exactly-once” is not the same as exactly-once effect when you charge a card or send an email.

Exactly-once processing is hard

Even if the broker is sophisticated, an external side effect (payment, SMS, inventory decrement) can still run twice. Design the effect to be safe under retry, not just the delivery.

🔁 Idempotency

If Charge $100 is delivered twice, a naive consumer charges twice. A safe consumer keys on something unique — usually order_id or a message id — and skips work already done.

Bad
message received → charge customer. Twice means two charges.
Better
Look up order_id = 123. Already processed? Ignore. Otherwise process and record the id in the same transaction when you can.

SQS Standard, Kafka at-least-once, and most cloud queues assume you will do this. Treat idempotent consumers as the default, not an optimization.

Horizontal scaling on a queue

Add workers. Messages spread across them. That is competing consumers.

Message 1 ---> Worker 1 Message 2 ---> Worker 2 Message 3 ---> Worker 3 Message 4 ---> Worker 1

Backpressure

When producers outrun consumers, the queue holds the difference. That backlog is consumer lag. A queue is a shock absorber, not a proof that you are keeping up. Watch depth / lag and scale workers or slow producers.

☠️ Dead Letter Queue, Retry, Delay

A poison message that always fails should not block the queue forever. After a retry budget, move it to a dead letter queue so you can inspect it.

Retry with backoff. Isolate poison messages. Never charge twice just because the broker retried.
  • Retry — attempt 1, 2, 3. Prefer exponential backoff (1s, 2s, 4s, 8s) over a tight loop.
  • DLQ — after the budget, isolate the message. SQS, RabbitMQ ecosystems, Service Bus, and others all support a dead-letter pattern; details differ.
  • Delay — some work should wait: reminder in 30 minutes, retry payment in 5, expire a reservation in 15. Platforms expose delay / scheduled messages differently.

💾 Persistence, Size, Managed vs Self-managed

Brokers are not object storage. Do not put a 10 GB video on the queue. Put the file in S3 / GCS / Azure Blob and send metadata plus the object key.

{ "event": "VideoUploaded", "objectKey": "videos/abc.mp4" }

Durable

If the broker crashes, the message should survive. Cloud-managed systems store durably by default according to their SLAs. Kafka writes to disk across brokers. RabbitMQ can use durable queues/messages. Redis Streams depend on Redis persistence settings.

Managed vs self-managed

Managed: SQS, Pub/Sub, Service Bus, EventBridge, MSK, Confluent Cloud. Self-managed: Kafka, RabbitMQ, NATS, ActiveMQ on your machines. More control, more operational work.

🌳 What Should You Choose?

Start from the job, not from the brand name. Background work, fan-out, and event history lead to different systems.
Use SQS
Background jobs on AWS

Emails, image resize, reports, order workers. Node.js API → SQS → worker.

Use RabbitMQ
Complex routing

Exchanges, topic patterns, work queues when you need broker-side routing.

Use Kafka
Events + history + replay

High volume, many independent consumers, stream processing, analytics.

Use Pub/Sub
GCP-native fan-out

Topics and subscriptions when you already live on Google Cloud.

Use Service Bus
Azure enterprise messaging

Queues plus topics/subscriptions in the Microsoft ecosystem.

Use Event Hubs / Kinesis
Massive ingestion

IoT, logs, telemetry, clickstreams — not a simple job queue.

🧩 Event-Driven Architecture

Instead of Order Service calling Payment, Inventory, and Email over HTTP, publish OrderCreated once. Each service consumes independently. That reduces direct coupling.

Order Service | | OrderCreated v Message System | +---------+---------+ | | | v v v Payment Inventory Email

Request/response vs messaging

Synchronous HTTP

Client waits for the server. Use when the user needs the answer now: login, checkout confirmation, a read.

Asynchronous messaging

API writes a message and returns. The worker finishes later. Use when the work is slow, bursty, or belongs to another team.

🟢 Node.js vs the Event Loop Queue

Because this site also covers Node.js internals: the broker is not the event loop. Confusing them is a common learning mistake.

Microtask queue and timer queue live inside one process. SQS / Kafka / RabbitMQ live between applications.

Inside the runtime

Event loop, microtask queue, timers, I/O callbacks, libuv thread pool. This schedules JavaScript in one Node.js process.

Between applications

Node.js API → network → broker → other Node.js workers, containers, or Kubernetes pods. This is distributed messaging.

A typical Node.js setup: the API publishes and returns. Workers are separate processes. You scale workers horizontally. You do not try to “queue work” by stuffing the event loop.

COMPUTER | CPU / cores / OS threads | Node.js process (event loop + libuv) | Load balancer | Node.js application | Message broker | Worker · Worker · Worker

📌 Mental Models

SQS

“Give this job to one worker.” Queue → worker.

SNS

“Tell everyone interested.” Topic → many subscribers.

Google Pub/Sub

“Publish an event, let subscriptions consume it.” Topic → subscriptions.

RabbitMQ

“Route messages intelligently to queues.” Producer → exchange → queues.

Kafka

“Keep an ordered stream that many consumers can independently read.” Topic / partitions → consumer groups.

The most important takeaway

SQS and RabbitMQ are primarily about distributing work. Kafka is primarily about storing and distributing an event stream. Pub/Sub is primarily about publishing events to independent subscriptions.

For a typical Node.js microservice: start with a queue (SQS / RabbitMQ / Service Bus). For event-driven fan-out with history, use Kafka or Pub/Sub. For millions of telemetry events, use a streaming platform (Kafka, Kinesis, Event Hubs, Pub/Sub).
