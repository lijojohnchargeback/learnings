🤝 6. AI Agents & Multi-Agent Systems

Step 6 of 12 — An agent is an LLM in a loop with tools, state, and a stop condition — not a personality.

What an agent is

An agent is a model that can choose actions, see results, and continue until a goal is met or a budget runs out. The control loop owns retries, permissions, and stop conditions. The model proposes the next step; your code decides whether that step is allowed.

Loop in the middle, constraints on the sides. Inputs are the goal, tool catalog, and system prompt. Guards are max steps, timeouts, HITL, and traces. Without the guards, an agent is a billing and safety incident waiting to happen.

Not a chatbot

Chat answers once. An agent can call tools, branch, and keep going until done or capped.

Not a personality

“Helpful assistant” is branding. Production value is schemas, state, and hard stop conditions.

Cost multiplier

Each step is another model call + tool latency. Agents fail louder and cost more than single-shot RAG.

When to use an agent

Use an agent when the task needs multiple steps, unknown tool order, or branching. Skip it when one retrieval + one generation is enough.

Use an agent whenDo not use an agent when
Tool order depends on intermediate resultsA single RAG call answers the question
You must branch (refund vs escalate vs FAQ)You are filling a form from structured extraction
Long workflows need checkpoints and approvalsLatency budget is a few hundred ms end-to-end
A human must approve side effects mid-flowThe “agent” would only call one fixed tool once
Default to less autonomy. Agents multiply cost, latency, and failure modes. Prefer a deterministic graph with LLM decision points over a free-form ReAct loop for production paths.

Agent loops

The minimal loop: model chooses a tool or a final answer; you execute the tool; you append the result; repeat until done or max_steps.

Happy path is teal; stop conditions are red. Cap steps, wall-clock time, and tokens on every production loop. “I’ll let it cook” is how teams burn five figures overnight.
def run_agent(user: str, tools: dict, max_steps: int = 8) -> str: messages = [{"role": "user", "content": user}] for _ in range(max_steps): msg = llm_with_tools(messages, tools) if msg.tool_calls: messages.append(msg) for call in msg.tool_calls: result = tools[call.name](**call.args) messages.append({"role": "tool", "tool_call_id": call.id, "content": result}) continue return msg.content return "Stopped: max steps reached."
BudgetWhy it matters
max_stepsStops wander / retry storms
Wall-clock timeoutUser and worker SLAs
Token / $ ceilingProtects the bill
Per-tool timeoutOne hung API must not hold the loop forever
Always cap steps, tokens, and wall-clock time. Infinite loops are a billing incident.

Planning

How the agent decides what to do next is the planning style. Demos love free-form ReAct; production prefers graphs you can audit.

Left → right = more control. ReAct is flexible and wanders. Plan-and-execute goes stale when the world changes. Graphs let you own auth, retries, and approvals on the edges.
StyleHowRiskBest for
ReActInterleave thought + tool in one modelVerbose; can wanderExploration, research prototypes
Plan-and-executeWrite a plan, then run stepsStale plans when the world changesStable, well-scoped tasks
Router / graphDeterministic nodes + LLM only at decision pointsMore code, much more controlSupport bots, ops, payments, compliance

Production systems trend toward graphs: you own the edges (auth, retries, approvals); the LLM fills slots, not the whole control plane.

Tools

Tools are functions with JSON schemas. Treat them like public APIs: validate args, least privilege, no raw SQL from the model, confirm before emails/payments/deletes.

Happy path is teal; red is banned. Schema → allowlist → secrets from a vault → timeout → truncate → audit. Never expose arbitrary SQL, an open HTTP proxy, or a shell on a shared host.
TOOLS = [{ "type": "function", "function": { "name": "search_docs", "description": "Search internal docs. Read-only.", "parameters": { "type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"] } } }]

Memory

Memory is not “whatever fits in the context window.” Split kinds of memory so you can summarize, retrieve, and store facts deliberately.

Four layers, four stores. Working = current thread. Episodic = past-thread summaries. Semantic = RAG over facts/tickets/code. Profile = structured prefs in a DB — never “hope the prompt remembers.”
  • Working: the current messages / scratchpad (fits in context)
  • Episodic: summaries of past threads
  • Semantic: RAG over facts, tickets, code
  • Profile: user prefs stored in a DB, not hoped-for in the prompt

Do not “let the agent remember” by stuffing unbounded history. Summarize, retrieve, and store structured facts.

State

Durable state is a checkpoint: thread id, node, tool results, pending approval. If the process dies mid-tool, you must not double-charge a customer. Use idempotency keys on side-effecting tools.

Crash → resume from checkpoint. Persist thread id, current node, tool results, and pending approvals. Side-effecting tools need idempotency keys so a replay cannot double-charge.
FieldWhy store it
Thread / run idCorrelate logs, resume, and user history
Current nodeKnow where the graph stopped
Tool resultsAvoid re-running expensive or mutating calls blindly
Pending approvalPause for HITL without losing context
Idempotency: every create/charge/send tool should accept a key you generate once per logical action. Retries with the same key must be no-ops.

Multi-agent patterns

More agents are not more intelligence. They are more latency, more contradictory tool use, and more surface area for prompt injection. Prefer a supervisor that routes to specialists.

Left = prefer; right = avoid. One supervisor routes to specialists that share retrieval and logging. Do not give every agent write access to production or let them debate forever.
PatternShapeUse when
Supervisor → specialistsRouter picks researcher / writer / opsMost production multi-agent work
PipelineFixed A → B → C with optional LLM per stageContent, review, or ETL-like flows
Debate / committeePeers argue then voteRare research; almost never ops
Multi-agent rule: Specialists should not all have write access to production. Put mutations behind the supervisor or a HITL gate.

Human-in-the-loop

HITL is a first-class node, not a Slack message you hope someone sees. Interrupt the graph, persist pending approval, resume only after an authenticated decision.

  • Require HITL for money, PII export, deletes, and privilege changes
  • Show the human the tool args and the evidence that led there
  • Expire stale approvals; do not resume a week-old charge silently

Observability

If you cannot replay a failed run, you cannot ship agents. Log every model call, tool call, and routing decision with the same run id.

SignalWhat to capture
TraceSpans for LLM, tools, retrieval, HITL waits
CostTokens and $ per run; alert on outliers
QualitySuccess / escalate / user undo rates
SafetyBlocked tools, injection flags, policy denials

Framework map

Pick one graph-style runtime for production control flow. Use the others only when your stack or team already depends on them.

One runtime first. LangGraph for explicit graphs. LangChain for loaders/prototypes. CrewAI for role-based content. OpenAI Agents / Google ADK when you are already on that cloud stack.

LangGraph

Graph runtime from the LangChain team: nodes, edges, conditional routing, persistence. Good when you want explicit control flow (support bot: retrieve → generate → grade → retry) instead of a free-form ReAct soup.

Learn: StateGraph, reducers, checkpointers, human-in-the-loop interrupts.
  • Model each step as a node you can test in isolation
  • Use checkpointers so crashes resume mid-graph
  • Put approvals on interrupt nodes, not in prompt text

LangChain

Ecosystem of model/tool/document loaders. Useful for prototyping. In production, keep the surface small: you own prompts, retrieval, and tracing. Avoid mega-chains you cannot debug.

  • Use for adapters (models, vector stores, parsers)
  • Do not bury business rules inside opaque chain objects
  • Prefer LangGraph when control flow grows beyond a linear chain

CrewAI

Role-based multi-agent: researcher, writer, reviewer. Fine for content workflows with a human editor. Risky for ops: more agents = more latency and contradictory tools. If you use it, pin tasks, share one retrieval layer, and log every agent’s output.

  • Pin roles and tools; do not let every agent invent new actions
  • Share one retrieval / knowledge layer across roles
  • Keep a human editor for anything customer-facing

OpenAI Agents

OpenAI’s agents SDK: handoffs, tools, tracing, guardrails, close to their API. Good if you are already on that stack. Same rules apply: schemas, max turns, approvals.

  • Use handoffs as supervisor → specialist, not free-for-all
  • Enable tracing before you ship; debug from spans, not vibes
  • Guardrails are filters — still validate tools server-side

Google ADK

Google Agent Development Kit — agents, tools, and orchestration aimed at Gemini / Vertex. Use when your enterprise is already on GCP. Compare on tracing, eval, and how tools map to IAM — not on demo videos.

Evaluate ADK on: IAM mapping for tools, Vertex tracing/eval hooks, and how multi-agent state persists — not on marketing demos.

Checkpoint — move on when

  • You can implement a tool loop with max steps without a framework
  • You can draw a graph for a real workflow (retrieve, act, approve, reply)
  • You persist state and never fire a payment tool twice by accident
  • You prefer supervisor → specialists over a debating committee
