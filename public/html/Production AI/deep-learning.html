🧠 3. Deep Learning & Transformers

Step 3 of 12 — How neural nets, attention, and GPUs actually produce tokens and embeddings.

Why you need this

You do not need to invent GPT from scratch. You do need to know why context windows cost money, why batching matters, and why a 7B model on a T4 behaves differently from an API call. This category is the mental model for inference, fine-tuning, and multimodal systems.

The production path: layers and loss → sequence models → attention → stacked transformers → GPU memory. Every later topic (RAG, agents, serving) sits on this stack.

What “deep” actually means

Deep learning is machine learning with multi-layer neural nets. Depth is useful because each layer learns a more abstract representation: pixels → edges → objects; tokens → syntax → intent. Transformers are deep nets with attention instead of convolution or recurrence as the mixing step.

  • Training finds weights that minimize a loss on data you have.
  • Inference runs those frozen weights on new inputs (chat, embeddings, vision).
  • Production is inference plus memory, latency, batching, and cost — not just accuracy in a notebook.

You will use this for

Choosing encoder vs decoder models, estimating VRAM, reading a Hugging Face card, and debugging “why is this request so slow / expensive.”

You will not need

Deriving every gradient by hand, or training a foundation model. Pretrained weights plus a tiny loop is the default.

Failure mode to avoid

Treating the API as magic. If you cannot name tokens, attention cost, and KV cache, you cannot budget or debug.

Neural networks

A network maps inputs to outputs through weighted layers and nonlinearities (ReLU, GELU). Each connection has a weight. Each unit has a bias. Training is just adjusting those numbers so a loss goes down. Overfitting is the default; regularization, dropout, and more data are the usual answers.

Data flows left to right. Learning changes the weights. Without the activation f, stacked layers collapse into one linear map — that is why ReLU / GELU exist.

The neuron, in one line

Formula: output = f(Σ (weight × input) + bias)

The sum is a linear mix of inputs. The activation f is the nonlinearity. Repeat this in layers and you can approximate complicated functions — images, speech, next-token probabilities.

Layers

  • Input: raw features, pixels, or token embeddings
  • Hidden: learned representations. More layers = deeper. Width = how many units per layer.
  • Output: logits (raw scores), class probabilities, a regression value, or a vocabulary distribution

Activation functions you will actually see

Overfitting is the default

A net with enough parameters can memorize training noise. You want low training error and low validation error. Watch the two curves together — not only the training loss going down.

Underfit = too simple (high bias). Overfit = memorizes noise (high variance). In production you catch this with a held-out set, early stopping, and slice metrics — not by staring at training loss.
RegularizerWhat it doesWhen you use it

Production note: A 90% training accuracy with a 60% validation accuracy is not “almost done.” It is a model that will fail on real traffic. Lock the split (and the metric) before you tune.

Training loop

Training is a loop, not a one-shot formula. You sample a batch, predict, measure error, send gradients backward, and step the optimizer. An epoch is one full pass over the dataset. Fine-tuning an LLM uses the same loop — just with more VRAM and a pretrained starting point.

One iteration: predict, measure error, send gradients backward, step the optimizer. Repeat thousands to millions of times. Autograd in PyTorch is this diagram as code.

The five steps

  1. Batch — sample a mini-batch (e.g. 32 images, or 4 sequences of 2048 tokens)
  2. Forward — compute predictions ŷ from the current weights
  3. Loss — compare ŷ to labels y (cross-entropy for classification / next-token; MSE for regression)
  4. Backward — chain rule gives ∂loss/∂weight for every parameter
  5. Step — optimizer (SGD, Adam, AdamW) updates weights by learning rate × gradient

Inference is not this loop

At serve time you only run the forward pass. No loss, no backward, no optimizer. That is why inference uses less memory than training — unless the KV cache for long context eats it anyway (see Attention).

CNN

Convolutional nets share a small filter across space. Nearby pixels are related, so a 3×3 kernel that detects an edge in the top-left also works in the bottom-right. That inductive bias is why CNNs crushed ImageNet in 2012 and still dominate cheap, small-scale vision.

A kernel slides over the image. Early filters learn edges; later layers learn parts and objects. ReLU keeps only useful activations. Pooling downsamples so the next layer sees a larger field of view.

Building blocks

PieceWhat it doesProduction angle
ConvolutionDot-product of a kernel with a local patchParameter count stays small even on big images
ReLUZeros negative activationsCheap nonlinearity; default after conv
Pooling / strideDownsample (max-pool or strided conv)Cuts compute; you lose precise location unless you skip
Skip / residual (ResNet)Add the input of a block back to its outputLets you train 50–150+ layers without vanishing gradients
Batch / layer normStabilize activationsMakes training less brittle to learning rate

In modern stacks, vision Transformers (ViT) and CLIP / SigLIP-style encoders often replace or sit beside CNNs. Conv bias is still useful: smaller data, on-device, real-time detection (YOLO), and as a cheap stem before a transformer.

Production: Use a pretrained vision encoder (OpenCLIP, SigLIP, cloud Vision APIs, or a frozen ResNet) unless you have a labeled dataset large enough and a reason to train from scratch. Fine-tune the head first; unfreeze later if the metric needs it.

Where CNNs still win

  • Object detection / segmentation at tight latency budgets (factory cameras, mobile)
  • Medical and industrial images where you have modest data and a strong conv baseline
  • Spectrograms — speech and audio often start as a 2D time-frequency image

RNN / LSTM

RNNs process sequences step by step. At time t they take the current token and a hidden state h(t-1), then emit h(t). LSTMs and GRUs added gates (forget, input, output) so the state could remember longer than a vanilla RNN. They still struggle to parallelize, and they still forget very long context. Transformers won because attention looks at all positions at once — with a quadratic cost.

Left: each step waits on the previous hidden state — GPUs sit idle. Right: every token attends to every other token in one matmul. That is why training GPT-scale models is feasible, and why long context is expensive.
ProblemRNN / LSTMTransformer
ParallelismMust run t=1, then t=2, …All positions in one shot (training)
Long-range linksSignal travels through many steps; gradients vanishDirect attention from token i to token j
Context costLinear in length, but quality diesQuality holds; compute/memory is O(n²)
StreamingNatural (one step at a time)Needs KV cache and careful chunking

You will still meet RNNs in older speech models, some on-device keyword spotting, and a few streaming setups. For new NLP, assume Transformer. If someone proposes an LSTM for a chatbot in 2026, ask what constraint (latency on a tiny MCU, existing checkpoint) makes that the right call.

Vanishing gradients: a vanilla RNN multiplies the same weight matrix at every step. After 50–100 steps the gradient is ~0 and the net cannot learn “the subject of this sentence was 80 tokens ago.” LSTM gates slowed that death. Attention skipped it.

Attention

Attention lets each token look at other tokens. Query / Key / Value: “what am I looking for / what do I contain / what do I pass on.” Scores are softmax(QKᵀ / √d); the output is a weighted mix of values. Multi-head attention runs this in several subspaces so one head can track syntax while another tracks coreference.

In “The cat sat on the mat”, the token sat puts high weight on cat and mat. Multi-head attention runs several of those mixes at once. Positional encoding is required because attention itself does not know word order.

Q, K, V without the mystique

  • Query (Q) — the current token asking “who is relevant to me?”
  • Key (K) — every token advertising “this is what I am about”
  • Value (V) — the payload mixed in if the query matches the key

Self-attention means Q, K, V all come from the same sequence. Cross-attention (encoder-decoder) means Q comes from the decoder and K/V come from the encoder — translation, some speech, and classic T5.

Why this is a production problem

Full attention is O(n²) in sequence length n. Double the context and you roughly quadruple that layer’s compute and the KV storage. That is why an 8K prompt and a 128K prompt are not “the same model, just more text.”

Prefill processes the prompt once and writes K and V. Decode generates one token at a time and reuses that cache instead of recomputing the past. The cache is why long chats eat VRAM even when the weight file fits.
IdeaWhat it isWhy it matters in production
Quadratic costAttention work scales with n × nContext length blows up compute, latency, and bill

Prefill vs decode (the latency split)

Prefill is compute-heavy and parallel — a long prompt saturates the GPU. Decode is memory-heavy — you stream one token, and the bottleneck is reading weights + KV. APIs feel “slow to first token” on huge RAG prompts (prefill) and “slow to finish” on long answers (decode). Batching many decodes together (vLLM continuous batching) is how you hide that.

Transformers

A transformer is a stack of attention + MLP blocks with residuals and layer norm. The 2017 paper (“Attention Is All You Need”) was encoder-decoder for translation. Almost every chat model you ship in 2026 is a decoder-only stack with a causal mask. Embedding models are often encoder-only.

Pick the flavor from the job: embed/classify → encoder; chat/code/agents → decoder; classic translation or some speech → encoder-decoder. Mixing them up is how teams serve a 70B chat model as an embedding endpoint.
FlavorMaskingExamplesJob
Encoder-onlyBidirectional (sees both sides)BERT, embedding models, many classifiersUnderstand / embed text
Decoder-onlyCausal (left to right)GPT, Llama, most chat modelsGenerate next tokens
Encoder-decoderEncoder bidirectional + decoder causal + cross-attnT5, classic translation, some speechMap sequence → sequence

One decoder block, in order

  1. Causal self-attention — token i may only attend to tokens ≤ i
  2. Residual + layer norm — add the input back so deep stacks stay trainable
  3. MLP / feed-forward — a large per-token network (often SwiGLU). This is where most parameters live
  4. Residual + layer norm again. Repeat dozens to hundreds of times

Around the stack: token embeddings turn IDs into vectors; positional encodings (absolute sin/cos, or RoPE in most modern LLMs) inject order; an lm_head maps the last hidden state to vocabulary logits; you sample or argmax the next token, append it, and repeat.

# Mental model of one decoder step # tokens -> embed + position (RoPE) # for each layer: self-attention (causal mask) -> MLP # lm_head -> logits over vocabulary # sample or argmax next token, append, repeat

RoPE and long context

Attention is permutation-invariant without position. Rotary embeddings (RoPE) rotate Q/K by an angle that depends on token index so “dog bites man” ≠ “man bites dog”. Long-context recipes (YaRN, NTK scaling) stretch RoPE so a 4K-trained model can run at 128K with some quality loss. A huge window is not free and is not lossless.

What this buys you as an engineer

  • An embedding model (encoder) is the right tool for search, clustering, and RAG indexes — not a chat model with “please return a vector.”
  • A chat / completion model (decoder) is the right tool for generation, tools, and agents.
  • Context is a budget: system prompt + history + RAG chunks + output tokens must fit, and the middle of a long prompt is where models go blind.

PyTorch

The default research-to-production DL framework. Learn tensors, autograd, nn.Module, Dataset/DataLoader, training loops, torch.save / load_state_dict, and moving models to CUDA. Hugging Face Transformers sits on PyTorch for almost all open models — if you can train TinyNet, you can fine-tune a small LLM with the same loop.

A tiny net

import torch import torch.nn as nn class TinyNet(nn.Module): def __init__(self, d_in, d_hidden, d_out): super().__init__() self.net = nn.Sequential( nn.Linear(d_in, d_hidden), nn.ReLU(), nn.Linear(d_hidden, d_out), ) def forward(self, x): return self.net(x) model = TinyNet(16, 32, 2) loss_fn = nn.CrossEntropyLoss() opt = torch.optim.AdamW(model.parameters(), lr=1e-3)

The loop you will copy forever

device = torch.device("cuda" if torch.cuda.is_available() else "cpu") model = TinyNet(16, 32, 2).to(device) for epoch in range(5): model.train() for xb, yb in loader: xb, yb = xb.to(device), yb.to(device) logits = model(xb) loss = loss_fn(logits, yb) opt.zero_grad() loss.backward() opt.step() model.eval() with torch.no_grad(): # validation metrics here — never step the optimizer pass torch.save(model.state_dict(), "tiny.pt") model.load_state_dict(torch.load("tiny.pt", map_location=device))

Hugging Face shortcut: AutoModelForCausalLM.from_pretrained(...) is still an nn.Module. LoRA / QLoRA wrap the same forward + backward loop with fewer trainable weights. You do not need a new mental model — you need less VRAM.

GPUs

Training and serving large models is a memory problem first. VRAM holds weights, activations (training), optimizer states (training), and the KV cache (decode). Speed comes after the model fits. An idle GPU waiting on a Python loop or a CPU dataloader is wasted money.

Adam optimizer states can be ~2× the weights. Activations scale with batch × sequence × layers. KV cache grows with every decoded token. If you OOM, shrink those — do not assume you “need A100s.”
ConceptPractical meaning
VRAMIf you OOM, shrink batch, sequence length, or use quantization / gradient checkpointing
UtilizationIdle GPU while waiting on CPU/data is wasted money. Watch nvidia-smi power and GPU-util %
fp16 / bf16Mixed precision: roughly 2× math throughput, smaller activations. bf16 is more stable on Ampere+
int8 / 4-bitWeight-only or activation quant for serving. More tokens/sec, possible quality drop — measure it
BatchingContinuous batching in vLLM / TGI is how APIs stay cheap. One-request-at-a-time is the expensive default
Tensor / pipeline parallelSplit a model across GPUs when it does not fit on one. Needed for big training, not for a 7B chat box

Rough VRAM intuition (inference, decoder)

Weights: about 2 bytes × parameters in fp16 (7B ≈ 14 GB). Add KV cache: scales with layers × heads × seq_len × batch. A long RAG prompt on a 70B model can blow past the weight file. Quantize (8-bit / 4-bit) to trade quality for fit.

nvidia-smi # memory-usage, GPU-util, power # if util is 5% and you are "slow", you are CPU-bound or unbatched
Cloud habit: Profile one request before you buy a bigger GPU. Many “we need A100s” problems are unbatched Python loops, a 32K prompt stuffed with unused PDF pages, or loading the model in fp32 by accident.

Checklist before you scale hardware

  • Is the model on GPU at all? (next(model.parameters()).device)
  • Are you in eval() + no_grad() / inference mode?
  • Is batch size 1 because nobody wired a queue?
  • Is sequence length 8K because the prompt includes the whole corpus?
  • Have you tried bf16 / 8-bit and measured quality on your eval set?

Checkpoint — move on when

  • You can draw a neuron (weights, bias, activation) and a training step (forward, loss, backward, update)
  • You can explain attention (Q, K, V), why long context is O(n²), and what the KV cache is for
  • You can pick encoder vs decoder well enough to choose an embedding model vs a chat model
  • You can run a tiny PyTorch loop, save weights, and read nvidia-smi without guessing
  • You treat VRAM as a budget: batch, sequence length, precision, then GPU size — in that order
