🏢 12. Enterprise AI Architecture

Step 12 of 12 — The difference between a demo and a company system: trust, cost, tenancy, and law.

The enterprise bar

A production AI engineer in a company designs a platform, not a single chatbot: identity, isolation, data contracts, model routing, spend controls, and an architecture that legal/security can approve. This category is how you sit in a design review and not get destroyed.

AuthN/Z belongs in your API, not in the prompt. RAG filters must apply before similarity search is returned to the model.

Governance

Who can change the system prompt? Who approves a new tool? Who looks at traces with PII? Set: model catalog, change tickets for prompt prod, eval owners, incident severity for "model said something illegal." Shadow AI (employees pasting data into public ChatGPT) is an architecture problem — give them a sanctioned gateway.

Cost optimization

  • Route: small model for classify, large for hard reasoning
  • Prompt cache, RAG instead of huge contexts, shorter max_tokens
  • Batch embeddings; don’t re-embed unchanged docs
  • Per-tenant and per-feature budgets; kill switches
  • Self-host only when utilization is high enough to beat API list price

Multi-tenancy

Isolation levels: shared app + tenant_id on every row and vector (default), siloed indexes for high-risk tenants, dedicated accounts for regulated ones. Never trust tenant id from the model. Row-level security in Postgres; metadata filter required on every vector query. Rate limits per tenant so one customer cannot starve the GPU pool.

Data engineering

AI is downstream of data. You need CDC or scheduled extracts, a warehouse/lake, quality checks, PII classification, and a documented path into the search index. Late-arriving facts and deletes must flow to the vector DB (tombstones). Feature/label stores still matter for classical ML next to LLMs.

Contract: source system of record → cleaned table → chunk job (versioned) → index. If you cannot replay it, you cannot debug it.

This is not legal advice — it is the checklist you bring to counsel. Architecture should make the compliant path the easy path.

Reference architecture

A typical enterprise AI platform:

  1. Edge: API gateway, WAF, auth (SSO), per-tenant quotas
  2. Orchestration: chat/workflow service, agent graphs, tool bus (MCP)
  3. Knowledge: parsers, chunk jobs, hybrid search, ACL-aware retrieval
  4. Models: router → vendor APIs and/or GPU serving
  5. Data: warehouse, object storage, secrets, encryption keys
  6. Control: eval service, prompt registry, cost explorer, audit log
  7. Observability: traces, metrics, alerts, incident runbooks
Anti-pattern: every team embeds OpenAI keys in a Streamlit app. Centralize the gateway; federate the use cases.
