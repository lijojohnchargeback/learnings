✨ 4. Generative AI & LLM Engineering

Step 4 of 12 — Treat models as unreliable computers with a token meter attached.

The job

LLM engineering is productizing next-token prediction: pick a model, bound the context, constrain the output, log traces, and control cost and latency. Prompting is the first lever; APIs and inference settings are the rest. The model is not a database, not a search engine, and not grounded unless you ground it.

Five stages you actually ship: the app, a prompt that mixes system + tools + RAG + user, a vendor API, constrained output, then traces for tokens, dollars, and latency. The orange token meter is the budget you never stop watching.
Stage in the diagramWhat it isWhat goes wrong if you skip it
1. User / appChat UI, ticket bot, or internal toolYou optimize the model instead of the product
2. Prompt builderSystem + tools JSON + retrieved chunks + user textInjection, bloated context, unversioned prompts
3. Model APIOpenAI, Anthropic, Gemini, Bedrock, or a local serverVendor lock-in, no timeout, no fallback on 429

Unreliable computer

Fluent text is not evidence. Retry, validate, cite, or refuse. Never let a raw completion hit a database or a customer without a gate.

Token meter

You pay for input + output. System prompts, tool schemas, RAG chunks, and retries are hidden meters that dominate cost.

Product levers

Model choice, context budget, output schema, sampling knobs, and traces. Prompting is only the first of those.

What “generative” covers (not only chat)

  • Text LLMs — decoder-only transformers that sample the next token. Chat, code, agents.
  • Diffusion / flow models — images, video, some audio. Different training loop than next-token prediction.
  • Speech — ASR in, TTS out; often a separate stack from the chat model.
  • This step — you productize LLMs as APIs. Images and voice get their own later steps.

LLMs

A large language model predicts the next token given previous tokens. Chat models add a conversation template (system / user / assistant). “Intelligence” is compressed statistics plus alignment. It is not a database and it is not grounded unless you ground it (RAG, tools, citations).

The existing next-token loop, with each box named. Production adds sampling, a stop reason, and a repeat until max_tokens or an end-of-sequence token — then you detokenize.

How a chat model is actually built

Modern assistants are not one training run. Skipping a stage shows up as a model that can complete text but cannot follow “answer in JSON” or refuses nothing.

Read the four panels left to right. Pretrain compresses the corpus. SFT teaches the chat format. Alignment steers style and safety. Serving is where your product lives — quantization, batching, and guardrails, not more pretraining.
PanelWhat happensWhat it does not do
1. PretrainingNext-token prediction on huge text/code corpora (web, books, code, papers)Does not teach “be a helpful assistant” or a guaranteed world model
2. SFTSupervised fine-tune on instruction → response pairs (format, tools, markdown, refusals)Does not add fresh weekly facts; quality of pairs beats volume of web text here
3. AlignmentRLHF (reward model + RL) or DPO (direct preference pairs). RLAIF uses AI judges at scaleDoes not guarantee factuality. Over-optimizing the reward can make the model sycophantic
4. ServingAPI or self-host: quantization, batching, safety filters, rate limitsThe weights are frozen unless you fine-tune again. Product quality is mostly prompts, retrieval, and evals
Grounding is extra. Pretrain + SFT + RLHF still hallucinate. If the answer must be true, retrieve evidence, call tools, or refuse. Alignment is about preferred style and policy, not a source of truth.

Tokens

Models do not see words. They see subword tokens from a fixed vocabulary (often 32K–200K IDs). English is roughly 0.75 words per token; code, URLs, CJK, and other languages differ — sometimes 2–3× more tokens for the same sentence. You pay for input + output tokens.

The sentence is four chips. The bill is not. Input is usually dominated by system + tools + RAG. Output is what the user sees, plus every retry you forgot to count.

Context windows

The window is the max tokens of prompt + generation the model can attend to. Long windows are not free: latency and price grow, and models still “lose” details in the middle. Prefer retrieval, summarization, and hierarchical memory over dumping a 200-page PDF.

The bar is a budget, not storage. Left is oldest; right is newest. If you pack retrieved docs until the dashed “output reserved” slice disappears, the model truncates from the left — often your system prompt.
Slice in the barWhat it holdsHow to keep it honest
System prompt (~8%)Role, policy, output contractKeep it short and stable; version it. If this drops, the model forgets the job
Chat history (~25%)Prior turns and tool tracesDrop oldest tool dumps; keep a rolling summary instead of infinite history
Retrieved docs (~40%)RAG chunks, tickets, wiki pagesTop-k after rerank, not “the whole PDF”. Metadata filters before ANN
User question (~7%)The current queryUsually cheap. Put it last (or follow the vendor’s recommended order)
Output reserved (~20%)Room for max_tokensAlways subtract this from the prompt budget. No reserve = truncated answers
  • Reserve budget for the completion (max_tokens) before you pack RAG
  • Put instructions first, retrieved evidence next, user query last — unless the vendor documents a different order
  • Drop oldest tool traces; keep a rolling summary
  • Advertised 1M windows still cost money and still miss the middle. Retrieval beats stuffing
Lost in the middle: Even when everything fits, models attend more to the start and end of the window. Put the critical instruction and the question at the edges; do not bury the only relevant chunk in position 40 of 80.

Prompting

Prompts are programs. Store them in files, version them, and evaluate. Techniques: role/system instructions, few-shot examples, chain-of-thought (when allowed), and “think then answer” only if you need reasoning and can afford tokens.

The red wall is the whole lesson. System is trusted code. User text and retrieved docs are data. They belong in the user/context slot — never concatenated into the system prompt. Version the file like prompts/support_v12.md.
Region in the diagramTreat asRule
Trusted: systemYour code / policyShort, versioned, no user strings interpolated in
Untrusted: userHostile by defaultCan contain “ignore previous instructions”. Delimit it
Untrusted: retrieved docsAlso hostileA wiki page can jailbreak you. Same boundary as the user
Git-style prompt fileAn artifactPR reviews, evals, A/B — not a string buried in a Jupyter cell
SYSTEM = """You are a support assistant for Acme. Answer only from the CONTEXT. If missing, say you don't know. Cite chunk ids. Never invent policy.""" def build_prompt(question: str, chunks: list[str]) -> str: ctx = "\n\n".join(chunks) return f"{SYSTEM}\n\nCONTEXT:\n{ctx}\n\nUSER:\n{question}"
Prompt injection: Treat retrieved docs and user text as data, not instructions. Separate them clearly; never concatenate untrusted text into the system prompt without a boundary. Tool results are untrusted too.

Structured output

Agents and UIs need JSON, not poems. Use JSON mode / tool calling / constrained decoding. Validate with Pydantic or Zod. Retry with the validation error as feedback — cap retries.

Schema first, then generate, then validate. The green path writes to the app. The red path sends the validator error back once. After two attempts, fail closed — do not loop forever on a confused model.
BoxJobFailure mode
SchemaFields, types, ranges (priority 1–5)Vague “return JSON” with no schema → extra keys, strings for numbers
JSON mode / toolsAsk the vendor to constrain decodingStill can be invalid against your schema. Always validate client-side
ValidatorPydantic / Zod / JSON SchemaParsing with json.loads only is not enough
Retry onceFeed the error text backUnbounded retries burn tokens and can oscillate
from pydantic import BaseModel, Field class Ticket(BaseModel): intent: str priority: int = Field(ge=1, le=5) needs_human: bool # 1) ask model for JSON (json_mode or tool call) # 2) Ticket.model_validate_json(raw) # 3) on ValidationError, retry once with the error text # 4) else: raise / send to human queue

Model APIs

OpenAI-compatible chat completions are the lingua franca. Wrap vendors so you can swap models. Always set timeout, max retries, and a fallback model for 429/5xx.

Product code talks to ChatClient, not to four SDKs. Primary vendor on the happy path; dashed arrow is the fallback when you hit rate limits or 5xx. Timeout and retry live on the client, not in each call site.

from openai import OpenAI client = OpenAI() # or base_url= for compatible servers resp = client.chat.completions.create( model="gpt-4.1-mini", messages=[ {"role": "system", "content": "Be concise."}, {"role": "user", "content": "List 3 RAG failure modes."}, ], temperature=0.2, max_tokens=400, timeout=30, ) print(resp.choices[0].message.content)
Compatibility: Many hosts speak the OpenAI chat schema (vLLM, TGI, Groq, Together, Azure). That is why the wrapper is worth it on day one — swapping is a config change, not a rewrite.

Fine-tuning

Fine-tune when you need a stable style, a private vocabulary, or a small model that must match a big one on a narrow task. Do not fine-tune to “add knowledge” that changes weekly — use RAG. Do not fine-tune before you have an eval set.

Walk the diamonds top to bottom. New weekly facts → RAG or tools. No special style → better prompts. No golden eval set → stop. Only then LoRA/QLoRA, and almost never a full fine-tune.
Diamond / leafMeaning in production
“Weekly facts?”Policies, prices, tickets, docs. Weights go stale; retrieval stays fresh
“Stable style / private vocab?”Brand voice, ICD codes, internal jargon, strict JSON the base model keeps missing
“Golden eval set?”Without it you cannot tell if LoRA helped or just overfit tonight’s examples

Inference

Inference is generating tokens. Settings change personality and cost. Decode is sequential: output length dominates latency even when the prompt is short.

Five knobs on one dashboard. Temperature and top_p change sampling. max_tokens is the hard stop. Streaming is UX, not a substitute for logs. The clock is a timeout. The bottom row is self-host — same product rules as a vendor API.

temperatureHigher = more random~0 for extraction/JSON; ~0.2–0.4 for support; ~0.7+ only if you want variety

Self-host later: vLLM, TGI, TensorRT-LLM, llama.cpp. Same product rules as the diagram’s bottom row: batching, queues, health checks, and a token meter. Quantization (AWQ, GPTQ, GGUF) trades quality for VRAM — measure on your eval set.

Checkpoint — move on when

  • You can ship a chat API with logging, token counts, timeouts, and JSON validation
  • You can walk the training-pipeline diagram and explain what each stage does not buy you
  • You treat the context window as a budget with a reserved output slice
  • You can explain when fine-tuning is the wrong tool
  • You treat prompts as versioned artifacts with evals, and untrusted text stays out of the system slot
