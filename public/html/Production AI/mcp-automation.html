🔌 7. MCP, Tools & AI Automation

Step 7 of 12 — Standardize how models call the world: protocols, APIs, and workflow engines.

Two layers

Tooling for agents/IDEs (MCP, function calling) and business automation (n8n, Make, Zapier, queues). Production AI engineers build the first and often wire the second. The shared rule: least privilege, audit logs, and no secrets in prompts.

Top = how the model reaches systems. Host → MCP client → servers exposing tools/resources/prompts. Bottom = how the business reacts to events. Webhook → queue → worker (maybe with an LLM step) → Slack/ticket. Same security rule on both layers.

MCP / tools

Give an assistant a typed catalog of actions and readable context. The model proposes; your code executes.

iPaaS glue

n8n / Make / Zapier connect SaaS fast. Great for ops; weak as the core of a product SLA without your own monitoring.

Durable workers

Queues, Temporal, Step Functions — retries, idempotency, and dead letters when the path must not silently die.

When to use what

Most teams over-automate with Zaps or under-automate with a single mega-agent. Pick the layer from the job.

Read the diamonds. Assistant touching systems → MCP/tools. Ops SaaS glue → iPaaS. Product durability → queue/Temporal. An LLM inside a workflow is a step, never the source of truth for control flow.

MCP (Model Context Protocol)

MCP is an open protocol for connecting AI apps to tools and data: resources (read), prompts (templates), and tools (actions). Clients (Cursor, Claude Desktop, custom agents) speak MCP to servers you run.

Primitives on the left, transport on the right, loop at the bottom. Local IDEs usually use stdio. Remote servers need Streamable HTTP (or SSE) plus auth. The model never “is” MCP — it picks a tool name; the client executes.
PrimitiveUseExample
ToolsActions with side effects or live queriescreate_ticket, query_metrics
ResourcesReadable context the host can attachfiles, ticket JSON, DB schemas
PromptsReusable instruction packs“triage this incident” template
# Conceptual MCP server (Python SDK pattern) # - list_tools / call_tool # - list_resources / read_resource # Transport: stdio for local IDEs, Streamable HTTP for remote @server.tool() def get_order(order_id: str) -> dict: """Fetch a single order by id (read-only).""" return db.fetch_order(order_id) # parameterized, scoped
Production MCP: authenticate remote servers, scope tools per user, rate-limit, and never mount a shell tool on a shared server.

Function calling

Vendor-native tool calling (OpenAI, Anthropic, Gemini) is how models emit structured tool requests. MCP often sits underneath as the catalog; the model still needs a schema. Validate arguments server-side even if the model “promised” types.

Not rivals — layers. Left: classic tool_call loop against schemas you pass into the chat API. Right: MCP makes those tools a pluggable catalog across hosts. Underneath, the model still emits a structured call.
tools = [{ "type": "function", "function": { "name": "get_order", "description": "Fetch one order by id", "parameters": { "type": "object", "properties": {"order_id": {"type": "string"}}, "required": ["order_id"], }, }, }] # Model returns tool_calls → you execute → append role=tool → continue

Safe tool design

Every tool is an API you will be paged for. Design for failure, abuse, and prompt injection — not for demos.

Happy path is teal; red is banned. Schema → allowlist → secrets from a vault → timeout → truncate results → audit. Never: arbitrary SQL, open HTTP proxy, or a shell on a shared MCP server.
RulePractice
Narrow > genericget_order(id) beats http_request(url)
Validate twiceJSON Schema at the edge; business rules in the handler
Timeouts + budgetsPer-tool deadline; max result bytes back to the model
Errors are dataMap 4xx → clear message; 5xx → “retry later”, not a stack trace dump
Idempotent writesClient-supplied idempotency key for creates/charges

APIs as tools

Each external API becomes a narrow tool, not a generic http_request. Allowlist hosts. Inject auth from a secret store. Map 4xx to the model as “user error” and 5xx as “retry later.”

ALLOWED = {"https://api.github.com"} async def github_get(path: str) -> str: url = "https://api.github.com" + path if not url.startswith(tuple(ALLOWED)): raise ValueError("host not allowed") # Authorization: Bearer from env / vault — never from the model ...
  • One tool per use-case (list_open_prs), not one mega “GitHub API”
  • Strip secrets and PII from tool results before they re-enter the prompt
  • Circuit-break flaky vendors so the agent can degrade gracefully

Database tools

Prefer parameterized queries and views. Give the agent a small set of queries (get_order, list_open_tickets), not “run any SQL.” For analytics, a read replica and a hard row limit.

Never: execute(user_sql) from the model. Prompt injection + SQL = data breach.
PatternWhy
Named queries onlyYou own the plan and indexes
Bound parametersNo string concatenation of IDs or filters
Row + time limitsStop a runaway scan from melting the replica
Tenant predicateAlways AND tenant_id = :caller in the tool layer

n8n

Open, self-hostable workflow tool. Good for ops: webhook → LLM node → Slack/ticket. You can keep data in your VPC. Treat workflows as code: export, review, version. Put API keys in n8n credentials, not in node fields that get logged.

  • Self-host when PII must not leave your network
  • Pin workflow versions; review diffs like application code
  • Use error workflows + retries; do not rely on “it usually works”

Make

Visual automation (formerly Integromat). Strong SaaS connectors. Same caution as Zapier: great for internal glue, weak as the core of a product SLA unless you add monitoring and retries you control.

Zapier

Fastest way to connect SaaS for non-engineers. AI actions exist, but you still need: rate limits, PII policy, and an owner. Promote critical paths to your own workers when volume or compliance grows.

Workflows

A workflow is a directed graph with retries: ingest → classify → human review → notify. LLMs are steps, not the orchestrator of record. Use Temporal, Step Functions, or a simple queue if you need durability. Visual tools are for edges; your domain logic belongs in tested functions.

OrchestratorFits
n8n / Make / ZapierInternal ops, low-stakes SaaS glue
Queue + workersSimple async jobs you own
Temporal / Step FunctionsLong-running, compensations, strict retries
Agent loop aloneRarely — too easy to wander and burn tokens

Event-driven automation

Triggers: webhooks, pub/sub, inbox, cron. Pattern: event → validate signature → enqueue → worker → LLM/tool → persist → emit result. Idempotency key = event id. Dead-letter after N failures. Alert on queue depth.

Follow the spine. Validate → dedupe by event id → queue → worker (LLM optional) → persist → emit. Failures after N tries go to the DLQ with an alert — not into a silent void.
# Webhook handler sketch def handle_stripe(event): if seen(event["id"]): return enqueue("refund.review", event) mark_seen(event["id"])

Advanced MCP patterns

Once one local server works, production asks for multi-server catalogs, remote auth, approval gates, and traces.

Four upgrades. Route across GitHub/DB/Docs servers. Scope remote tools with OAuth per user. Pause dangerous writes for a human. Trace every call: name, latency, args hash, success/fail.
PatternIdeaWatch out
Multi-server routingOne host, many MCP servers; filter tools by taskTool-name collisions; too many tools confuse the model
Remote MCP + OAuthUser token → server scopes tools to that principalToken leakage into logs/prompts
Sampling / elicitationServer asks the host/model for help mid-toolNested calls and cost explosions
Resource subscriptionsPush updates when a file/ticket changesFan-out and stale caches
Tool result budgetsHard cap tokens returned into contextTruncation that hides the answer — summarize first

Security & tenancy

  • Least privilege: read tools by default; write tools behind roles + HITL
  • Tenant isolation: pass the authenticated principal into every tool; never trust model-supplied tenant_id
  • Secret hygiene: vault / env only; redact from traces and tool results
  • Prompt injection: treat tool outputs and retrieved docs as untrusted data
  • Supply chain: pin MCP server versions; review community servers before install
Never mount an unrestricted shell, arbitrary SQL, or open HTTP proxy on a shared or remote MCP server. That is remote code execution with a chat UI.

Observability

If you cannot answer “which tool failed for which user,” you do not have production tooling.

SignalWhy
tool_name, latency_ms, successFind slow/flaky tools
args hash (not raw secrets)Debug without leaking PII
tokens in/out + $Catch agent loops early
approval_id for HITLAudit who allowed a write
queue depth / DLQ rateOps health for event paths

Human-in-the-loop

Any tool that moves money, deletes data, emails customers, or changes IAM should pause for approval — or be unreachable to the model.

def refund_order(order_id: str, amount_cents: int, actor: User) -> str: require_role(actor, "support_lead") ticket = create_approval("refund", {"order_id": order_id, "amount_cents": amount_cents}) return f"Pending approval {ticket.id}" # worker executes after approve
Prefer propose → approve → execute over “the model already charged the card.” Store the approval audit trail next to the tool trace.

Checkpoint — move on when

  • You can ship an MCP or function-calling tool with auth, allowlist, timeout, and audit log
  • You can explain when to use MCP vs n8n vs a durable queue worker
  • You never let a model run arbitrary SQL, HTTP, or shell
  • Write tools that matter go through HITL; tenants cannot see each other’s tools/data
  • You can trace a failed automation from webhook → queue → tool → DLQ
