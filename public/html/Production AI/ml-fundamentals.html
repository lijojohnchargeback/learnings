🤖 2. AI / ML Fundamentals

Step 2 of 12 — Classical ML vocabulary so you can evaluate models, not just call APIs.

Why this still matters in the LLM era

LLMs did not replace ML; they sit on top of it. Ranking, routing, fraud, churn, latency forecasts, and “is this RAG answer grounded?” are still classifiers and regressors. A Production AI engineer who cannot read a confusion matrix will ship a 99% accurate spam filter that misses every real attack — because the class is rare and accuracy is the wrong number.

This step is not “become a Kaggle grandmaster.” It is the mental model you reuse for every LLM eval: split data honestly, pick a metric from the cost of being wrong, beat a cheap baseline, then monitor drift.

Read the image left to right. The dashed loop is the part notebooks skip: production data shifts, so you retrain. Skip the baseline box and you will not know whether the fancy model earned its complexity.

What you will be able to do

  • Explain AI vs ML vs deep learning vs generative AI without marketing language
  • Pick supervised, unsupervised, or self-supervised for a real product problem
  • Split data by time, spot leakage, and refuse a fake metric
  • Train a sklearn baseline and defend precision, recall, MAE, or RMSE
  • Encode categoricals, scale numbers, and treat prompt fields as features

AI vs ML vs deep learning vs GenAI

These words get stacked in pitch decks as if they were synonyms. They are a containment hierarchy plus one overlapping product category. AI is the field. Machine learning is one way to build AI (learn from data instead of only writing rules). Deep learning is machine learning with multi-layer neural nets. Generative AI is a job the model does — produce new text, images, audio, or code — and it is usually deep learning, but not always a chatbot.

Read the nesting. A rule engine is AI but not ML. A logistic regression spam filter is ML but not deep learning. A Transformer is deep learning. GPT is generative AI; a churn model is not, even if it uses a neural net. The footnote on the image is the production rule: start with the cheapest system that hits the metric.
Same idea, different drawing (from the AI fundamentals guide). Outer ring = the field. Middle ring = learn from data. Inner ring = neural nets. The three boxes along the bottom are specializations, not a new layer of intelligence: Transformers are an architecture, LLMs are large sequence models, GenAI also includes diffusion. Use this image when someone asks “is ChatGPT ML or AI?” — the answer is both, and also deep learning.

Production view

Start with the cheapest system that meets the metric. A regex + logistic regression can beat a 70B model on a narrow task (PII detection, intent, routing). Use an LLM when the input is messy language and the output is language — and still put a classifier in front to route, score, or refuse.

Supervised vs unsupervised (and the siblings)

The question is not “which algorithm.” It is what signal you have. If every row has a target you care about, it is supervised. If you only have X and want structure, it is unsupervised. If labels come from the data itself (next token, masked patch), it is self-supervised — that is how LLMs are pretrained.

How to read this image. Column 1: each house has a price — that pair (X → y) is supervised. Column 2: colored blobs with no labels — the algorithm invented the groups. Column 3: the robot (agent) acts, the world (environment) returns a new state and a reward; that loop is how AlphaGo and some LLM alignment (RLHF) work. Self-supervised is missing from the drawing on purpose: it looks like unsupervised data but trains like supervised (predict the next token).

1. Supervised

Labeled examples (x, y). Classification and regression. Most business ML, and most LLM evals (thumbs up/down, grounded/not, toxicity score).

  • Classification: y is a class — spam, intent, ticket priority, “this citation supports the claim”
  • Regression: y is a number — latency, token cost, CSAT, remaining useful life

2. Unsupervised

No labels. Clustering, dimensionality reduction, anomaly detection. Useful for segments (“these tenants behave alike”) and “this request looks weird.” Do not treat cluster IDs as ground truth unless a human named the clusters.

3. Semi-supervised

A little labeled data plus a lot of unlabeled data. Typical when labels are expensive (medical images, legal review). The unlabeled mass helps the model learn the shape of the input space.

4. Self-supervised

Labels from the data itself: next token, masked token, masked image patch. This is how LLMs and many vision models are pretrained. You do not need humans to label every token — the text is the label.

5. Reinforcement learning

An agent takes actions, observes a new state, and gets a reward. Exploration vs exploitation is the hard part. In production AI you mostly meet RL as RLHF (a reward model scores completions) or as a bandit that picks which prompt/model to serve.

Train / validation / test — and leakage

A model that memorizes the training set is useless. You need three buckets with different jobs:

  • Train: fit parameters
  • Validation: pick hyperparameters, thresholds, and when to stop
  • Test: touch once, at the end, to report the number you will defend

For anything that happens over days in production — tickets, transactions, chat logs — split by time, not at random. Random splits leak the future into the past.

Left panel: time flows left to right; test is locked (you look at it once). Right panel: two classic lies. “Shuffle split” mixes January and December, so the model peeks at tomorrow. “Feature leakage” uses a column that only exists after the outcome (purchased_after_churn). If your metric looks too good, look here first.
Leakage: If a feature is only known after prediction time, or includes the label, your metric is a lie. Other silent leaks: IDs that encode the target, preprocessing fit on train+test, duplicates of the same user in both sides, and RAG chunks that contain the answer because you indexed the eval set.
# Time-based split — production events, not i.i.d. rows df = df.sort_values("event_time") cut = int(len(df) * 0.8) X_train, y_train = df.iloc[:cut].drop(columns=["y"]), df.iloc[:cut]["y"] X_test, y_test = df.iloc[cut:].drop(columns=["y"]), df.iloc[cut:]["y"] # Group split — keep the same user / tenant / session on one side from sklearn.model_selection import GroupShuffleSplit gss = GroupShuffleSplit(n_splits=1, test_size=0.2, random_state=42) train_idx, test_idx = next(gss.split(X, y, groups=df["user_id"]))

Classification

Predict a class: spam vs ham, intent, ticket priority, “this RAG answer is grounded.” Classes can be binary or multi-class. Imbalance is the default in production — fraud, PII, and incidents are rare. Accuracy on a 1% positive class can be 99% while you catch nothing.

Left: the model draws a boundary; output is a class (spam/ham, fraud/ok). Right: the model draws a line through numbers; the dashed verticals are residuals — the errors MAE and RMSE measure. If your y is a score you will threshold later (toxicity 0–1), it is still classification at the product layer even if you trained a regressor.

The confusion matrix

Every classification metric is a story about four counts. Draw this on a whiteboard before you pick a number:

Read the grid, then ignore any tiny formula art. TP = you said yes and you were right. FP = you said yes and you were wrong (false alarm). FN = you said no and missed it. TN = you said no and it really was no. Precision = TP / (TP + FP) — when you flag fraud, how often are you right? Recall = TP / (TP + FN) — of all real fraud, how much did you catch? You cannot maximize both without changing the data or the cost of review.
MetricFormulaUse when
Accuracy(TP + TN) / NClasses are balanced and all errors cost the same (rare)
PrecisionTP / (TP + FP)False positives are expensive (flagging fraud, blocking users)
RecallTP / (TP + FN)False negatives are expensive (missing cancer, missing PII)
F1Harmonic mean of precision and recallYou need a single number on imbalanced data
ROC-AUC / PR-AUCRanking quality across thresholdsPR-AUC when positives are rare; ROC-AUC can look fine while PR is bad

Thresholds are a product decision

Most models output a probability. The 0.5 default is arbitrary. Plot precision and recall vs threshold, then pick the operating point from the cost of a false alarm vs a miss. For LLM judges, the same idea applies: “score ≥ 0.8 means grounded” is a threshold you must tune on a labeled set.

from sklearn.metrics import classification_report, confusion_matrix y_pred = clf.predict(X_test) print(confusion_matrix(y_test, y_pred)) print(classification_report(y_test, y_pred, digits=3)) # Operating point: raise threshold to buy precision, lower it to buy recall proba = clf.predict_proba(X_test)[:, 1] y_strict = (proba >= 0.8).astype(int)

Regression

Predict a continuous value: latency, token cost, CSAT, remaining useful life, expected tokens in a prompt. Linear models are still strong baselines and are explainable — coefficients you can show a PM. Trees and boosting win on messy tabular data with nonlinearities and missing values.

MetricMeaningWatch out
MAEAverage absolute error — robust, easy to explain (“off by 12 ms”)Treats a 100 ms miss like ten 10 ms misses
RMSEPenalizes large errors more — good when outliers hurtOne bad row can dominate the number
MAPEPercent error — useful for finance-style reportingExplodes when true values are near 0; avoid for latency
R²Fraction of variance explained vs predicting the meanCan look high while MAE is still unusable for the product
from sklearn.linear_model import Ridge from sklearn.metrics import mean_absolute_error, mean_squared_error model = Ridge(alpha=1.0) model.fit(X_train, y_train) pred = model.predict(X_test) print("MAE", mean_absolute_error(y_test, pred)) print("RMSE", mean_squared_error(y_test, pred, squared=False))

LLM crossover

Token billing, time-to-first-token, and “how long will this agent run?” are regression problems. A Ridge model on prompt length + tool count often beats a gut feel — and is cheaper than asking GPT to estimate GPT’s cost.

Evaluation

Evaluation is a product decision. Choose the metric from the cost of being wrong, then lock a validation protocol: holdout, k-fold, or time-based split. For LLMs you reuse this mindset with offline eval sets, LLM-as-judge, and human ratings — the protocol matters more than the library.

How to read this image. Blue dots = data. Teal curve = the true pattern. Orange line = what the model learned. Left (underfit / high bias): too simple — training and validation error are both high. Middle (good fit): follows the wave, ignores noise — both errors low. Right (overfit / high variance): wiggles through every point — training error looks amazing, validation error is bad. In production this is “99% on the notebook, 60% after launch.” Fix underfit with a richer model or better features. Fix overfit with more data, regularization, dropout, or a simpler model. Always watch train vs validation together.
  • Baseline first: majority class, last week’s average, keyword matcher. If you cannot beat that, you do not have a model — you have a ritual.
  • Calibration: predicted probabilities should match observed rates if you threshold. A model that says 0.8 should be right ~80% of the time in that bucket.
  • Slices: report metrics by language, tenant, or traffic source. Averages hide the one customer who generates the support tickets.
  • Online vs offline: A/B tests catch distribution shift that notebooks miss. Offline eval is necessary and not sufficient.
  • Error analysis: read 20 failures. Patterns (one vendor’s PDF, one locale, one prompt template) beat another hyperparameter sweep.
LLM eval trap: “The model sounds good” is not a metric. Build a golden set of 50–200 labeled examples, freeze it, and rerun it on every prompt or model change — same idea as a unit test suite.

Feature engineering

Features are how you turn raw logs into something a model can learn. Production ML is often 80% data work. For LLM systems the same job is chunking, metadata filters, and prompt fields — they are features with different names.

Follow the arrows. Raw logs (left) are not model-ready. Numeric columns go through a scaler so tokens and latency_ms share a scale. Categorical columns (model, region) become one-hot bits. Those branches join into one vector, then a classifier. The red badge is the production lesson: a column that only exists after score time is leakage — drop it. The small callouts (embeddings, 1h/7d windows) are how you bring text and time into the same pipeline.
TechniqueWhenPitfall
One-hot / target encodingCategorical columnsTarget encoding leaks if you fit it on the whole dataset
Scaling (Standard / MinMax)Distance-based and regularized linear modelsTrees do not need it; still fit the scaler on train only
Binning, logs, ratiosSkewed counts, money, latenciesLog of 0; invent a +1 or a missing flag
EmbeddingsText, images — bridge to RAG and deep learningMixing embedding models without re-indexing
Time windowsCounts in last 1h / 7d — classic for fraud and opsUsing the current event in the window (leakage)

LLM crossover: Chunking, metadata filters, and prompt fields are feature engineering for retrieval and generation. A “user_tier” field in the system prompt is a feature. So is “retrieved_at” if you accidentally include tomorrow’s doc in today’s index.

Classical models you should still know

Before you fine-tune or call an API, know the cheap models that still win on tabular data. A Production AI stack often looks like: boosting model for structured events + embeddings/LLM for language.

FamilyStrengthUse when
Linear / logistic / RidgeFast, stable, explainable coefficientsBaseline, well-scaled numeric features, you need to debug
Decision treesNonlinear, missing values, no scalingTeaching, simple rules, tiny datasets
Random forestBags of trees; hard to overfit badlySolid tabular default before boosting
Gradient boosting (XGBoost, LightGBM, CatBoost)Usually the best on tabular competitions and production tablesChurn, fraud, ranking, conversion — if you have labels
k-NN / SVMSimple geometry / marginsSmall data; rarely the production default in 2026
Do not use an LLM as a classifier until a boosting model (or even logistic regression) has lost. Language in, language out is the LLM’s job. “Is this JSON valid?” and “which of 12 ticket queues?” are usually not.
