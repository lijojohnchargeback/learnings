📚 5. RAG & Knowledge Engineering

Step 5 of 12 — Retrieve the right evidence, then generate. Most “hallucinations” are retrieval failures.

What RAG is

Retrieval-Augmented Generation fetches relevant documents at query time and puts them in the prompt so the model answers from your data. Knowledge engineering is the boring work that makes it true: parsing, chunking, metadata, ACLs, freshness, and evals.

Two paths, one system. Ingest builds the index offline. Query walks the live path: embed → retrieve (with filters) → optional rerank → prompt → cited answer. The dashed loop is what notebooks skip: measure failures, then re-chunk or re-index.
Same idea at the call-site level. If the answer is wrong, open the retrieved chunks before you blame the model. No evidence in top-k → retrieval bug. Evidence present but ignored → prompt or generation bug.

Canonical pipeline

  1. Ingest: parse PDF/HTML/tickets → clean text + metadata
  2. Chunk + embed + index (with delete-by-source-id)
  3. Query: rewrite → embed → retrieve → (optional) hybrid + rerank
  4. Generate with citations → log chunk ids → evaluate

Not a database

The LLM compresses context into fluent text. Citations and faithfulness checks are how you keep it honest.

Retrieval first

If the right chunk never enters the prompt, no amount of prompt craft or model upgrade will save you.

Knowledge engineering

Parsers, ACLs, freshness, and golden sets are the product. The vector DB is plumbing.

Top RAG techniques

These are the techniques you will actually see in papers, vendor blogs, and production stacks. Treat them as a menu ordered by complexity — ship vanilla + hybrid + rerank first; graduate only when a golden-set failure demands it.

Left → right, then down. Teal = baseline. Orange = retrieval upgrades that usually win on docs/support. Purple = loops and graphs — high power, high cost. The footer rule is the whole curriculum: start left, move right only when eval fails.
#TechniqueWhat it doesUse whenCost / risk

2Hybrid search BM25/sparse + dense vectors, fused (often RRF) SKUs, error codes, names, mixed jargon Low–medium. Production default for support/docs
3Cross-encoder rerank Retrieve wide (30–50), score query+chunk jointly, keep 3–8 Recall@50 OK but precision@5 poor +50–200ms. Best ROI after hybrid

7Contextual retrieval Prepend doc/section context to each chunk before embed (Anthropic-style) Chunks lose title/scope (“the policy says…”) Ingest LLM rewrite = $ and latency
8Corrective RAG (CRAG) Grade retrieved docs; if weak, web/fallback search or rewrite Corpus gaps; open-domain facts Extra graders + tools; must cap steps
9Self-RAG Model decides when to retrieve and critiques its own answer Mixed questions that sometimes need no retrieval Needs special training or careful prompting
10Adaptive / routed RAG Classifier or LLM routes to FAQ / tickets / no-retrieve / agent Multiple indexes or product surfaces Mis-routes are silent failures — eval per route

Recommended progression (production)

  1. Vanilla + structure-aware chunking + metadata filters
  2. Add hybrid (BM25 + dense)
  3. Add rerank when precision@k stalls
  4. Add multi-query / HyDE only if recall@k is still soft
  5. Upgrade chunking to parent–child or contextual if context is the failure
  6. Reach for Graph / Agentic / CRAG only with a labeled failure mode

Baseline stack

Vanilla + hybrid + rerank covers most internal docs and support bots. Measure before anything fancier.

Retrieval upgrades

Multi-query, HyDE, parent–child, contextual retrieval fix “wrong neighborhood” and “lost context” failures.

Control loops

CRAG, Self-RAG, adaptive routing, Graph, Agentic — powerful, expensive. Cap steps and eval each path.

Technique shopping is a smell. If you cannot name the metric that failed (hit@k, precision, faithfulness), do not add a new RAG pattern — fix chunking, filters, or freshness first.

Embeddings

An embedding is a dense vector that places similar meaning nearby. Use a dedicated embedding model (not a chat model). Same model at index time and query time. Watch dimension, multilingual support, max tokens, and instruction prefixes (e.g. query: vs passage:).

How to read this. Left: text → vectors. Center: nearest neighbors in meaning-space — the query star should land in the right cluster. Right: cosine cares about angle, not magnitude. The red badge is non-negotiable: one model per index.
from openai import OpenAI client = OpenAI() def embed(texts: list[str]) -> list[list[float]]: r = client.embeddings.create(model="text-embedding-3-small", input=texts) return [d.embedding for d in r.data]
ChoiceWhy it matters
DimensionHigher dims can help quality; they always cost storage and ANN latency
Matryoshka / truncationSome models let you keep the first N dims — measure before you cut
DomainLegal/medical/code often need domain embeddings or fine-tuned ones
Batch + cacheCache embeddings by content hash; never re-embed unchanged chunks
Never mix models in one index. Re-embed everything if you change the embedding model — including the query path.

Vector databases

Stores vectors + metadata and runs ANN search (HNSW, IVF, DiskANN). Options: pgvector (start here if you already have Postgres), Pinecone, Weaviate, Qdrant, Chroma, OpenSearch / Elasticsearch k-NN, Milvus.

NeedLook for
ACLsMetadata filters on tenant / role before ANN, not after
UpdatesDelete-by-source-id and re-index a document atomically
HybridSparse + dense in one query, or two indexes + fusion
OpsBackups, replicas, SLO on p95 query latency, index rebuild story
ScaleSharding by tenant, quantized vectors (PQ/SQ) when RAM hurts
ANN is approximate. You trade perfect recall for speed. Raise ef_search / probes when eval recall is soft; do not “just take top-3” and hope.

Chunking

Chunks are the unit of retrieval. Too big: diluted similarity. Too small: missing context. Overlap helps sentences that straddle a boundary. Prefer structure: headings, pages, tickets, functions — not only N characters.

Pick from the query, not from a blog default. Fixed size is a baseline. Structure-aware wins on docs. Parent-child retrieves small, generates with large. Contextual / late chunking prepends document context so every chunk knows where it came from.
def chunk(text: str, size: int = 800, overlap: int = 120) -> list[str]: out, i = [], 0 while i < len(text): out.append(text[i:i + size]) i += size - overlap return out

Better: split on markdown headings, then pack until a token budget. Keep source, title, page, updated_at, tenant on every chunk.

StrategyWhenWatch out
Fixed + overlapQuick baseline, chat logsCuts mid-table / mid-code

Ingestion & freshness

Production RAG dies on stale or duplicated chunks. Treat ingest like an ETL job with idempotent upserts.

def upsert_document(doc_id: str, text: str, meta: dict): vector_db.delete(filter={"source_id": doc_id}) # remove old chunks pieces = structure_aware_chunk(text) vectors = embed(pieces) vector_db.upsert([ {"id": f"{doc_id}:{i}", "vector": v, "text": t, "metadata": {**meta, "source_id": doc_id, "chunk_i": i}} for i, (t, v) in enumerate(zip(pieces, vectors)) ])
  • Parsers: Unstructured, LlamaParse, custom HTML → markdown, OCR for scans
  • Dedup: content hash; skip embed if unchanged
  • Freshness: updated_at filter or boost; tombstone deleted docs
  • PII: redact or segment before embed if policy requires

Retrieval

Always log the retrieved chunk ids and scores. If the answer is wrong, first ask: was the evidence in top-k?

def retrieve(q: str, k: int = 8, tenant: str | None = None): qv = embed([q])[0] filt = {"tenant": tenant} if tenant else None return vector_db.query(qv, top_k=k, filter=filt)
top-k is a product knob. Too small → miss evidence. Too large → noise, cost, and prompt dilution. Measure hit@k on a golden set before you “feel” a number.

Query transformation

When users ask like humans (vague, multi-part, or jargon-light) and your corpus is written like docs, rewrite before you search.

Three levers. Multi-query raises recall by unioning paraphrases. HyDE embeds a made-up answer document when queries and passages live in different styles. Step-back asks a more abstract question first. All of them spend tokens — gate them on low recall@k, not by default.
TechniqueIdeaCost
Multi-queryGenerate 3–5 paraphrases; union retrieve; dedupeN× retrieve (+ 1 LLM call)
HyDELLM writes a hypothetical passage; embed that1 generation + 1 embed
Step-backAsk a broader question, then the specific oneExtra retrieve pass
Query routingClassifier/LLM picks index or tool (FAQ vs tickets)Small; huge when corpus is mixed

Reranking

Bi-encoders (embeddings) are fast and approximate. A cross-encoder reranker reads query+chunk together and scores relevance. Pattern: retrieve 30–50, rerank to 3–8.

Worth it when latency budget allows (~50–200ms extra) and eval shows recall@50 is fine but precision@5 is not.

Hybrid search

Keyword search (BM25 / sparse) wins on SKUs, error codes, names, and exact phrases. Vectors win on paraphrase. Fuse with RRF (reciprocal rank fusion) or a weighted score. This is the production default for support and docs.

Keyword for IDs, vectors for meaning, rerank for precision. Do not skip BM25 because “embeddings are smarter” — users paste ticket numbers and product codes every day.
def rrf(rank_lists, k=60): scores = {} for ranks in rank_lists: for r, doc_id in enumerate(ranks, start=1): scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (k + r) return sorted(scores, key=scores.get, reverse=True)

Metadata filters & ACLs

Multi-tenant RAG without pre-filters is a data leak waiting to happen. Similarity search will happily return a neighbor from another customer.

Filter before ANN, not after. Post-filtering means you scored secret neighbors and then threw them away — and you may return fewer than top-k. Same query, different tenants → different worlds.
  • Store tenant, roles, doc_acl, sensitivity on every chunk
  • Pass the authenticated principal into every retrieve call
  • Test with two tenants and the same query in CI
Never put retrieved text into the system prompt as trusted instructions. Treat corpus + user text as data. A poisoned doc can jailbreak as easily as a user message.

Advanced patterns — pick from the failure mode

Do not start with Graph RAG or agents. Start with hybrid + rerank + eval. Graduate when a specific failure shows up on the golden set.

Left → right by complexity. Graph when answers need multi-hop relations. Agentic when one retrieve pass is not enough. Multimodal when the truth lives in tables and screenshots, not markdown.

Graph RAG

Extract entities and relations (or use an existing knowledge graph), retrieve a subgraph relevant to the question, then generate. Wins on “who owns X and what depends on it?” style questions where flat chunks miss the join.

Use whenSkip when
Multi-hop facts across docsFAQ / single-paragraph answers
You already have a KG or CRM graphYou cannot maintain entity quality
Eval shows missing relational evidenceYou have not tried hybrid + rerank yet

Agentic RAG

An LLM loop that can search, read, critique, and search again — with a hard max_steps and timeout. Useful for research-style questions; dangerous for cost and latency if every chat message becomes an agent.

def agentic_rag(question: str, max_steps: int = 4) -> str: notes = [] for _ in range(max_steps): plan = llm.decide(question, notes) # search | answer | refuse if plan.action == "answer": return generate_with_citations(question, notes) hits = hybrid_retrieve(plan.query, k=8) notes.append(critique(question, hits)) # keep / drop / need more return "Stopped: max retrieval steps."
Cap steps, tokens, and wall time. Log every tool call. Prefer a fixed graph (retrieve → critique → maybe second retrieve) over an open-ended ReAct loop for customer-facing apps.

Multimodal RAG

PDFs are not text. Tables, screenshots, and diagrams need OCR, table extractors, or vision embeddings. Options: caption images into text and embed; or use a multimodal embedding space (image+text). Store the original asset URL so the UI can show the figure, not only the caption.

  • Table → markdown / CSV chunk with page number
  • Figure → caption + thumbnail URL in metadata
  • Slide decks → one chunk per slide + speaker notes

RAG evaluation

Build a golden set of 50–200 real questions with labeled source docs. Automate with LLM-as-judge only after you sample-check the judge. Track regressions when you change chunking or models.

Metrics tell you where it broke. Hit@k / context recall = did evidence arrive? Precision = was noise low? Faithfulness = did the model stick to context? Citation accuracy = do footnotes lie? The flowchart below the cards is the debug order.
MetricQuestion it answers
Context recall / hit@kDid we retrieve a chunk that contains the answer?
Context precisionAre retrieved chunks actually relevant?
FaithfulnessDoes the answer stick to the context?
Answer relevanceDoes it address the user question?
Citation accuracyDo cited chunks support the claims?

Debug playbook

  1. Open the trace. List chunk ids and scores for the failing question.
  2. Evidence missing from top-k? Fix chunking, hybrid, query rewrite, filters, or index freshness — not the prompt.
  3. Evidence present? Tighten the system instructions, require citations, lower temperature, or add a faithfulness check.
  4. Add the failure to the golden set before you change anything else.
Frameworks (LangChain, LlamaIndex, Haystack) are fine once you can write the pipeline without them. Learn the failure modes first; then pick a library for connectors and tracing.

Checkpoint — move on when

  • You can walk the top-12 techniques map and pick the next upgrade from a failed metric
  • You can ingest a corpus, retrieve with metadata filters, and cite sources
  • You run hybrid + optional rerank and know why each is on
  • You have an eval set and know your hit@k and faithfulness
  • You can debug a bad answer by looking at retrieved chunks first
  • You can explain when Graph / Agentic / Multimodal is worth the complexity
