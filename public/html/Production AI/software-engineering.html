🧑‍💻 Software Engineering — Introduction

Category introduction — the map of how computers, networks, and software domains fit together so you can ship real systems (also Step 1 of the Production AI Engineer path).

What this category is

Software engineering is how you turn ideas into running systems: hardware and OS underneath, internet in between, then frontend, backend, data, AI, and cloud on top — with tests, Git, and operations so it stays up. This page is the introduction to that map. Deeper modules on this site cover each stack in more detail.

How to use this intro: read Computer foundations → Domains → Languages → Application core → Engineering basics → Daily craft → Production. Then open the related category modules below for depth.

What you will be able to do

  • Explain hardware, OS, and internet basics (and why GPUs/VRAM/latency matter)
  • Map the five domains: frontend, backend, data science, AI/ML, and cloud
  • Write backend services in Python and Node.js / TypeScript
  • Design REST/JSON APIs with auth, validation, and errors
  • Store and query data in SQL and document databases
  • Use Git, Linux, tests, and traces as daily tools
  • Reason about services, queues, retries, and failure in distributed systems

Computer foundations

Before domains and frameworks, know what a computer is: hardware runs an OS, the OS talks to the internet, applications sit on top. AI training and inference still sit on this stack — a GPU is hardware; CUDA needs a driver; your API is a process on an OS.

Bottom up. Hardware → OS → networks → apps. Skip this and “the model is slow” becomes guesswork about CPU, RAM, disk, or network.

Hardware

Software is instructions; hardware executes them. For Production AI you especially care about CPU (APIs, orchestration), RAM (context, KV cache, batch size), disk (models, corpora), and GPU (training and many inference workloads).

Hierarchy = speed vs size. Registers/cache are tiny and fast; SSD/network are large and slower. OOM kills are usually RAM (or GPU VRAM), not “Python being slow.”
Hardware is the machine. The OS and your programs are software that schedule work onto that machine.
PartWhat it doesAI product note
CPUGeneral compute, few powerful coresRuns APIs, workers, tokenization, orchestration
RAMFast volatile working memoryLimits concurrent requests, RAG context, batch size
Disk / SSDPersistent storageModel weights, document corpora, logs
GPU / acceleratorMassive parallel mathTraining + much local inference; watch VRAM
NICNetwork interfaceVendor API latency; throughput for streaming

Operating systems

The OS manages processes, memory, files, and devices. Linux dominates servers and GPU boxes; macOS/Windows are fine for local dev. Containers share a kernel; VMs virtualize hardware.

Kernel in the middle. Your FastAPI process is user space. Disk, GPU, and NIC access go through the OS. Permissions and resource limits are OS features — use them.
Processes isolate memory (safer). Threads share memory (cheaper context switch, easier races). Know which model your runtime uses (e.g. Node event loop vs multi-process uvicorn).
ConceptWhy it matters
Process / PIDWhat you start, kill, and monitor (ps, systemd)
Virtual memoryEach process thinks it owns RAM; OOM killer when it lies
Filesystem + permissionsWho can read model files and secrets
Signals / exitsGraceful shutdown of workers on deploy
cgroups / limitsContainers cap CPU/RAM so one job cannot starve others

Internet & networks

The internet moves packets between machines. Your chat UI reaches a model API through DNS → TCP → TLS → HTTP. Latency, packet loss, and DNS failures look like “AI bugs” until you check the network.

Follow the path. Name → IP (DNS), reliable bytes (TCP), encrypted (TLS), then application protocol (HTTP). Ports select which program on the host.
IdeaPlain English
IP addressWhere a machine lives on a network
PortWhich process on that machine (80, 443, 8000…)
DNSHuman name → IP
TCP vs UDPReliable stream vs fast datagrams
Latency vs bandwidthDelay per round trip vs bits per second — LLM chat is latency-sensitive
Public vs privateInternet-facing vs VPC-only services
HTTP details come later under Application Core. Here you need the network path that HTTP rides on.

Data representation

Computers store bits. Engineers still hit encoding bugs daily: UTF-8 vs Latin-1, float precision, and “why is my JSON 2MB.”

TopicPractical takeaway
Bits / bytesSizes: KB → MB → GB; model weights are often GBs
Text encodingsPrefer UTF-8 everywhere; declare it in files and HTTP
NumbersInts vs floats; floats are approximate — money uses decimals
JSON / binaryJSON is text; protobuf/msgpack are denser for high volume
Tokens ≠ wordsLLM billing uses tokenizer pieces, not English words

Virtualization & containers

VMs emulate machines (own guest OS). Containers share the host kernel and package your app + libs. Cloud instances are usually VMs; Docker images are containers. You will use both.

TechIsolatesUse when
VMHardware + full OSStrong isolation, different kernels, GPU passthrough setups
ContainerProcess + filesystem viewShip the same API image to every environment
ServerlessFunction invocationSpiky, short work — watch cold starts for LLM calls
Hands-on packaging is under Production → Docker. Here you only need the mental model.

Files & storage

Everything durable is a file or a block device somewhere: code, logs, model checkpoints, uploaded PDFs. Know paths, permissions, and the difference between local disk and object storage (S3).

  • Local disk: fast for the machine; dies with the instance unless attached volumes
  • Block volumes: cloud disks you attach to VMs
  • Object storage: S3/GCS for corpora, artifacts, backups — cheap, durable, higher latency
  • Permissions: least privilege on model and secret files; never world-readable keys

Language stack

You do not need five languages. You need a clear split: Python for ML/RAG/agents, TypeScript for product UI and typed contracts, Node when the runtime or MCP/tooling ecosystem fits.

Notebooks explore; services ship. Python owns model-adjacent backends. TypeScript owns UI and shared contracts. Node often hosts MCP servers and lightweight workers that call Python over HTTP.

Python

Primary language for ML, RAG, agents, and FastAPI backends. Learn syntax, typing, packaging, async, and how to structure a service — not just notebooks.

# FastAPI skeleton you should be able to write from memory from fastapi import FastAPI, HTTPException from pydantic import BaseModel app = FastAPI() class AskRequest(BaseModel): question: str user_id: str @app.post("/ask") def ask(body: AskRequest): if not body.question.strip(): raise HTTPException(status_code=400, detail="question required") return {"answer": f"echo: {body.question}", "user_id": body.user_id}
Practice: venv, pip/poetry/uv, type hints, dataclasses, logging, pytest, and a 3-file project (api / services / tests).
SkillWhy it matters for AI
Pydantic / typingTool schemas and request validation
async + httpxCall model vendors without blocking the event loop
packagingReproducible workers and MCP servers
loggingTrace ids across retrieve → generate → tool

JavaScript / TypeScript

Needed for AI apps (React/Next.js), tool UIs, and many agent SDKs. TypeScript is the production default — types catch contract bugs between frontend, APIs, and model JSON.

type ChatMessage = { role: "user" | "assistant"; content: string }; async function sendChat(messages: ChatMessage[]): Promise<string> { const res = await fetch("/api/chat", { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify({ messages }), }); if (!res.ok) throw new Error(`HTTP ${res.status}`); const data = (await res.json()) as { reply: string }; return data.reply; }
  • Prefer Zod (or similar) at the boundary of every API route
  • Stream UI with SSE / fetch streams — do not block the page on full completion
  • Keep model keys on the server; the browser talks only to your API

Node.js

Runtime for JS backends, MCP servers, and automation workers. Learn the event loop, streams, env config, and calling Python services over HTTP.

import express from "express"; const app = express(); app.use(express.json()); app.post("/tools/search", async (req, res) => { const q = String(req.body.query ?? ""); // call vector search or Python RAG service res.json({ results: [], query: q }); }); app.listen(3000);
CPU-heavy embedding or inference? Put it in Python/GPU workers. Node shines at I/O and glue, not at matmul.

HTTP & networking

Almost every AI feature is an HTTP call: browser → your API → model vendor / vector DB / tools. Know methods, status codes, headers, TLS, and what “connection refused” vs “timeout” means.

Request line + headers + body in; status + headers + body out. Streaming chat is still HTTP — just a long-lived response.
ConceptYou should know
MethodsGET safe/idempotent; POST creates; PUT/PATCH update; DELETE removes
HeadersAuthorization, Content-Type, Idempotency-Key, Retry-After
TLSHTTPS everywhere; pin certs in internal mesh when required
DNS / portsDebug “works on my machine” with curl, dig, ss

APIs

Every LLM feature is an API: chat, retrieve, tool-call, evaluate. Design resources, not ad-hoc functions. Always define auth, validation, idempotency keys, and error shapes.

Gateway in the middle. Clients never hold vendor model keys. Contracts (OpenAPI / Pydantic / Zod) define the wire format. Status codes and idempotency keys are product features, not afterthoughts.
Classic REST mapping still applies to AI products: threads, messages, documents, and eval runs are resources you can CRUD and paginate.
ConcernProduction rule
ContractsJSON Schema / OpenAPI / Pydantic / Zod — never “whatever the model returns”
AuthAPI keys or JWT at the edge; never put model keys in the browser
ErrorsStable codes: 400 validation, 401/403 auth, 404 missing, 429 rate limit, 500 unexpected
Versioning/v1/... when clients are external; additive changes only
IdempotencyRequire Idempotency-Key on charges, ticket creates, and other writes
PaginationCursor-based for threads/messages; never unbounded list endpoints

Authentication vs authorization

AuthN answers “who are you?” AuthZ answers “what may you do?” Mixing them up is how tenant data leaks into another user’s chat history.

Login proves identity. Permissions decide access to threads, documents, and admin tools. Always take user_id / tenant from the verified token — never from the JSON body alone.
  • Common AuthN: session cookies, JWT bearer, API keys for services
  • Common AuthZ: RBAC roles, ABAC attributes, per-resource ACLs
  • AI-specific: scope tools per role; filter RAG by tenant before retrieval

Databases

AI apps still need users, threads, traces, documents, and billing. Learn SQL first (PostgreSQL), then a document store (MongoDB). Vector DBs come later in RAG — they are not a replacement for your system of record.

System of record first. Users → threads → messages (with token meters). Traces, documents, and billing sit beside. Vectors answer “what’s similar?” — they do not own truth about who paid or what was said.
-- Typical AI product tables CREATE TABLE users (id uuid PRIMARY KEY, email text UNIQUE NOT NULL); CREATE TABLE threads ( id uuid PRIMARY KEY, user_id uuid REFERENCES users(id), created_at timestamptz DEFAULT now() ); CREATE TABLE messages ( id uuid PRIMARY KEY, thread_id uuid REFERENCES threads(id), role text CHECK (role IN ('user', 'assistant', 'tool')), content text NOT NULL, tokens_in int, tokens_out int );
Use SQL when relations and transactions matter (billing, ACLs). Use documents when the shape is nested and evolving (tool payloads, prompt versions). Many products use both.

Engineering basics map

After domains, languages, and app core, these are the cross-cutting engineering basics every Production AI Engineer still needs. Models sit on top of structures, async, caches, queues, and modular code — they do not replace them.

Use as a checklist. HTTP and auth are covered in Application Core above. Here focus on structures, concurrency, caching, queues, modular design, and config. Debugging lives in Daily Craft next.

DSA introduction

DSA = Data Structures + Algorithms. A data structure is how you store and organize data. An algorithm is a step-by-step procedure that uses those structures to solve a problem. You pick a structure for access patterns, then an algorithm for the job — search, sort, traverse, or transform.

Left = shapes. Right = recipes. Arrays and hash maps for everyday APIs; trees and graphs when hierarchy or links matter. Search/sort/BFS/DFS are the starter algorithms. Big-O answers: “if input grows 10×, does cost grow 10× or 100×?”
PieceMeaningStarter examples
Data structuresHow data is laid out and accessedArray, list, stack, queue, hash map, tree, graph
AlgorithmsSteps that compute a resultLinear/binary search, sort, recursion, two pointers, BFS/DFS
Complexity (Big-O)How time/memory grow with input size nO(1), O(log n), O(n), O(n log n), O(n²)

Why engineers care (not only interviews)

  • Wrong structure → slow APIs (e.g. scanning a list instead of a hash lookup)
  • Wrong algorithm → timeouts on larger datasets (e.g. nested loops on 100k items)
  • In AI products: top-k heaps, graph walks, dedupe sets, and queue BFS show up constantly

This page is only the introduction. Next section maps structures to production use. For language-specific practice, see JavaScript Data Structures and Python Data Structures.

Concurrency & async

AI backends spend most of their time waiting on networks (model APIs, DBs). Async I/O lets one process handle many in-flight calls. Parallelism (multiple cores/GPUs) is different — know which one you need.

Sync: one call blocks the worker. Async: await the vendor while other requests progress. Do not confuse “async” with “faster model” — it is about utilization.
Concurrency = many tasks in progress. Parallelism = many tasks at the same instant. Embedding batches and GPU inference need parallelism; chat gateways mostly need concurrency.

Caching

Cache what is expensive and stable: embeddings of unchanged chunks, rarely changing docs, repeated identical prompts (with care). Do not cache personalized or ACL-sensitive answers without including the principal in the key.

Layers stack: CDN → app/redis → DB. Each layer needs a TTL and an invalidation story. Stale RAG embeddings after a doc edit are a product bug.
CacheGood forInvalidate when
Embedding cacheSame text → same vectorEmbedding model changes
Retrieval cacheHot FAQ queriesCorpus or ACL changes
HTTP CDNStatic UI assetsDeploy / version bump
Full answer cacheIdentical public promptsPolicy, model, or prompt version changes

Queues & background jobs

Anything slow, bursty, or retriable belongs off the request path: embedding a corpus, batch evals, sending emails, tool side effects with HITL.

PatternUse
At-least-once deliveryDefault for most queues — make handlers idempotent
Visibility timeoutWorker crash → message returns for retry
Dead-letter queuePoison messages after N failures
Scheduled / cronNightly evals, stale-doc reindex
On the synchronous path, keep middleware thin (auth, logging, validation). Heavy work after that should enqueue — not block the user’s HTTP response.

Modular design

Keep business rules free of vendor SDKs. Routes talk to use-cases; use-cases talk to ports; adapters implement DB, queue, and LLM providers. Swapping OpenAI for Anthropic should not rewrite billing or ACL logic.

Dependencies point inward. Domain does not import the OpenAI SDK. Adapters sit at the edge. That is how you add a second model or a mock in tests without surgery.
Classic backend shape still applies: clients → API → services → data stores. AI adds model and vector dependencies as just more adapters.

Config & environments

Follow 12-factor habits: config in env, secrets in a vault, one artifact across dev/stage/prod. Never bake model keys or tenant URLs into the image.

# .env.example (commit this). Real .env stays local / in the secret manager. DATABASE_URL=postgres://... MODEL_API_KEY= MODEL_BASE_URL=https://api.openai.com/v1 LOG_LEVEL=info MAX_TOOL_STEPS=8
  • Fail fast on missing required env at boot
  • Feature flags for risky prompt or model rollouts
  • Separate rate limits and quotas per environment

Git

Production teams live in PRs. Learn branching, rebasing vs merge, .gitignore, conventional commits, and how to review diffs that include prompts, evals, and infra.

git checkout -b feat/rag-rerank git add -p git commit -m "Add cross-encoder rerank step to retrieval pipeline" git push -u origin HEAD
  • Version prompts and eval sets like code — not as unnamed Slack pastes
  • Never commit .env, model keys, or customer dumps
  • Small PRs: one retrieval change is easier to eval than a mega-diff

Debugging

Most “the model is broken” tickets are engineering: bad input, wrong tenant filter, timeout too low, or a silent 4xx from a tool.

  1. Reproduce with a request id / trace id
  2. Check your logs before the vendor dashboard
  3. Bisect: API validation → retrieval → prompt build → model → tool
  4. Reduce: smallest payload that still fails
  5. Fix + add a regression test or golden-set case
Keep a debug checklist in the repo. When on-call is tired, checklists beat heroics.

Testing

Model output is non-deterministic, so tests must split: deterministic code (chunking, tools, parsers) vs evals (quality). Start with pytest / Vitest on everything that is not an LLM.

Left is CI every PR. Right is quality. Mock the LLM in unit tests. Never assert exact prose. Golden sets and faithfulness/hit@k run on a schedule or before you change chunking/models.
def test_rejects_empty_question(client): r = client.post("/ask", json={"question": " ", "user_id": "u1"}) assert r.status_code == 400 def test_tool_schema_is_valid(): schema = load_tool("search_docs") assert "query" in schema["parameters"]["properties"]

Observability

If you cannot answer “which request, which model, how many tokens, how much $,” you are flying blind.

SignalWhy
request_id / trace_idJoin gateway → retrieve → generate → tool
latency p50/p95Users feel p95; averages lie
tokens_in / tokens_out / USDCatch prompt bloat and retry storms

Log structured JSON. Redact secrets and PII. Keep raw prompts in a secure store if you need them for debugging — not in world-readable logs.

Security basics

  • Authn at the edge; authz on every resource (user_id / tenant from the token, not the body)
  • Secrets in a vault/env — never in prompts, repos, or client bundles
  • Treat model output and retrieved docs as untrusted (prompt injection)
  • Rate-limit per user and per IP; cap max tokens and tool calls
  • Least privilege for DB roles and cloud IAM used by workers
A leaked OpenAI/Anthropic key in a frontend build is an incident. Proxy model calls through your backend.

Docker intro

Containers package your API the same way in dev and prod. You do not need Kubernetes on day one — you need a Dockerfile that runs migrations-less boot, a non-root user, and a healthcheck. Deeper container orchestration lands in Cloud AI / LLMOps.

# Minimal API image sketch FROM python:3.12-slim WORKDIR /app COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt COPY app ./app USER nobody CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
  • One process per container; put workers in another service
  • Pass secrets at runtime — never ENV MODEL_API_KEY=sk-... in the Dockerfile
  • Tag images by git SHA for rollback

Microservices

Split when a team or scaling axis needs it — not because a blog said so. Common AI split: API gateway, retrieval service, inference/worker, eval job. Communicate with HTTP or a queue; share a contract, not a database, unless you must.

Left is often correct. One FastAPI chat+RAG process is fine. Split when retrieval and inference need different scale or owners — and accept the latency tax around every LLM call.
Rule: A chat app with one FastAPI process is not a failure. Premature microservices add latency around every LLM call.

Distributed systems

LLMs time out, GPUs OOM, and vendors rate-limit. You need timeouts, retries with jitter, idempotency, circuit breakers, and “at least once” vs “exactly once” thinking for tool side effects.

Long or flaky work (embedding a corpus, batch evals, tool side effects) belongs on a queue — not on the request thread that holds the user’s HTTP connection.
import httpx async def call_model(prompt: str) -> str: async with httpx.AsyncClient(timeout=30.0) as client: for attempt in range(3): try: r = await client.post(MODEL_URL, json={"prompt": prompt}) r.raise_for_status() return r.json()["text"] except httpx.TimeoutException: if attempt == 2: raise

Resilience patterns

These five patterns show up in every production AI stack. Memorize them; you will implement them repeatedly.

Timeouts bound pain. Retries need jitter. Idempotency protects writes. Circuit breakers stop stampeding a dying vendor. DLQs catch what still fails. Map each to a real failure: 429, OOM, duplicate charge.
PatternAI-specific note
TimeoutsSeparate connect vs read; streaming needs idle timeouts too
Retries + jitterRetry 429/5xx; do not retry non-idempotent POSTs without a key
IdempotencyTool writes and billing must survive “at least once” delivery
Circuit breakerFail fast when the vendor is down; show a degraded UI
BulkheadsIsolate retrieval vs generation pools so one cannot starve the other
