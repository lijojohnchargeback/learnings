🔧 How Python Works

CPython, bytecode, the GIL, memory, and garbage collection — what actually happens when your code runs.

🗺️ The Big Picture

Python is an interpreted, high-level language whose most common implementation is CPython. Your .py file is not executed as raw text — it is compiled to bytecode, then run by a virtual machine written in C.

LayerWhat it does
Your code.py source files
CompilerParses source → AST → bytecode (.pyc)
CPython VMEval loop executes bytecode opcodes
RuntimeObjects, memory, GIL, GC, import system
OS / CPUActual process, threads, and machine instructions
# Mental model (not literal code) .py source → tokenize & parse → Abstract Syntax Tree (AST) → compile to bytecode → CPython evaluation loop → object model + C extensions → OS threads / memory / I/O

The rule this page uses

Python code runs on one bytecode evaluation loop per thread, and CPython’s GIL means only one thread executes Python bytecode at a time. Parallelism for CPU work needs processes, native extensions that release the GIL, or free-threaded builds (3.13+ experimental).

🐍 Implementations

“Python” is a language specification. Several runtimes implement it:

RuntimeNotes
CPythonReference implementation. What almost everyone means by “Python.”
PyPyJIT compiler — often faster for long-running pure-Python workloads.
Jython / IronPythonRun on JVM / .NET (limited C-extension support).
MicroPythonTiny subset for microcontrollers.

This guide focuses on CPython — the engine behind python / python3 on most machines.

⚙️ Source → Running Code

When you run python app.py:

  1. Read the source file
  2. Lex & parse into an AST (ast module can show this)
  3. Compile the AST to a code object (bytecode + metadata)
  4. Execute that code object in a frame on the call stack
import ast, dis src = "x = 1 + 2" tree = ast.parse(src) print(ast.dump(tree, indent=2)) # Module( # body=[Assign(targets=[Name(id='x')], value=BinOp(...))] # ) code = compile(src, "<string>", "exec") dis.dis(code) # 1 LOAD_CONST 0 (1) # LOAD_CONST 1 (2) # BINARY_OP 0 (+) # STORE_NAME 0 (x) # RETURN_CONST 2 (None)
💡 Tip: dis.dis(fn) is the best way to see what the VM actually runs for a function.

📦 Bytecode & .pyc Files

Bytecode is a compact, platform-independent instruction set for the CPython VM. Cached copies live under __pycache__/ as .pyc files so imports skip recompilation when the source is unchanged.

# After: python -c "import mymodule" # You get something like: # __pycache__/mymodule.cpython-312.pyc import importlib.util spec = importlib.util.find_spec("os") print(spec.origin) # path to os.py or extension

🔁 The Evaluation Loop

CPython’s heart is a giant switch/dispatch loop (historically in ceval.c). For each opcode it:

  • Reads the next instruction
  • Manipulates the value stack and locals
  • May call into C for builtins / extensions
  • Periodically checks signals and GIL release points
def add(a, b): return a + b # Roughly at the VM level: # LOAD_FAST a # LOAD_FAST b # BINARY_OP + # RETURN_VALUE # Locals like `a` and `b` use LOAD_FAST (array index) — # much cheaper than LOAD_GLOBAL / LOAD_NAME (dict lookup).

🧱 Everything is an Object

In CPython, integers, functions, classes, modules, and even types are heap objects with a shared header: type pointer, reference count, and (for many types) GC headers.

x = 42 print(type(x)) # <class 'int'> print(type(type(x))) # <class 'type'> — types are objects too print(type(type)) # <class 'type'> — type is an instance of itself def f(): pass print(f.__code__.co_code) # raw bytecode bytes print(f.__globals__) # module dict the function closes over

Even small ints are objects. CPython caches a range of small integers (−5…256) so a is b can be true for equal small ints — but never rely on is for value equality. Use ==.

🏷️ Names vs Values

Python variables are names bound to objects, not boxes that hold values. Assignment rebinds a name; it does not copy the object.

a = [1, 2, 3] b = a # b points to the SAME list b.append(4) print(a) # [1, 2, 3, 4] c = a[:] # shallow copy — new list object c.append(5) print(a) # [1, 2, 3, 4] print(c) # [1, 2, 3, 4, 5] # Function args work the same way: def append_x(lst): lst.append("x") # mutates the caller's list def rebind(lst): lst = lst + ["y"] # rebinds local name only; caller unchanged
OperationWhat happens
x = yName x now refers to same object as y
x = x + 1 (int)Creates new int; rebinds x
x.append(1)Mutates the list object in place
x is ySame object identity (same pointer)
x == yValue equality (calls __eq__)

🧠 Memory Layout (CPython)

  • Stack: C call stack for the interpreter itself + Python frame objects for running code
  • Heap: virtually all Python objects live here
  • Arenas / pools: CPython’s pymalloc allocator optimizes small-object allocation
import sys x = [] print(sys.getsizeof(x)) # empty list overhead (implementation-dependent) x.append(1) print(sys.getsizeof(x)) # grows in overallocation chunks # Reference count (CPython-specific; may not exist elsewhere) print(sys.getrefcount(x)) # includes the temporary arg to getrefcount

🧵 The Global Interpreter Lock (GIL)

The GIL is a mutex in CPython that protects the interpreter’s internal state. Only one thread can execute Python bytecode at a time.

# Two CPU-bound threads do NOT use two cores for Python bytecode import threading def burn(n): x = 0 for i in range(n): x += i return x # This takes ~2× a single thread, not ~1× — GIL serializes bytecode t1 = threading.Thread(target=burn, args=(10_000_000,)) t2 = threading.Thread(target=burn, args=(10_000_000,)) t1.start(); t2.start() t1.join(); t2.join()

Why the GIL exists

It keeps reference counting simple and fast, and makes the C API easier. The cost is limited multi-core parallelism for pure-Python CPU work.

from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor # CPU-bound → processes with ProcessPoolExecutor() as pool: results = list(pool.map(expensive_fn, data)) # I/O-bound → threads (or asyncio) with ThreadPoolExecutor(max_workers=32) as pool: results = list(pool.map(fetch_url, urls))

Python 3.13 introduced an experimental free-threaded (no-GIL) build. Treat it as opt-in until ecosystem support is mature.

♻️ Garbage Collection

CPython uses reference counting as the primary memory manager, plus a cyclic garbage collector for reference cycles.

import gc, sys a = [] b = [] a.append(b) b.append(a) # cycle: a ↔ b del a, b # refcounts drop but cycle remains gc.collect() # cyclic GC can reclaim them # Inspect generations print(gc.get_stats()) print(gc.get_threshold()) # (700, 10, 10) typical defaults
MechanismRole
RefcountingFrees an object as soon as refcount hits 0
Generational GCFinds unreachable cycles (young → old generations)
__del__Finalizer — can complicate cycle collection; prefer context managers

📥 The Import System

Imports are dynamic lookups through sys.meta_path finders and loaders. Successful imports are cached in sys.modules.

import sys # 1. Check sys.modules cache # 2. Ask finders on sys.meta_path # 3. Loader executes module code, binds into sys.modules print("json" in sys.modules) import json print(sys.modules["json"]) # Circular imports fail when module A needs B before B finishes loading. # Fix: local imports, rearrange, or lazy import inside functions.
💡 Backend tip: Heavy imports at module top-level slow cold starts. For CLI tools and serverless, consider lazy imports inside functions that need them.
