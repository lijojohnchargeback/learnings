🔴 Redis Complete Guide

In-memory data structure store — caching, messaging, streams, and distributed building blocks

🏠 Introduction to Redis

Redis (Remote Dictionary Server) is an open-source, in-memory data structure store used as a database, cache, message broker, and streaming engine. Data lives primarily in RAM, which is why Redis is extremely fast — often sub-millisecond latency.

Redis is not “just a cache.” It is a Swiss-army knife of data structures that happen to live in memory — with optional durability on disk.

What Redis is

An in-memory key-value store with rich types (strings, hashes, lists, sets, sorted sets, streams, bitmaps, HyperLogLog, geospatial).

What Redis is for

Caching, sessions, rate limiting, leaderboards, real-time analytics, job queues, pub/sub, and short-lived coordination.

What Redis is not

A full replacement for your primary relational/document DB when you need complex queries, large durable datasets, or strong multi-key ACID across shards.

Senior Tip: Memory is the product

Every Redis design decision starts with memory. Keys cost memory. Values cost memory. Expired keys still occupy memory until Redis lazily or actively removes them. Plan capacity, TTLs, and eviction before you ship traffic.

Why teams choose Redis

Benefit Why it matters
Speed In-memory + efficient data structures → typically <1ms ops
Rich types You model problems with lists/sets/zsets instead of inventing schemas in app code
Atomic commands Single-threaded command execution makes many ops race-free without locks
Versatility One service covers cache, sessions, queues, pub/sub, and streams
Ecosystem Clients for every language; managed Redis on AWS, GCP, Azure, Redis Cloud

🏗️ Redis Architecture

Redis uses a client–server model. Clients speak a simple text protocol (RESP) over TCP (default port 6379). The server keeps the dataset in memory and processes commands through an event loop.

Main thread mental model. Commands are executed one at a time on the main thread. That is why individual commands feel atomic — and why a slow command can block everyone.

Single-threaded core

The command processor is single-threaded. No two commands mutate data concurrently. Complex ops (large KEYS, big SORT) can stall the whole server.

I/O & background work

Modern Redis can use I/O threads for network. Persistence, AOF rewrite, and replication use background processes / threads so the main loop stays responsive.

Core components

Component Role
Clients redis-cli, node-redis, ioredis, redis-py, Jedis, etc.
Event loop Accepts connections, parses RESP, runs commands
Dict / dataset In-memory hash table of keys → typed values
Persistence RDB snapshots and/or AOF log to disk
Replication Async copy of data to replicas

RESP protocol (simplified)

Commands look like arrays of bulk strings. Example: SET user:1 "Ada" is sent as an array of two bulk strings. You almost never hand-write RESP — clients do it for you.

⚙️ Install & Connect

Docker (fastest for local)

# Run Redis 7+ docker run -d --name redis -p 6379:6379 redis:7-alpine # With persistence volume docker run -d --name redis -p 6379:6379 \ -v redis-data:/data \ redis:7-alpine redis-server --appendonly yes # Open CLI docker exec -it redis redis-cli

First commands

PING # PONG SET greeting "hello redis" GET greeting # "hello redis" INFO server DBSIZE FLUSHDB # wipe current DB (careful!)

Logical databases

By default Redis has 16 logical DBs (0–15). Switch with SELECT n. In Cluster mode, only DB 0 is supported. Prefer key prefixes (app:users:) over juggling DBs.

🔑 Keys, Namespaces & TTL

Every value in Redis is addressed by a string key. Good key design is half of Redis mastery.

Key naming conventions

  • user:1001 — entity by id
  • user:1001:profile — related object
  • session:abc123 — opaque tokens
  • cache:product:55 — cached query/result
  • ratelimit:ip:1.2.3.4 — counters

Use : as a separator. Keep keys short but readable. Avoid huge key names — they consume memory too.

Essential key commands

EXISTS user:1001 TYPE user:1001 DEL user:1001 UNLINK big:key # async delete (safer for large values) RENAME old:key new:key RANDOMKEY SCAN 0 MATCH user:* COUNT 100 # NEVER use KEYS * in production

TTL (Time To Live)

SET session:abc "payload" EX 3600 # expire in 1 hour SETNX lock:job1 "1" EXPIRE lock:job1 30 TTL lock:job1 # seconds remaining (-1 no expiry, -2 missing) PTTL lock:job1 # milliseconds PERSIST lock:job1 # remove expiry

KEYS vs SCAN

KEYS pattern blocks the server while it walks the whole keyspace. Use SCAN cursor iteration in production tooling, admin scripts, and migrations.

📦 Data Types Overview

Redis values are typed. The type determines which commands you can run. Pick the structure that matches the access pattern — not just “whatever fits as JSON.”

Six workhorse types. Master these first. Bitmaps, HyperLogLog, and geospatial indexes build on strings/zsets.
Type Best for Example
String Cache blobs, counters, flags cache:page:/home
Hash Objects with fields user:42 → name, email
List Queues, recent activity queue:emails
Set Unique membership, tags user:42:roles
Sorted Set Leaderboards, ranked feeds game:scores
Stream Event logs, consumer groups orders:stream

📝 Strings

Strings are binary-safe blobs up to 512 MB (don’t store 512 MB values). They also power counters and bit operations.

SET page:home "<html>..." GET page:home MSET a 1 b 2 c 3 MGET a b c SET visits:2026-03-24 0 INCR visits:2026-03-24 INCRBY visits:2026-03-24 10 GETSET token old-value # set new, return old SET lock:resource "owner-id" NX EX 30 # distributed lock attempt

NX / XX options

NX = set only if not exists. XX = set only if exists. Combined with EX/PX they form the basis of locks and idempotent writes.

Bitmaps & HyperLogLog

SETBIT/GETBIT for dense boolean flags. PFADD/PFCOUNT for approximate unique counts with tiny memory.

🗂️ Hashes

Hashes store field → value maps under one key. Ideal for user profiles, config objects, and shopping carts — without serializing a whole JSON blob when you only need one field.

HSET user:42 name "Ada" email "ada@example.com" plan "pro" HGET user:42 email HMGET user:42 name plan HGETALL user:42 HINCRBY user:42 login_count 1 HEXISTS user:42 plan HDEL user:42 plan HLEN user:42

Hash vs JSON string

Store a Hash when you frequently read/update individual fields. Store a JSON string when you always load/replace the whole document and want a simple cache of an API response.

📋 Lists

Lists are linked lists of strings. Use them for queues, stacks, and “latest N items” feeds.

LPUSH queue:emails "job-1" "job-2" RPUSH feed:user:1 "post-9" LPOP queue:emails BRPOP queue:emails 30 # blocking pop, 30s timeout LRANGE feed:user:1 0 19 # latest 20 LLEN queue:emails LTRIM feed:user:1 0 99 # keep only newest 100
Naive queue
LPUSH + LPOP alone can lose jobs if the worker crashes after pop.
Reliable pattern
Prefer Streams with consumer groups + ACK, or move jobs to a processing list and acknowledge by deletion.

🔷 Sets

Sets store unique unordered members. Perfect for tags, unique visitors (exact), and relationship membership.

SADD article:10:tags redis cache database SISMEMBER article:10:tags redis SMEMBERS article:10:tags SCARD article:10:tags SREM article:10:tags cache SINTER user:1:friends user:2:friends SUNION tag:redis tag:nodejs SDIFF set:a set:b

🏆 Sorted Sets (ZSets)

Sorted sets associate each member with a floating-point score. Members are unique; scores define order. This is the classic leaderboard structure.

ZADD game:scores 1200 alice 950 bob 1800 cara ZINCRBY game:scores 50 bob ZRANGE game:scores 0 2 WITHSCORES # lowest scores ZREVRANGE game:scores 0 9 WITHSCORES # top 10 ZRANK game:scores alice ZSCORE game:scores cara ZCOUNT game:scores 1000 2000 ZREMRANGEBYRANK game:scores 0 -101 # keep top 100

Advanced ZSet uses

  • Time-ordered feeds: score = timestamp
  • Delay queues: score = run-at time; worker polls ZRANGEBYSCORE
  • Rate windows: score = event time; prune old members
  • Geospatial: Redis GEO commands are built on ZSets

⚡ Caching Patterns

Caching is the most common Redis use case. The pattern you choose determines consistency vs speed tradeoffs.

Cache-aside is the default for most apps. Write-through favors consistency. Write-behind favors write throughput with more complexity.

1. Cache-aside (lazy loading)

# Pseudocode value = redis.GET("product:55") if value is nil: value = db.query("SELECT ...") redis.SET("product:55", value, EX=600) return value

2. Write-through

On every write, update Redis and the database in the same request path. Reads almost always hit Redis. Simpler consistency; slower writes.

3. Write-behind (write-back)

Write to Redis immediately; asynchronously flush to DB. Highest write speed, hardest correctness (crash windows, ordering).

Cache stampede

When a hot key expires, many requests miss at once and hammer the DB. Mitigate with locking, probabilistic early expiry, or staggered TTLs.

Negative caching

Cache “not found” briefly so missing keys don’t repeatedly hit the DB. Use a short TTL sentinel value.

🧹 Memory & Eviction Policies

When Redis hits maxmemory, it must evict keys or reject writes — depending on policy.

Policy Behavior
noeviction Return errors on writes when full (default in many installs)
allkeys-lru Evict least-recently-used among all keys — common for pure caches
volatile-lru LRU only among keys that have a TTL
allkeys-lfu Evict least-frequently-used keys
volatile-ttl Evict keys with nearest expire time first

🎫 Sessions, Locks & Rate Limiting

Session store

SET session:s3cr3t '{"userId":42,"role":"admin"}' EX 86400 GET session:s3cr3t DEL session:s3cr3t # logout

Simple fixed-window rate limit

INCR ratelimit:ip:1.2.3.4 EXPIRE ratelimit:ip:1.2.3.4 60 # only on first hit # if count > 100 → reject

Distributed lock (basics)

SET lock:invoice:99 "worker-7" NX EX 30 # do work... # release only if value still matches (use Lua for safety)

Production locks

For serious distributed locking, study the Redlock algorithm and libraries like Redisson — or prefer a consensus system when correctness is critical. Always set a TTL so dead holders cannot lock forever.

📣 Pub/Sub

Redis Pub/Sub is a lightweight fire-and-forget messaging channel. Publishers send to a channel; active subscribers receive messages in real time.

No persistence. If a subscriber is offline, it misses the message. Use Streams when you need durability and replay.
# Subscriber SUBSCRIBE orders PSUBSCRIBE order.* # Publisher (other connection) PUBLISH orders '{"id":123,"status":"created"}' PUBLISH order.shipped '{"id":123}'

Good for

Live notifications, cache invalidation signals, presence, ephemeral fan-out.

Not good for

Job queues, audit logs, anything that must survive disconnects or require ACK/retry.

🌊 Redis Streams

Streams are an append-only log with consumer groups — Redis’s answer to lightweight Kafka-style processing inside Redis.

Consumer groups + PEL. Each message is delivered to one consumer in the group. Unacked entries stay in the Pending Entries List for reclaim.
# Produce XADD orders:stream * orderId 123 total 49.99 # Create group starting from new messages XGROUP CREATE orders:stream payments 0 MKSTREAM # Consume XREADGROUP GROUP payments worker-a COUNT 10 BLOCK 5000 STREAMS orders:stream > # Acknowledge XACK orders:stream payments 1710000000000-0 # Inspect pending XPENDING orders:stream payments XCLAIM orders:stream payments worker-b 60000 1710000000000-0

When to use Streams vs Lists vs Pub/Sub

  • Pub/Sub — ephemeral realtime fan-out
  • Lists — simple queues, prototypes
  • Streams — durable processing, consumer groups, replay, ACKs

🚀 Pipelines & Transactions

Cut round trips and keep logic close to the data. Pipelines batch network calls. Transactions queue commands. Lua runs atomically on the server.

Pipelining

Sending one command per network round trip wastes latency. Pipelines batch many commands, then read all replies.

# redis-cli --pipe or client pipeline API SET a 1 SET b 2 INCR counter GET a

MULTI / EXEC transactions

MULTI INCRBY wallet:42 -50 INCRBY wallet:99 50 EXEC

All queued commands run sequentially and atomically relative to other clients. Redis transactions do not roll back on runtime errors inside EXEC the way SQL does — validate carefully. Use WATCH for optimistic locking:

WATCH balance:42 val = GET balance:42 MULTI SET balance:42 (val - 10) EXEC # fails (nil) if key changed since WATCH

📜 Lua Scripts

Lua scripts run inside Redis atomically. They are the right tool for compare-and-delete locks, custom rate limiters, and multi-key logic that must not interleave.

# Release lock only if we still own it EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" \ 1 lock:invoice:99 worker-7 # Load once, run by SHA SCRIPT LOAD "..." EVALSHA <sha> 1 lock:invoice:99 worker-7

Lua rules of thumb

  • Keep scripts short and deterministic
  • Declare all keys in KEYS[] (required for Cluster compatibility)
  • Avoid long loops — scripts block the server
  • Prefer EVALSHA after warm-up to reduce bandwidth

💾 Persistence (RDB & AOF)

Redis can survive restarts by writing to disk. You choose durability vs performance.

RDB = periodic compact snapshots. AOF = log of write commands. Many production setups enable both.
RDB AOF
What Point-in-time binary snapshot Append-only log of write ops
Pros Small files, fast restarts Better durability, finer recovery
Cons Can lose minutes of data Larger files; rewrite needed
Config save 60 1000 etc. appendonly yes, appendfsync everysec
BGSAVE # trigger RDB in background LASTSAVE BGREWRITEAOF # compact AOF CONFIG GET appendonly CONFIG GET save

Durability reality check

Even with AOF everysec, you can lose ~1 second of writes on crash. For cache-only workloads, you may disable persistence entirely and treat Redis as disposable.

🔄 Replication & Sentinel

Replication copies data from a primary to one or more replicas asynchronously. Reads can scale out; writes go to the primary.

Sentinel watches the primary, agrees on failure via quorum, and promotes a replica automatically.

Manual replication

# On replica REPLICAOF 10.0.0.5 6379 INFO replication # Promote manually REPLICAOF NO ONE

Redis Sentinel

  • Monitors primary + replicas
  • Notifies clients/apps of topology changes
  • Performs automatic failover with quorum
  • Typically run 3+ Sentinel processes

Async replication caveat

Replicas can lag. A failover may promote a replica that is slightly behind — accepting possible loss of the last few unreplicated writes. Design for idempotent writes when that matters.

🧩 Redis Cluster

Redis Cluster shards data across multiple primary nodes for horizontal scale. The keyspace is divided into 16384 hash slots.

Slot = CRC16(key) mod 16384. Clients follow MOVED/ASK redirects. Hash tags {user}:profile keep related keys on the same node.

Hash tags

# These share the same slot because of {user42} SET {user42}:profile "..." SET {user42}:cart "..." # Multi-key ops only work when all keys map to one slot

Cluster strengths

Horizontal memory scale, high availability (each master has replicas), automatic resharding tools.

Cluster tradeoffs

Multi-key commands limited to one slot. Transactions/Lua across arbitrary keys fail. Slightly more client complexity.

🧩 Redis Modules & Modern Features

Modules extend Redis beyond core types. On Redis Stack / Redis Cloud you often get them preloaded.

Module Purpose
RedisJSON Native JSON documents with path updates
RediSearch Full-text and secondary indexing
RedisBloom Bloom, Cuckoo, Count-Min, Top-K filters
RedisTimeSeries Time-series metrics with downsampling
RedisGraph (legacy) Graph queries (community shifted; check current status)

Other advanced building blocks

  • Geospatial: GEOADD, GEOSEARCH for nearby queries
  • Bitfields: packed counters in a string
  • Functions (Redis 7+): registered libraries as a modern alternative to ad-hoc Lua
  • ACLs: fine-grained user permissions
  • Client-side caching: server-assisted tracking to invalidate local caches

🔒 Security

  • Never expose Redis to the public internet without auth + TLS
  • Use requirepass / ACL users (Redis 6+)
  • Bind to private interfaces; firewall port 6379
  • Disable dangerous commands (FLUSHALL, CONFIG, KEYS) via rename-command or ACL
  • Enable TLS for in-transit encryption in production
  • Run as non-root; keep Redis updated
ACL SETUSER app on >strongpass ~app:* +@read +@write -@dangerous AUTH app strongpass ACL WHOAMI

🟢 Redis with Node.js

Popular clients: redis (node-redis) and ioredis (great Cluster support).

// npm i redis import { createClient } from 'redis'; const client = createClient({ url: 'redis://127.0.0.1:6379' }); client.on('error', (err) => console.error('Redis', err)); await client.connect(); await client.set('cache:hello', 'world', { EX: 60 }); const value = await client.get('cache:hello'); // Pipeline const pipe = client.multi(); pipe.set('a', '1'); pipe.incr('counter'); await pipe.exec(); // Pub/Sub const sub = client.duplicate(); await sub.connect(); await sub.subscribe('orders', (message) => { console.log('got', message); });

Connection hygiene

Reuse one client (or a small pool) per process. Always handle reconnect. In serverless, prefer short commands and managed Redis with connection multiplexing / proxies (e.g. Redis Cluster + good client, or AWS MemoryDB/ElastiCache best practices).

✨ Best Practices & Mental Models

Do

  • Design keys with prefixes and TTLs
  • Use SCAN, never KEYS * in prod
  • Pipeline bulk work
  • Monitor memory, hit rate, evictions, latency
  • Pick Streams for durable jobs
  • Test failover before you need it

Don’t

  • Store unbounded collections without trim
  • Run huge synchronous commands on hot instances
  • Treat Redis as your only source of truth blindly
  • Expose Redis without ACL/TLS
  • Ignore replica lag in read-your-writes paths
  • Use Pub/Sub as a job queue

The sentence to remember

Redis is a memory-first data structure server. Use the right type for the access pattern, expire what you can, and graduate from “cache box” to Streams, Sentinel, and Cluster only when your reliability and scale requirements demand it.
