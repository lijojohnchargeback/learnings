🔗 Context API

React’s built-in way to share state without prop drilling — Provider, useContext, reducers, and performance.

📚 What is Context?

The Context API lets a parent provide a value that any descendant can read, no matter how deep the tree is. It solves prop drilling: passing the same prop through components that do not use it.

Left: every layer forwards theme. Right: Provider broadcasts; only the toggle needs to subscribe.
Prop drilling Context broadcast App { theme } ThemeProvider value={theme} └── Layout { theme } └── Layout └── Header { theme } └── Header └── Toggle └── Toggle ← useContext()
// Prop drilling — ThemeToggle never uses theme, it only forwards it <App theme={theme}> <Layout theme={theme}> <Header theme={theme}> <ThemeToggle theme={theme} /> </Header> </Layout> </App> // Context — any child can read theme without a chain of props <ThemeContext.Provider value={theme}> <Layout> <Header> <ThemeToggle /> </Header> </Layout> </ThemeContext.Provider>

Mental model

Context is a broadcast. The Provider is the radio tower. useContext is the radio. When the tower changes frequency (value), every radio listening to that station re-renders.

🏭 createContext

Call createContext(defaultValue) once at module scope. The default is used only if a component reads context without a matching Provider above it.

import { createContext } from 'react'; export const ThemeContext = createContext('light'); // default export const AuthContext = createContext(null);
⚠️ Create the context object outside components. Creating it inside a render produces a new identity every time and breaks consumers.

📡 Provider

Context.Provider wraps a subtree and sets the current value. Nested providers override outer ones for that subtree.

function App() { const [theme, setTheme] = useState('light'); const value = { theme, setTheme }; return ( <ThemeContext.Provider value={value}> <Dashboard /> </ThemeContext.Provider> ); }

If value is a new object every render (like { theme, setTheme } created inline), every consumer re-renders even when theme did not change. Memoize the value when it is an object.

const value = useMemo( () => ({ theme, setTheme }), [theme] );

🪝 useContext

useContext(SomeContext) returns the nearest Provider’s value. The component re-renders whenever that value’s reference (or primitive) changes.

import { useContext } from 'react'; import { ThemeContext } from './theme-context'; function ThemeToggle() { const { theme, setTheme } = useContext(ThemeContext); return ( <button onClick={() => setTheme(theme === 'light' ? 'dark' : 'light')}> Mode: {theme} </button> ); }

Legacy: Context.Consumer

Before hooks, you used a render-prop Consumer. Prefer useContext in function components.

<ThemeContext.Consumer> {({ theme }) => <span>{theme}</span>} </ThemeContext.Consumer>

🎁 Custom Hook Wrapper

Always wrap useContext in a hook that throws if the Provider is missing. That turns a silent null bug into a clear error.

import { createContext, useContext } from 'react'; const AuthContext = createContext(null); export function AuthProvider({ children, value }) { return ( <AuthContext.Provider value={value}> {children} </AuthContext.Provider> ); } export function useAuth() { const ctx = useContext(AuthContext); if (!ctx) { throw new Error('useAuth must be used inside AuthProvider'); } return ctx; }

🔁 Context + useReducer

For shared state with many update kinds (add, remove, hydrate), pair Context with useReducer. This is a mini Redux: dispatch goes in, new state comes out, UI reads state from context.

const CartContext = createContext(null); function cartReducer(state, action) { switch (action.type) { case 'add': return { ...state, items: [...state.items, action.item] }; case 'clear': return { ...state, items: [] }; default: return state; } } export function CartProvider({ children }) { const [state, dispatch] = useReducer(cartReducer, { items: [] }); const value = useMemo(() => ({ state, dispatch }), [state]); return ( <CartContext.Provider value={value}> {children} </CartContext.Provider> ); } export function useCart() { const ctx = useContext(CartContext); if (!ctx) throw new Error('useCart must be used inside CartProvider'); return ctx; } // usage const { state, dispatch } = useCart(); dispatch({ type: 'add', item: { id: 1, name: 'Book' } });
💡 Split state and dispatch into two contexts if many children only dispatch. Dispatch is a stable function; they will not re-render when state changes.

✂️ Splitting Contexts

One fat context (user + theme + cart + notifications) means a cart change re-renders the theme toggle. Split by how often they change and who needs them.

❌ One fat context ThemeProvider value={{ theme, user, cart }} └── ThemeToggle re-renders when cart changes ✅ Split by change rate ThemeProvider value={theme} ← rare AuthProvider value={user} ← rare CartProvider value={cart} ← frequent

Slow-changing

Theme, locale, feature flags — one Context is fine. Few updates, many readers.

Fast-changing

Cart line items, live search results — isolate them, or use Redux/RTK with selectors.

🎨 Theme & Auth Examples

Theme

function ThemeProvider({ children }) { const [theme, setTheme] = useState( () => localStorage.getItem('theme') || 'light' ); useEffect(() => { document.documentElement.dataset.theme = theme; localStorage.setItem('theme', theme); }, [theme]); const value = useMemo(() => ({ theme, setTheme }), [theme]); return ( <ThemeContext.Provider value={value}> {children} </ThemeContext.Provider> ); }

Auth (read-only user + login/logout)

function AuthProvider({ children }) { const [user, setUser] = useState(null); const [status, setStatus] = useState('idle'); // idle | loading | ready const login = async (credentials) => { setStatus('loading'); const next = await api.login(credentials); setUser(next); setStatus('ready'); }; const logout = () => { setUser(null); setStatus('idle'); }; const value = useMemo( () => ({ user, status, login, logout }), [user, status] ); return ( <AuthContext.Provider value={value}> {children} </AuthContext.Provider> ); }

⚡ Re-renders & Performance

Context has no selector. If the Provider value is a new object, all consumers update. That is the main reason large apps move hot data to Redux or a dedicated store.

  • Memoize object/array values with useMemo.
  • Keep functions stable with useCallback (or get them from useReducer dispatch).
  • Split state vs dispatch contexts.
  • Do not put high-frequency values (mouse position, keystrokes) in Context.
  • Wrap heavy children in React.memo only after splitting context — memo does not skip context updates in the memoized component itself.

React 19 note

use(Context) can read context in more places (including some async patterns). The Provider/re-render model is the same: changing the provided value still notifies readers.

🎯 When Context is Enough

  • Dependency injection: theme, i18n, a design-system config
  • Auth session that changes rarely
  • Small apps or a small island of shared state
  • You already have Redux for domain data and only need Context for UI chrome

When many independent fields update often, and different screens need different slices, go to Redux / Redux Toolkit.

🟣 Context vs Redux

ContextRedux / RTK

Same app? Yes. Context for theme; Redux for cart and entities.

🚫 Pitfalls

  • Default value hiding a missing Provider — you think data is live; it is the fallback.
  • Storing server lists in Context — no cache, no deduping; use RTK Query or similar.
  • Inline value={{ x }} — new object every render.
  • Using Context as an event bus — dispatch a reducer or a store instead of stuffing callbacks for everything.
