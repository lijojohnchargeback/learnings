🧵 Redux Saga

Generator-based middleware for side effects: APIs, cancellation, debouncing, and long-running flows.

📚 What is a Saga?

A saga is a background worker that listens to Redux actions and runs side effects. Reducers stay pure. The saga calls APIs, then puts new actions so reducers can update state.

redux-saga uses ES6 generators so async steps look sequential, and so the library can pause, cancel, or restart the worker.

Watchers listen. Workers call APIs and put results back. takeLatest cancels the previous in-flight job.
dispatch(search/queryChanged) │ ▼ Watcher takeLatest │ ├── Worker A call(api) ✕ cancelled └── Worker B call(api) ──put──► search/fulfilled │ ▼ reducer

Thunk vs Saga in one line

A thunk is “dispatch a function that does async.” A saga is “a long-lived process that reacts to actions with declarative effects.” Thunks are simpler; sagas win at orchestration.

⚙️ Generators (Crash Course)

A generator function is declared with function*. yield pauses it and hands a value to the caller. redux-saga reads those yielded objects (effects) and performs the real work.

function* count() { yield 1; yield 2; return 3; } const it = count(); it.next(); // { value: 1, done: false } it.next(); // { value: 2, done: false } it.next(); // { value: 3, done: true }

You almost never call .next() yourself in app code. You yield effect creators; the middleware runs them.

🔧 Setup

npm install redux-saga // store.js (classic or Toolkit) import createSagaMiddleware from 'redux-saga'; import { createStore, applyMiddleware } from 'redux'; import rootReducer from './rootReducer'; import rootSaga from './rootSaga'; const sagaMiddleware = createSagaMiddleware(); const store = createStore(rootReducer, applyMiddleware(sagaMiddleware)); sagaMiddleware.run(rootSaga); // With Redux Toolkit import { configureStore } from '@reduxjs/toolkit'; const sagaMiddleware = createSagaMiddleware(); export const store = configureStore({ reducer: rootReducer, middleware: (getDefault) => getDefault({ thunk: false }).concat(sagaMiddleware) }); sagaMiddleware.run(rootSaga);

If you keep thunks (RTK default) and saga, you can concat saga without disabling thunk. Disable thunk only if you want saga as the sole async path.

📦 Effect Catalog

Effects are plain objects describing intent. The middleware executes them.

EffectRole
take(pattern) Wait until a matching action is dispatched. Resumes with that action.
takeEvery(pattern, saga) Run a worker on every matching action (parallel; can overlap).
takeLatest(pattern, saga) Start a worker; if a new action arrives, cancel the previous worker.
takeLeading(pattern, saga) Ignore new actions until the current worker finishes.
call(fn, ...args) Invoke a function (often returning a Promise). Testable: yield the descriptor, don’t run fn in tests.
put(action) Dispatch an action into the store (like dispatch).
select(selector) Read current state (optionally with a selector).
fork(saga) Non-blocking child task. Parent can cancel it. Errors bubble to parent.
spawn(saga) Detached fork. Child errors do not kill the parent.
join(task) Wait for a forked task to finish.
cancel(task) Cancel a forked task. Worker should handle cancelled().
delay(ms) Sleep. Cancel-friendly (unlike raw setTimeout in a thunk).
all([...effects]) Run in parallel; wait for all (like Promise.all).
race({ a, b }) Run in parallel; first winner cancels the rest.

👀 Watcher & Worker

A watcher saga listens. A worker saga does the job. The root saga starts watchers.

import { takeEvery, call, put, all } from 'redux-saga/effects'; function* fetchUserWorker(action) { const user = yield call(api.getUser, action.payload); yield put({ type: 'user/fulfilled', payload: user }); } function* watchFetchUser() { yield takeEvery('user/requested', fetchUserWorker); } export default function* rootSaga() { yield all([ watchFetchUser(), watchLogin(), watchCheckout() ]); }

🌐 Typical Async Flow

function* loginWorker(action) { try { yield put({ type: 'auth/pending' }); const session = yield call(api.login, action.payload); yield put({ type: 'auth/fulfilled', payload: session }); const profile = yield call(api.getProfile, session.userId); yield put({ type: 'profile/fulfilled', payload: profile }); } catch (err) { yield put({ type: 'auth/rejected', error: err.message }); } } function* watchLogin() { yield takeLatest('auth/loginRequested', loginWorker); } // UI dispatch({ type: 'auth/loginRequested', payload: { email, password } });

The reducer only handles pending / fulfilled / rejected. The saga owns the sequence: login then profile.

🛑 Cancellation, Debounce, Race

Search as you type — takeLatest

Each new keystroke cancels the in-flight request worker.

function* searchWorker(action) { yield delay(300); // debounce inside the worker const results = yield call(api.search, action.payload); yield put({ type: 'search/fulfilled', payload: results }); } function* watchSearch() { yield takeLatest('search/queryChanged', searchWorker); }

Race: request vs cancel button

function* fetchWithCancel() { const { response, cancel } = yield race({ response: call(api.slowJob), cancel: take('job/cancel') }); if (cancel) { yield put({ type: 'job/cancelled' }); return; } yield put({ type: 'job/fulfilled', payload: response }); }

Cleanup on cancel

import { cancelled } from 'redux-saga/effects'; function* fetchWorker() { const controller = new AbortController(); try { const data = yield call(api.get, { signal: controller.signal }); yield put({ type: 'data/fulfilled', payload: data }); } finally { if (yield cancelled()) { controller.abort(); } } }

🩹 Errors & Retry

function* fetchWithRetry(fn, args, retries = 3) { for (let i = 0; i < retries; i++) { try { return yield call(fn, ...args); } catch (err) { if (i === retries - 1) throw err; yield delay(500 * 2 ** i); } } } function* loadDashboard() { try { const stats = yield call(fetchWithRetry, api.getStats, []); yield put({ type: 'dashboard/fulfilled', payload: stats }); } catch (err) { yield put({ type: 'dashboard/rejected', error: err.message }); } }

🧪 Testing Sagas

Because effects are data, you can step through a generator and assert yielded descriptors (classic style), or run the saga with a mock store.

import { runSaga } from 'redux-saga'; import { call, put } from 'redux-saga/effects'; // Step style const gen = fetchUserWorker({ payload: '1' }); expect(gen.next().value).toEqual(call(api.getUser, '1')); expect(gen.next(fakeUser).value).toEqual( put({ type: 'user/fulfilled', payload: fakeUser }) ); expect(gen.next().done).toBe(true); // Integration style const dispatched = []; await runSaga( { dispatch: (a) => dispatched.push(a), getState: () => ({}) }, fetchUserWorker, { payload: '1' } ).toPromise();

⚖️ Saga vs Thunk

ThunkSaga
Mental model Function you dispatch Always-on process watching actions
Cancel / debounce Manual (AbortController, flags) Built-in (takeLatest, race, delay)
Testability Mock dispatch + APIs Yielded effects are data
Learning curve Low Generators + effect API
Typical use One-shot fetch Workflows, websockets, complex timing

🎯 When to Use Saga

  • Checkout, onboarding, or sync jobs with many steps and failure paths
  • Search, autosave, or polling that must cancel on new input or unmount
  • Coordinating several actions that are not a simple “fetch then save”

Do not reach for saga for a single GET that RTK Query or createAsyncThunk already handles.

⚠️ Avoid putting business-critical branching only in sagas with no tests. Sagas are easy to over-abstract. Prefer small workers named after the user journey (checkoutSaga, sessionSaga).
