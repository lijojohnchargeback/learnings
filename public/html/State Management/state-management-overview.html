🔄 UI State Management

An overall map of Context API, Redux, Redux Saga, and Redux Toolkit — then jump into each library in detail.

📦 What is UI State?

UI state is every piece of data that decides what the screen looks like and how it behaves right now: the logged-in user, a shopping cart, a loading spinner, a selected tab, form values, and cached API results.

React already has local state (useState, useReducer). A state management library is needed when that state must be shared, predictable, and easy to debug across many components.

The core problem

As an app grows, passing props down many layers (prop drilling) becomes noisy. Two distant components need the same data. Async calls, caching, and undo/redo appear. Libraries give you a single source of truth and a clear way to update it.

🧩 Kinds of State

Not all state belongs in a global store. Mix the right tool with the right kind of data.

Keep each kind of state in the smallest place that still works — local first, global only when shared.
KindExamplesBest home
Local UI Open/closed accordion, input draft, hover useState in the component
Shared UI Theme, current user, cart, feature flags Context API or Redux/RTK
Server / remote Product list, user profile from an API RTK Query, React Query, or Saga + store
URL state Filters, page number, selected tab React Router search params
Form state Multi-step wizard fields, validation Local state or a form library
💡 Rule of thumb: Keep state as close as possible to where it is used. Lift it only when two or more siblings (or distant trees) need it.

❓ Why These Libraries Exist

React’s Context API is built-in. Redux is a separate, predictable store. Saga sits on top of Redux for complex async. Toolkit is the official, shorter way to write Redux today.

Without a library

  • Prop drilling through 6 layers
  • Ad-hoc fetch in every screen
  • Hard to replay bugs
  • Inconsistent loading/error handling

With a clear store

  • Any component can read what it needs
  • Updates go through known actions
  • DevTools time-travel debugging
  • Side effects live in one place

How they stack

Context can stand alone. Redux replaces (or sits beside) Context for a large shared store. Saga is optional middleware on Redux. Toolkit is how you should write Redux in 2026 — you can still add Saga on top of a Toolkit store if you need it.

🎯 When to Use What

Choose Context API when…

  • You share a few values: theme, locale, current user, “is sidebar open”
  • Updates are rare (user logs in once, theme changes occasionally)
  • You do not need time-travel debugging or a large action log

Choose Redux / Redux Toolkit when…

  • Many screens read and write the same domain data (cart, dashboard, editor)
  • You want a single store, serializable state, and DevTools
  • Several developers must follow the same update pattern

Add Redux Saga when…

  • Flows are long: login → fetch profile → hydrate cache → navigate
  • You need to cancel in-flight work (search-as-you-type, route change)
  • You must race, debounce, or retry in a testable, declarative way
⚠️ 2026 default: For a new React + Redux app, start with Redux Toolkit (and RTK Query for server cache). Use classic action/reducer files only to understand the model. Add Saga only when thunks become spaghetti.

➡️ Data Flow (One-Way)

All of these tools share the same idea: UI reads state, events produce updates, updates create new state, UI re-renders.

Data never jumps backward. Events go in as actions; the UI only reads the resulting state.
UI event │ ▼ dispatch(action) ──► reducer (pure) ──► new store │ │ │ Redux Saga / thunk / RTK Query │ │ (optional side effects) │ └──────────────────────────────────────────┘ ▼ useSelector / useContext ▼ UI
Context: UI event → setState / dispatch(reducer) → Context value changes → consumers re-render Redux / Toolkit: UI event → dispatch(action) → reducer (pure) → new store → useSelector re-render Redux + Saga: UI event → dispatch(action) ↳ reducer updates sync state ↳ saga watches action → call API → put(success/failure action) → reducer

Reducers (and Context reducers) must be pure: same input → same output, no fetch, no Date.now() as a hidden dependency, no mutations of previous state (Toolkit uses Immer so you write mutations that become immutable updates).

🧭 Suggested Learning Path

  1. Read this overview so the vocabulary is shared.
  2. Open Context API — you will use it even in Redux apps (theme, i18n).
  3. Open Redux — understand store, actions, and reducers without shortcuts.
  4. Open Redux Toolkit — this is how production Redux is written.
  5. Open Redux Saga when you need advanced async orchestration.
💡 Interview angle: Be ready to explain why Context can over-render, why Redux state should be serializable, what problem Saga solves vs thunks, and why Toolkit’s createSlice still produces the same actions/reducers underneath.

🚫 Common Mistakes

  • Putting everything in Redux — local hover state does not belong in the store.
  • One giant Context — every consumer re-renders on any change. Split contexts or use a store.
  • Fetching inside reducers — reducers stay pure; async lives in thunks, sagas, or RTK Query.
  • Non-serializable values in Redux — no class instances, Promises, or functions in state/actions.
  • Saga for a single GET — a thunk or RTK Query endpoint is simpler.
  • Skipping selectors — components subscribe to huge slices and re-render constantly.
