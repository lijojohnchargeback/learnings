Essential Software Engineering Concepts

Build reliable systems, prevent production failures, improve performance, and deploy changes safely — beyond writing feature code.

Why these concepts matter

As a software engineer working with Node.js, React, APIs, databases, and cloud deployments, coding alone is not enough. The highest-leverage skills are the ones that keep systems correct under retries, fast under load, and safe under continuous release.

How the pieces connect

Efficient queries improve performance. Idempotency makes retries safe. Queues control workloads. Observability detects problems. Canary deployments reduce release risk. Learn them as a connected system, not isolated buzzwords.

What this topic covers

  • Database performance (N+1, indexes, pooling)
  • API correctness (idempotency, validation)
  • Reliability patterns (timeouts, circuit breakers)
  • Safe deployments (canary, blue-green, flags)
  • Queues, concurrency, and observability

Recommended starting trio

  1. N+1 queries — stop silent latency
  2. Idempotency — retry without duplicates
  3. Canary deployment — ship with a safety net

2A. The N+1 query problem

Suppose your API returns 100 merchants and their reports. A naive loop fetches reports one merchant at a time.

Bad path: 101 queries

Query 1
All merchants
→
Queries 2–101
Report per merchant
→
High latency
DB + network cost
Bad (Node.js + MongoDB): one query inside the loop for every merchant.
const merchants = await Merchant.find(); for (const merchant of merchants) { merchant.reports = await Report.find({ merchantId: merchant._id }); }
Better: batch with $in, then group in memory. Often 1–2 queries total.
const merchants = await Merchant.find(); const ids = merchants.map(m => m._id); const reports = await Report.find({ merchantId: { $in: ids } }); const byMerchant = new Map(); for (const report of reports) { const key = String(report.merchantId); if (!byMerchant.has(key)) byMerchant.set(key, []); byMerchant.get(key).push(report); } for (const merchant of merchants) { merchant.reports = byMerchant.get(String(merchant._id)) || []; }

SQL vs MongoDB

  • SQL: prefer a JOIN or a second batched query with WHERE merchant_id IN (...)
  • MongoDB: $in batching or $lookup aggregation
  • ORMs: eager loading / include / populate — but verify the generated SQL

Why it matters: fewer round trips reduce API latency, database load, and cloud cost. Pair this with indexes, query plans, pagination, and avoiding over-fetching.

2C. Why “username already taken” feels instant

Signup forms often show “username already taken” within ~100–300ms while you type. That speed is not magic — it is several small optimizations stacked together.

1. Unique index on username

A unique index turns “does this name exist?” into an index lookup (O(log n)), not a full table scan. Millions of users still answer in milliseconds.

2. Server / edge near the user

CDN, regional API, or edge function cuts network RTT. A light check that takes 5ms in the DB still feels slow if the round trip is 400ms across continents.

3. Lightweight API

Endpoint does almost nothing: validate format → indexed exists query → return { available: false }. No heavy joins, no auth side effects, tiny JSON.

4. Debounce on the client

Wait ~300ms after the user stops typing before calling the API. Prevents a request on every keystroke and keeps the server cool.

'free' : 'taken'); }, 300); // debounce return () => clearTimeout(t); }, [username]); return status; }

Still enforce uniqueness on write

The availability check is a UX hint. Two users can still race and both see “available.” The unique index (or unique constraint) on insert is the real guarantee — catch the duplicate-key error and show “already taken.”

3A. Idempotency

Production checklist for idempotent POST

  • Persist the key and result (or in-progress lock) atomically
  • Handle concurrent requests with the same key (unique constraint / transaction)
  • Reject the same key reused with a different payload
  • Account for payment-provider behavior (they may also be idempotent)

HTTP note: GET, PUT, and DELETE are defined as idempotent methods. POST is not inherently idempotent — you make it so by design.

3A+. Invoice POST: accidental double-click

User clicks Create Invoice. The network is slow, so they click again. Without protection you get two invoices, two emails, two ledger entries.

UI alone is not enough. Disabling the button helps, but a retry, a second tab, or a flaky network can still send the POST twice. The server must also be idempotent.

Defense in depth (use both)

1. Client: disable submit while waiting

On first click, disable the button (and show a spinner). Re-enable only after the response — success or error. Stops most accidental double submits.

2. Server: client-generated idempotency key

Before the first request, the client generates one UUID (or key). Every retry of that “create invoice” action sends the same key. Server creates the row once and returns the same result.

// Client (React) — generate key once per "intent", disable while in flight import { useRef, useState } from 'react'; import { v4 as uuid } from 'uuid'; function CreateInvoiceButton({ payload }) { const [loading, setLoading] = useState(false); const idempotencyKey = useRef(uuid()); // one key for this form submit intent async function onSubmit() { if (loading) return; // ignore extra clicks setLoading(true); // disable submit immediately try { const res = await fetch('/invoices', { method: 'POST', headers: { 'Content-Type': 'application/json', 'Idempotency-Key': idempotencyKey.current, }, body: JSON.stringify(payload), }); const invoice = await res.json(); // success → navigate or show invoice return invoice; } catch (err) { // keep the SAME key so a retry does not create a second invoice throw err; } finally { setLoading(false); // re-enable after response } } return ( <button type="button" disabled={loading} onClick={onSubmit}> {loading ? 'Creating…' : 'Create invoice'} </button> ); }
// Server (Node) — unique index on idempotencyKey guarantees one entry // db.invoices.createIndex({ idempotencyKey: 1 }, { unique: true }) app.post('/invoices', async (req, res) => { const key = req.header('Idempotency-Key'); if (!key) return res.status(400).json({ error: 'Idempotency-Key required' }); const existing = await Invoice.findOne({ idempotencyKey: key }); if (existing) { return res.status(200).json(existing); // same key → same invoice } try { const invoice = await Invoice.create({ ...req.body, idempotencyKey: key, }); return res.status(201).json(invoice); } catch (err) { // concurrent double POST: unique index won the race if (err.code === 11000) { const again = await Invoice.findOne({ idempotencyKey: key }); return res.status(200).json(again); } throw err; } });

Key rules

  • Client generates the key once per user intent (e.g. when the form mounts or on first click) — not a new UUID on every retry
  • Server stores the key with a unique constraint and returns the stored invoice on repeats
  • Disable the button after click until the response arrives (UX layer)
  • On success, generate a new key only if the user starts creating a different invoice
Think of it as: UI prevents casual double-clicks; idempotency key prevents duplicate invoices when the network or the user still sends the request twice.

4A. Canary deployment

Release a new version to a small percentage of users first. If it stays healthy, increase traffic. If not, roll back immediately.

Stable v1 — 95%
Canary v2 — 5%

Monitor the canary

  • Error rate and HTTP 5xx
  • Latency (especially p95 / p99)
  • CPU, memory, database load
  • Business metrics and correctness

Decide

  • Healthy: 5% → 10% → 25% → 50% → 100%
  • Unhealthy: stop rollout, route all traffic back to v1

Percentages are examples — choose based on traffic volume, risk, and detection speed.

4B. Compare deployment strategies

Canary

Gradually expose the new version to a small group. Best for limiting risk and validating real production behavior.

Blue-green

Two environments; switch traffic from old to new. Fast rollback if the old environment stays ready.

Rolling

Replace old instances gradually with new ones. Natural fit for multi-replica services.

Feature flags

Deploy code with a feature off or limited. Turn it off without necessarily redeploying.

Related deployment topics

  • CI/CD — automatically test, build, and deploy
  • Readiness / liveness probes — should this instance get traffic? Should it restart?
  • Graceful shutdown — stop accepting new work; finish in-flight requests
  • Zero-downtime deploys — no interruption during release
  • Database migration safety — old and new app versions must coexist
  • Rollback vs roll-forward — restore old version, or ship a fix
  • Infrastructure as code — version-controlled infrastructure
  • Immutable artifacts — promote the same tested build across environments

Critical rule

Rolling back application code does not automatically roll back database changes. Use backward-compatible schema changes and a deliberate migration plan (expand → migrate → contract).

A queue separates the API that accepts a task from the workers that perform it. Essential when processing URLs, generating reports, or calling slow external APIs.

Typical async job flow

  1. Accept and validate the request
  2. Store a job record
  3. Put the job on a queue
  4. Workers process with controlled concurrency
  5. Track progress and final status
  6. Retry transient failures; send exhausted jobs to a DLQ

5C. Concurrency and race conditions

Two requests update the same merchant at almost the same time — a classic lost update.

Request A

  1. Read balance = 100
  2. Compute 100 − 20 = 80
  3. Write balance = 80

Request B (overlapping)

  1. Read balance = 100
  2. Compute 100 − 30 = 70
  3. Write balance = 70

A's update is overwritten. Final balance is wrong.

Prefer atomic updates ($inc, UPDATE ... SET balance = balance - 20) or optimistic locking with a version field.

Also learn: distributed locks/leases, deadlocks, worker concurrency limits, mutexes/semaphores, event ordering, and shared mutable state. Distributed locks need clear ownership, expiration, and recovery.

5D. Optimistic vs pessimistic locking

Both solve the lost update problem (two requests overwrite each other). They differ in when they stop conflicts.

Optimistic locking

“Assume no conflict; check at write time.”

  • Read the row including a version (or updatedAt)
  • Change data in memory
  • Write only if version is still the same
  • If someone else wrote first → fail and retry / show conflict

Pessimistic locking

“Assume conflict; lock first.”

  • Begin a transaction
  • SELECT … FOR UPDATE (row lock)
  • Other writers wait (or fail) until you commit/rollback
  • Only one writer holds the row at a time
OptimisticPessimistic
When lock happensAt update (version check)At read (row lock)
Best whenConflicts are rareConflicts are common / costly
ThroughputUsually higher (no waiting)Lower under contention
Failure modeUpdate returns 0 rows → conflictWaiters block; risk of deadlock
Typical useEdit profile, CMS, shopping cartBank transfer, inventory seat booking
Works well withHTTP APIs, long user think-timeShort DB transactions

Refresh and try again.'); }
-- SQL optimistic lock UPDATE merchants SET name = $1, version = version + 1 WHERE id = $2 AND version = $3; -- If rowcount = 0 → conflict

-- PostgreSQL pessimistic lock (keep the transaction SHORT) BEGIN; SELECT balance FROM accounts WHERE id = $1 FOR UPDATE; -- balance is locked; other writers wait here UPDATE accounts SET balance = balance - 20 WHERE id = $1; COMMIT;
// MongoDB: findOneAndUpdate is atomic (often better than a long lock) const updated = await Account.findOneAndUpdate( { _id: id, balance: { $gte: 20 } }, { $inc: { balance: -20 } }, { new: true } ); if (!updated) throw new Error('Insufficient funds or missing account');

How to choose

  • Optimistic — user edits a form, opens a page, thinks for seconds/minutes, then saves. Locking the DB row that whole time would be terrible.
  • Pessimistic — money, seats, inventory where two simultaneous writers must not both succeed. Keep the lock duration tiny (milliseconds inside a DB transaction).
  • Atomic update — often the simplest: $inc / SET balance = balance - 20 with a condition. Prefer this when you can express the change without a separate read-modify-write.
Do not hold a pessimistic lock across HTTP calls, emails, or user input. Lock → do work that can wait → other requests pile up or deadlocks appear.
Optimistic locking pairs well with APIs: return 409 Conflict when versions clash, and let the client refresh and retry.

11. Caching strategies

Caching reduces repeated expensive reads, but wrong invalidation creates stale or inconsistent data. Treat cache as an optimization layer, not the source of truth.

Cache-aside (lazy)

App reads cache → on miss, load DB → write cache. Most common for APIs.

Write-through

Writes go to cache and DB together. Stronger freshness, more write latency.

TTL + soft TTL

Expire after time. Soft TTL serves stale briefly while one request refreshes.

Cache stampede

Many requests miss at once and hammer the DB. Use locks, singleflight, or jittered TTL.

// Cache-aside sketch (Redis) async function getMerchant(id) { const key = `merchant:${id}`; const cached = await redis.get(key); if (cached) return JSON.parse(cached); const merchant = await Merchant.findById(id); if (merchant) { await redis.set(key, JSON.stringify(merchant), 'EX', 300); } return merchant; }

Invalidation rules of thumb

  • Prefer short TTLs for volatile data; longer TTLs for mostly-static reference data
  • On write, delete or update related keys deliberately
  • Never cache personalized or permission-sensitive payloads carelessly
  • Measure hit rate and origin load — a cache that is never hit is wasted cost

13. Rate limiting

Rate limits protect your API and downstream dependencies from abuse, bugs, and traffic spikes.

Fixed window

N requests per calendar minute. Simple; can burst at window edges.

Sliding window

Smoother limit over a rolling period. More accurate, slightly costlier.

Token bucket

Allows short bursts while enforcing average rate. Common at gateways.

14. Authentication patterns

Session cookies

Server stores session; browser sends HttpOnly cookie. Easy to revoke. Watch CSRF on cookie-based apps.

JWT (bearer)

Stateless claims in a signed token. Scale well; harder to revoke early unless you add a denylist or short TTL + refresh.

OAuth 2.0 / OIDC

Delegate login to an identity provider. Use for “Sign in with …” and third-party API access.

API keys

Service-to-service or partner access. Store hashed; scope tightly; rotate.

Authorization is separate

Authentication answers “who are you?” Authorization answers “what may you do?” Always check object-level access (IDOR): owning merchantId in the path does not mean the caller may read it.

17. CAP theorem and consistency

During a network partition, a distributed system cannot be fully Consistent and Available at the same time. You choose a trade-off.

Consistency

Every read reflects the latest successful write (within the model you chose).

Availability

Every non-failing node can still respond.

Partition tolerance

System continues despite network splits — required in real networks.

ModelMeaningTypical use
Strong consistencyRead sees latest committed writeBalances, inventory reservations
Eventual consistencyReplicas converge laterFeeds, search indexes, analytics
Read-your-writesUser sees their own updates promptlyProfile edits, settings
Pick consistency per data type. Not everything needs strong consistency — and paying for it everywhere costs latency and availability.

18. Outbox pattern and sagas

Transactional outbox

Write business data and an “event to publish” row in the same DB transaction. A relay publishes to the queue. Prevents “DB committed but message lost.”

Saga

Multi-step business workflow across services. Each step has a compensating action if a later step fails (e.g. reserve stock → charge card → ship; on charge fail, release stock).

19. Webhooks

Webhooks notify your system when something happens elsewhere (payment captured, repo push, email delivered).

  • Verify signatures — HMAC or provider-specific signing secrets
  • Idempotent handlers — providers retry; process each event once
  • Respond fast — ack quickly, do heavy work on a queue
  • Timeouts & retries — expect at-least-once delivery
  • Replay protection — store event IDs; reject duplicates

21. Feature flags in depth

Flags separate deploy from release. You can ship dark code and turn it on for 1%, one tenant, or everyone — or kill it instantly.

Good uses

  • Gradual rollout of risky features
  • A/B experiments
  • Kill switches for broken paths
  • Per-tenant entitlements

Pitfalls

  • Flag debt (permanent if/else forests)
  • Testing every flag combination
  • Flags that change DB schema unsafely
  • Client/server flag mismatch
Clean up flags after rollout. A flag that lived longer than the feature launch is usually accidental complexity.

22. Incident response basics

  1. Detect — alerts from SLOs, error rate, or user reports
  2. Triage — severity, blast radius, who is impacted
  3. Mitigate — rollback, disable flag, scale up, shed load — stop the bleeding first
  4. Diagnose — logs, metrics, traces, recent deploys
  5. Resolve — permanent fix, verify with monitors
  6. Learn — blameless postmortem, action items with owners

During the incident

One incident commander, short status updates, mitigate before perfect root cause.

After the incident

Timeline, contributing factors, what worked, what to change in code/process/alerts.
