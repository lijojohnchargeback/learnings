🏗️ System Design Complete Guide

From Developer to Architect

📚 Introduction to System Design

System Design is the process of defining the architecture, components, modules, interfaces, and data for a system so it can satisfy specified requirements — usually under real-world constraints of scale, latency, cost, and failure.

In interviews and production, “design a system” means more than drawing boxes. You clarify requirements, estimate load, pick a high-level architecture, then go deep on the pieces that will actually break: the database, the cache, the queue, and the failure modes.

How to approach a design

  • Clarify – functional vs non-functional requirements, read/write ratio, data size
  • Estimate – QPS, storage, bandwidth, how many servers you actually need
  • Sketch – client → edge → app → data stores → async path
  • Deep dive – the 2–3 bottlenecks (usually DB, cache, and fan-out)
  • Harden – failures, consistency, security, observability, cost

Key Objectives

Every serious design is a trade-off among a small set of goals. Name them out loud so you do not optimize the wrong one.

⚡ Performance

Minimize latency, maximize throughput. p50 vs p99 matters more than average.

📈 Scalability

Handle 10× or 100× users by adding machines, not by rewriting the product.

🛡️ Reliability

Stay available and correct when nodes, networks, and deploys fail.

🔒 Security

Protect data in transit and at rest; authenticate, authorize, and audit.

🚀 Operability

Easy to deploy, roll back, observe, and debug at 3 a.m.

💰 Cost

Right-size storage, compute, and egress. Premature sharding is expensive.

Back-of-envelope Estimates

Architects estimate before they scale. These numbers are good enough for interviews and capacity planning.

Numbers worth memorizing

  • L1 cache ~0.5 ns · RAM ~100 ns · SSD ~100 µs · HDD ~10 ms · datacenter RTT ~0.5 ms · continent ~50–150 ms
  • 1 request/sec ≈ 86,400 requests/day. 1M users × 10 requests/day ≈ 116 QPS average (spike higher)
  • 1 character ≈ 1 byte. 1 million 1 KB records ≈ 1 GB. A year of 1 KB writes at 100 QPS ≈ ~3 TB
  • A typical app server: thousands of QPS if I/O-bound and cached; a single DB primary is often the first wall
Example: URL shortener at 100M new URLs / month Writes ≈ 100e6 / (30 * 86400) ≈ 40 QPS (peak ~200 QPS) Reads at 10:1 → ~400 QPS avg, ~2k peak Storage: 100M * 500 bytes ≈ 50 GB / month → ~600 GB / year

Always state assumptions: DAU, requests per user, read/write ratio, payload size, and peak multiplier (often 3–10× average).

⚡ Performance

What is Performance?

Performance measures how fast or responsive a system is under a given workload and hardware. Optimize the critical path: the work that sits on every user request.

Performance Metrics

  • Latency: Wait time + processing time (track p50, p95, p99 — not only average)
  • Throughput: Requests processed per second (QPS / RPS)
  • Response time: Total time until the client has a complete answer
  • Resource utilization: CPU, memory, disk, network — headroom prevents collapse at peak
  • Saturation: Queues growing means you are past capacity even if average CPU looks fine

1. Network Latency

Time taken for data to travel between client and server — often the largest slice of user-facing latency. You cannot make light faster; you can move work closer and send less of it.

Solutions

  • ✅ Connection pooling: Reuse TCP/TLS connections instead of handshaking every request
  • ✅ Compression: gzip / brotli for text; image CDNs for media
  • ✅ CDN: Serve static (and some dynamic) content from the nearest PoP
  • ✅ TLS session resumption: Avoid a full handshake on every visit
  • ✅ HTTP/2 or HTTP/3: Multiplex streams, fewer connections, better loss recovery
  • ✅ Keep-alive / persistent connections: Cut handshake cost for chatty APIs
  • ✅ Regional deployment: Put app + data near users when a single region is too far

2. Memory & CPU

Memory latency

Challenges

  • ⚠️ Large heap memory = aggressive garbage collection pauses
  • ⚠️ Memory bloat = cache eviction, swapping, and poor locality
  • ⚠️ Memory leaks = slowly rising RSS until the process is killed

Solutions

  • ✅ Bound caches (LRU + max memory). Never unbounded in-process maps of “hot” data
  • ✅ Use weak/soft references or off-heap stores for large objects
  • ✅ Prefer multiple smaller processes/pods over one giant JVM/Node heap
  • ✅ Tune GC (G1/ZGC, Node --max-old-space-size) and measure pause times

CPU performance

Issues

  • ❌ Inefficient algorithms (O(n²) on hot paths)
  • ❌ Excess context switching and lock contention
  • ❌ JSON encode/decode and crypto on every request without need

Solutions

  • ✅ Efficient algorithms and indexed queries
  • ✅ Batch / async I/O so the CPU is not blocked waiting on disk or network
  • ✅ Event-loop or well-sized thread pools (Node, Nginx, Go goroutines)
  • ✅ Profile before rewriting — CPU flame graphs beat guesses

3. Disk I/O Latency

Disk is orders of magnitude slower than RAM. Sequential writes (logs, WAL) beat random writes. Indexes turn table scans into seeks.

Solutions

  • ✅ Sequential I/O: Append-only logs (Kafka, WAL, LSM trees)
  • ✅ Batch I/O: Group writes; flush on interval or size, not per row
  • ✅ Async I/O: Do not block the request thread on slow disks
  • ✅ Query optimization: Indexes, covering queries, avoid N+1
  • ✅ Data caching: Redis / Memcached in front of hot keys
  • ✅ SSD: Lower latency and better random IOPS than HDD
  • ✅ Partitioning: Keep working set smaller per node

Caching Strategy

Requests try fast layers first. A HIT returns early; a MISS loads from the database and warms the cache with a TTL.

Cache the result of expensive or frequent work. Every cache needs a key, a TTL, an eviction policy, and a plan for invalidation.

Cache types

  • HTTP / browser cache: Cache-Control, ETag — free capacity at the client
  • CDN / static cache: Images, CSS, JS, public API responses at the edge
  • Application cache: Redis objects, sessions, computed aggregates
  • Database cache: Buffer pool, query result cache (use carefully)
  • Full-page / fragment cache: Rendered HTML for mostly-static pages

Common patterns

Pattern How it works Use when
Cache-aside App reads cache; on miss, load DB and populate cache Most web apps (Redis + Postgres)
Read-through Cache itself loads the store on miss You want the app unaware of the DB
Write-through Writes go to cache and DB together Read-heavy data that must stay consistent
Write-behind Write cache first; async flush to DB Very high write QPS; accept delay / risk

When NOT to cache — and classic pitfalls

  • ❌ Data that changes every request, or must be strictly real-time
  • ❌ User-specific secrets in a shared public cache key
  • ❌ Stampede: many clients miss together — use locking, stale-while-revalidate, or probabilistic early expiry
  • ❌ Thundering herd after a deploy that flushes everything — warm in stages

📈 Scalability

Scalability is the ability to handle increased load by adding resources — without a linear explosion in operational pain.

Scale up buys time. Scale out buys headroom — if the app is stateless and the data layer can split work.

Types of scaling

Type Description Pros Cons
Vertical scaling
(Scale up)		 Add CPU, RAM, or disk to the same machine ✅ Simple
✅ No code changes		 ❌ Hardware ceiling
❌ Single point of failure
❌ Cost grows fast
Horizontal scaling
(Scale out)		 Add more machines behind a balancer ✅ Near-unlimited capacity
✅ High availability
✅ Commodity hardware		 ❌ Statelessness required
❌ Data consistency is harder

Practical rule: scale the app tier horizontally first (cheap), then cache, then replicate the database for reads, then shard only when a single primary cannot take writes.

Load Balancing

A load balancer distributes traffic across healthy servers, terminates TLS, and hides individual instance failures from clients.

Unhealthy instances are pulled from rotation. Algorithms trade evenness, locality, and connection reuse.

Algorithms

  • Round robin: Equal share; fine when servers are identical
  • Least connections: Send to the server with the fewest in-flight requests (good for long-lived connections)
  • Weighted round robin: Bigger instances get more traffic
  • Least response time: Prefer the currently fastest backend
  • IP hash / consistent hash: Same client → same server (sessions, cache locality)

L4 vs L7

  • L4 (TCP): Fast, protocol-agnostic, less insight into HTTP paths
  • L7 (HTTP): Route by path, header, or host; can do canaries, WAF, auth at the edge

Health checks must match real readiness: a process that accepts TCP but cannot talk to the database should not receive traffic. Use a /health that checks dependencies with timeouts.

Database Scaling

Replication multiplies read capacity. Sharding splits writes and storage when one primary is no longer enough.

Indexes

An index is a side structure (usually a B-tree) that turns “scan the table” into “jump to the row.” Index the columns you filter and join on. Too many indexes slow writes.

Replication (primary–replica)

  • 🔷 Primary: All writes (and strongly consistent reads if you need them)
  • 🔷 Replicas: Serve reads; lag is typically milliseconds to seconds
  • ✅ High read scalability and a hot standby for failover
  • ⚠️ Replica lag: a read-your-writes user may not see their own update unless you read from primary or use session stickiness

Sharding (horizontal partitioning)

  • Split rows across databases so no single node holds everything
  • Range sharding: IDs 1–10k, 10k–20k — simple, but hot ranges (new users) pile onto one shard
  • Hash sharding: hash(user_id) % N — even spread; range scans across shards are painful
  • Directory / lookup: A mapping service decides the shard (flexible, extra hop)
  • ✅ Handles massive datasets and write QPS
  • ❌ Cross-shard joins and transactions become application problems

Consistent Hashing

When you add or remove a cache or shard node, you do not want to remap every key. Consistent hashing places nodes and keys on a ring; a key belongs to the next node clockwise. Adding a node only steals keys from its neighbor.

Virtual nodes (many positions per physical server) keep load even when hardware sizes differ.

Where it shows up

  • Distributed caches (Memcached clusters, some Redis cluster modes)
  • Partition assignment in streaming systems
  • Load balancers that want session affinity without a sticky table
  • CDN / edge cache key placement

Microservices & Message Queues

Microservices architecture

Split a monolith along business boundaries (users, billing, feed) so teams can deploy and scale independently. You pay for this with network hops, distributed transactions, and operational complexity.

Benefits

  • ✅ Independent deployment and scaling
  • ✅ Technology flexibility per service
  • ✅ Fault isolation (if you design for it)
  • ✅ Smaller, focused teams

Costs

  • ❌ Distributed debugging and eventual consistency
  • ❌ Network latency between services
  • ❌ Need for a platform: tracing, service mesh, CI/CD, on-call
  • ❌ Start with a modular monolith unless you have a real scaling or team boundary

Message queues

Decouple components and absorb spikes. The API returns quickly; workers do the slow work.

Producers enqueue; workers pull. Failed jobs retry, then land in a dead-letter queue for inspection.
  • RabbitMQ: Smart broker, competing consumers, classic task queues
  • Kafka: High-throughput log; consumers keep offsets so messages can be replayed
  • AWS SQS: Managed queue; pair with SNS for fan-out

Use cases

  • 📧 Email and push notifications
  • 📊 Report generation and ETL
  • 🖼️ Image / video processing
  • 🔔 Webhooks to third parties (with retries)
  • 📰 Feed fan-out (write to many timelines asynchronously)

🛡️ Reliability & Fault Tolerance

Reliability means the system stays available and correct even when parts fail. Design for failure; it is the normal case at scale.

Types of failures

  • 🔴 Network failure: Packet loss, partitions, DNS blips
  • 🔴 Machine failure: Disk, host, zone outage
  • 🔴 Software failure: Bugs, memory leaks, deadlocks
  • 🔴 Deployment failure: Bad release, schema mismatch
  • 🔴 Load-induced failure: Traffic spike, retry storms, cache flush

Useful numbers: SLA / SLO (e.g. 99.9% availability ≈ 8.8 hours down per year). Error budgets tell you how much risk you can take on deploys.

Redundancy Strategies

1. Active redundancy (active–active)

  • All servers handle traffic
  • If one fails, others absorb the load (keep spare capacity)
  • Example: N app servers behind a load balancer

2. Passive redundancy (active–passive)

  • Primary handles traffic; standby takes over on failure
  • Example: database primary + hot standby

3. Cold redundancy

  • Backups or offline environments; slower RTO
  • Fine for disaster recovery, not for user-facing APIs

Spread replicas across availability zones. A single rack or AZ is one failure domain.

Circuit Breaker Pattern

When a dependency is sick, calling it harder makes everything worse (threads pile up, retries amplify load). A circuit breaker stops sending traffic after a failure threshold, then probes recovery.

Closed = normal. Open = fail fast to a fallback. Half-open = a trial request decides whether to close again.
  • Closed: Requests flow; failures are counted
  • Open: Calls fail immediately (or hit a cache / default); the dependency gets time to recover
  • Half-open: A small number of trial requests; success closes the circuit, failure re-opens it

Pair with timeouts that are shorter than the user’s patience, and with bulkheads so one slow dependency cannot exhaust the whole thread pool.

Health Checks & Retry Strategies

Health checks

  • 🩺 Liveness: Process is running (restart if this fails)
  • 🩺 Readiness: Can serve traffic (DB connected, warmup done)
  • 🩺 Heartbeat: Periodic signal in clustered systems

Retry strategies

  • 🔄 Immediate retry: Only for clearly transient errors, and only once or twice
  • 🔄 Exponential backoff + jitter: 1s, 2s, 4s… with randomness so clients do not retry in lockstep
  • 🔄 Idempotency keys: Safe to retry POSTs that create resources
  • 🔄 Circuit breaker: Stop retrying a known-down dependency

Retries without backoff turn a small outage into a retry storm. Cap attempts, add jitter, and prefer queues for work that can wait.

🔒 Security — Authentication

Authentication vs authorization

Authentication Authorization
Verifying identity (“Who are you?”) Verifying permissions (“What can you do?”)
Login with password, SSO, passkeys Role-based or attribute-based access control
Session cookie or JWT proves the login Policies decide which resources that identity may touch

Authentication methods

  • 🔐 Session-based: Server stores session; cookie is an opaque ID. Easy to revoke
  • 🔐 Token-based (JWT): Stateless at the API; harder to revoke unless you keep a denylist or short TTL + refresh
  • 🔐 OAuth 2.0 / OIDC: Delegate login to Google, GitHub, a company IdP
  • 🔐 MFA: Password + TOTP / WebAuthn — stops most credential stuffing

Authorization

Never trust the client. Check permission on every request for the specific resource (object-level), not only “is logged in.”

  • RBAC: Roles like admin, editor, viewer
  • ABAC: Rules on attributes (department, resource owner, time of day)
  • ACL: Per-object lists (Google Docs style sharing)

APIs should return 401 when identity is missing/invalid and 403 when identity is known but not allowed — do not leak whether a resource exists if that is sensitive.

OWASP Top 10 & Hardening

Vulnerability Description Prevention
Injection SQL, command, or template injection Parameterized queries, never concatenate untrusted input into queries
XSS Injected scripts in the browser Escape output, Content-Security-Policy, sanitize HTML
Broken authentication Weak passwords, stolen sessions MFA, hashed passwords (Argon2/bcrypt), secure cookie flags
Sensitive data exposure Cleartext secrets or PII TLS everywhere, encrypt at rest, minimize what you store
Broken access control IDOR: user A fetches user B’s object by guessing an ID Authorize every object; do not rely on hidden IDs

Security best practices

  • ✅ HTTPS (TLS) for all traffic; HSTS
  • ✅ Hash passwords (bcrypt, Argon2) — never reversible encryption for passwords
  • ✅ Rate limiting and bot protection on login and expensive endpoints
  • ✅ Input validation at the boundary; output encoding at the view
  • ✅ Security headers: CSP, HSTS, X-Frame-Options / frame-ancestors
  • ✅ Principle of least privilege for DB users, IAM roles, and secrets
  • ✅ Logging, alerting, and a process to rotate leaked credentials

🎯 CAP Theorem

The CAP Theorem says that during a network partition, a distributed system cannot be both fully consistent and fully available. You pick a side for that failure mode. Partition tolerance is not optional on a real network.

On a partition you choose CP (refuse some requests to stay correct) or AP (keep serving, reconcile later).
PropertyDescriptionExample
ConsistencyEvery read sees the latest write (linearizability)Bank ledger, inventory decrement
AvailabilityEvery non-failing node returns a responseSocial feed, “likes” counters
Partition toleranceThe system keeps a defined behavior when the network splitsMulti-AZ / multi-region

Trade-offs (simplified)

  • CA: Single-node or tightly coupled RDBMS in one failure domain (MySQL, PostgreSQL on one primary)
  • CP: Prefer correctness: MongoDB (majority concern), etcd, ZooKeeper, Redis with strong settings
  • AP: Prefer liveness: Cassandra, DynamoDB (eventual), CouchDB — conflict resolution later

PACELC adds: even without a partition, you still trade latency vs consistency (sync replication vs async).

🌐 Distributed Systems

Key challenges

  • 🔄 Data consistency: Replicas diverge; you choose strong, sequential, or eventual
  • ⏱️ Latency: Every hop and cross-region RTT is visible to users
  • 🔀 Concurrency: Lost updates, compare-and-swap, optimistic locking
  • ⚠️ Failure handling: Timeouts, retries, fencing tokens, leader election
  • 🕐 Time: Do not trust unsynchronized clocks for correctness; use logical clocks or a true-time API when you must

Consensus

  • Paxos: Classic, notoriously subtle
  • Raft: Leader + log replication; used in etcd, Consul, many DBs
  • BFT: Survive malicious nodes (blockchains); expensive

Replication strategies

  • Synchronous: Wait for replicas — strong consistency, higher write latency
  • Asynchronous: Primary acknowledges first — faster, possible data loss on crash
  • Quorum (R + W > N): Dynamo-style tunable consistency

Unique IDs at scale

Auto-increment IDs do not work across shards. Options: UUID v4 (simple, not sortable), ULID/UUIDv7 (time-sortable), Twitter Snowflake (timestamp + worker + sequence). Avoid coordinating a global counter on every insert.

🔌 API Design Best Practices

REST principles

  • ✅ HTTP methods: GET (read), POST (create), PUT/PATCH (update), DELETE
  • ✅ Nouns for resources: /users, /products/42/reviews
  • ✅ Status codes: 200, 201, 204, 400, 401, 403, 404, 409, 429, 500
  • ✅ Version: /api/v1/... or header-based versioning
  • ✅ Pagination (cursor-based at scale), filtering, sorting
  • ✅ Idempotency for payments and order creation

API security

  • 🔐 OAuth 2.0 or session/JWT with short access tokens
  • 🔐 Rate limiting (token bucket / sliding window) per user and per IP
  • 🔐 Validate and bound payload size
  • 🔐 HTTPS only; never put secrets in query strings
  • 🔐 API keys for server-to-server; rotate them

Response shape

{
  "status": "success",
  "data": {
    "id": 1,
    "name": "John Doe"
  },
  "message": "User retrieved successfully",
  "timestamp": "2024-01-01T12:00:00Z"
}

GraphQL, gRPC, and webhooks are alternatives when REST’s round-trips or payload shape become the bottleneck — pick them for a reason, not for fashion.

Observability

You cannot operate what you cannot see. The three pillars:

  • Logs: Structured events (JSON) with request IDs — searchable, not a wall of print statements
  • Metrics: QPS, latency histograms, error rate, saturation (RED / USE methods)
  • Traces: One request across services (OpenTelemetry) so you see which hop is slow

Alert on symptoms users feel (error rate, p99 latency, checkout success), not only on CPU. Dashboards plus on-call runbooks close the loop.

Case Study: URL Shortener

A classic interview problem that uses almost every idea above. Product: turn a long URL into a short code; redirect on GET.

Writes persist a mapping. Reads should almost always hit cache, then 302 to the original URL.

Requirements (typical)

  • Create short URL; optional custom alias and expiry
  • Redirect with HTTP 301/302; analytics (click count) can be async
  • High read:write ratio; 100M+ redirects/day is a common prompt

Core design

  1. API: POST /urls returns https://short.ly/abc123; GET /abc123 redirects
  2. ID generation: Base62-encode a Snowflake ID, or hash the URL and take 7 characters (handle collisions)
  3. Storage: short_code → long_url, created_at, owner in a SQL store; shard by hash(code) if huge
  4. Cache: Redis for hot codes (viral links); TTL plus write-through on create
  5. Scale reads: CDN or edge cache for 301s if the mapping is immutable
  6. Analytics: Enqueue click events; workers aggregate — do not write the DB on every redirect
GET /abc123 → LB → App → Redis GET abc123 HIT → 302 Location: https://example.com/... MISS → DB lookup → set Redis → 302 → (async) click event → Kafka → counters

Same playbook for rate limiters (token bucket in Redis), news feeds (fan-out on write vs read), and chat (gateway + fan-out + partitioned message store). Always start from QPS and data size, then pick the boxes.
